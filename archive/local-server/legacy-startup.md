# RelayForge · 接力工坊

本地单项目开发工作台。你在网页提交目标与验收条件，主 Agent 读取代码拟定计划，一个 Worker 在独立 Git worktree 内实现和交接。PostgreSQL 保存项目线程、任务队列、裁定、检查点与集成结果。首版规划和执行都使用本机登录的 Codex CLI，执行进程退出后仍可换会话接手。项目目录和专用数据库一一对应。

## 启动

在本目录运行。需要 Python 3.10+、Git、已登录的 Codex、可连接的 PostgreSQL 和 psql。下面使用本机默认 socket 和当前用户，如需指定连接可设置 PGHOST、PGPORT、PGUSER 和 PGDATABASE。优先使用本机认证或 .pgpass。

首次使用默认库时，先单独执行建库命令。如果该库已经存在，直接执行下一段。

```sh
createdb project_guide_seed
```

在同一终端运行数据库测试，通过后启动工作台。

```sh
(cd seed && SEED_TEST_PG=1 python3 -B -m unittest -v tests.test_seed_pg) && python3 -B seed/seed.py
```

打开 http://127.0.0.1:8765 。服务在专用库内自行创建 seed_events 与阶段表。每次提交独立需求授权一次规划和一次 Worker 调用，回复或退回授权一次新的执行。使用同一目录的本地文件锁限制一个服务进程。请用本机终端运行，仅交给它你愿意让本机用户执行和测试的代码。

网页顶部显示服务启动时加载的完整提交和本地 main 当前完整提交，每次刷新重新读取 main。两者相同时显示“运行版本已同步”；不同时显示“需要重启以加载新版本”。当前服务仍运行启动时加载的代码，现有调度在仓库版本变化后暂停接手 queued（等待执行）和 answered（已回复，等待接手）队列，重启加载新代码后再继续接手。在启动本服务的终端按 Ctrl-C，然后在原项目目录、沿用原数据库环境和原启动参数重新执行 `python3 -B seed/seed.py`；自定义端口须保留 `--port` 参数及原端口值。当前版本会在规划或 Worker 执行完成、HTTP 提交响应完成后自动重启继续派工。旧版本升级至此版本需先手动重启一次，之后保留原参数自动切换。

## iPad 局域网访问

Mac 和 iPad 连接同一可信 Wi-Fi。后台仍在 127.0.0.1:8765 运行，另一个终端在本目录启动带访问码的局域网入口。将下方地址替换为 Mac 当前的局域网 IPv4。

```sh
python3 -B seed/seed_gateway.py --host 192.168.50.217 --port 8766
```

用 iPad Safari 打开终端显示的 iPad URL，输入终端显示的访问码。入口使用 HTTP，适用于上述局域网环境。它代理到原后台，登录后的页面、提交、裁定和验收使用同一套记录；未登录不能读取工作台或提交操作。访问码和会话密钥保存在被 Git 忽略的 .seed/lan-access.json，文件权限为 600，登录有效期一天。后台自动切换版本时登录仍有效。Mac 地址变化后需用新地址重新启动入口。

```sh
cd seed && python3 -B -m unittest -v tests.test_seed_gateway
```

## 阶段目标与任务草稿

网页有两个入口：“阶段目标”先规划，“独立需求”提交后直接进入原有执行流程。本轮仅支持当前本地项目的一个阶段，不提供多阶段管理、重规划、并行 Worker 或全局检索。

1. 填写阶段目标与阶段验收。协调器在对应提交的隔离快照中调用真实只读主 Agent，生成 2～6 张任务草稿。此时没有代码 Worker、任务工作树或可执行任务。页面保留完整来源 SHA、模型运行与日志引用。
2. 用普通表单逐卡编辑标题、需求、验收和依赖；依赖复选框表示“必须先人工启用”。点击“保存草稿”产生新版本。“确认此版本并授权执行”只确认已保存内容；如果同时改了表单，首次点击先保存，请核对新版本后再次明确确认。
3. 空验收、缺失依赖、自依赖和循环依赖会显示错误并保留输入。版本冲突同样保留输入，打开最新页面核对后手动合并。确认在 PostgreSQL 单个事务内整批建立任务；同版本重复或并发确认返回同一批任务，旧版本不能覆盖新版本。授权后草稿冻结。
4. 单 Worker 扫描全部可运行任务。上游处于代码完成、测试通过或等待验收（review）时，下游仍等待；只有人工启用（activated）才放行。相关关系不阻塞，等待上游的任务不挡住独立任务。任务沿用原有裁定、退回、差异、测试和人工启用路径。
5. 启用上游后，后台在当前执行结束时自动加载新版本。下游以重启后的当前提交开工，检查其中已包含上游提交；简报携带阶段目标、阶段验收、自身验收、授权版本和上游提交与交付摘要。
6. 全部子任务人工启用后，仅显示“子任务已启用，待阶段验收”。另行填写阶段验收说明并记录通过，才显示阶段验收已通过。可以记录未通过反馈；关闭子任务仍使阶段未完成，不自动替换或追加任务。

阶段、每版草稿、授权映射与事件保存在现有专用 PostgreSQL 内新增的 `seed_stage*` 表中。重启恢复草稿与授权。规划中服务中断会保留来源和运行引用并显示中断；确认旧主 Agent 已退出后，可点击重试只读规划。未授权规划失败不会建立部分任务。已有独立任务及其历史继续使用 `seed_events`。

验收命令（数据库测试各自创建并清理 `seed_test_<UUID>` schema，不改正式项目数据）：

```sh
cd seed
python3 -B -m unittest discover -v -s tests
SEED_TEST_PG=1 python3 -B -m unittest -v tests.test_seed_pg
SEED_TEST_PG=1 python3 -B -m unittest discover -v -s tests
```

默认模型测试为结构化样例；临时仓库闭环使用模拟模型、真实 Git/worktree 和真实测试执行。真实只读模型验收可显式运行下面命令，会消耗一次规划调用：

```sh
cd seed && SEED_TEST_PG=1 SEED_TEST_LIVE=1 python3 -B -m unittest -v tests.test_seed_live
```

该验收通过本地 HTTP 表单提交临时样例阶段，调用真实只读 Codex，检查来源、草稿恢复、零 Worker 调用，再编辑并授权至临时队列；不会执行或启用候选。运行证据和日志保存在 `.seed/live-stage/<UUID>/`，临时 schema 随后清理。真实代码 Worker 交付与人工启用的端到端路径需另行验收，不能将模拟结果作为真实模型交付证据。

本轮验收记录（2026-11-06）：真实只读模型生成了 3 张草稿，运行 ID 为 `aedcf40248d84e64a409acc54170d625`，样例仓库来源提交为 `dec72eb6799e6dc7fa819d63f1d52c3ba8a3c210`。HTTP 编辑与授权通过，Worker 调用数为 0；临时数据库 schema 已清理。原始日志及 `evidence.json` 保存在 `.seed/live-stage/51b0e45c0fd540d8a0e95b05554a7130/`。这是阶段规划与表单授权的真实模型证据；代码 Worker 的端到端交付仍未做真实模型验收。

阶段验收反馈也检查页面版本并推进阶段版本；重复发送同一份验收请求不会重复记录，不同内容的过期表单会冲突。授权草稿版本单独保留，不随阶段验收反馈改变。

实现（都在 `seed/` 下）涉及 `seed.py`（网页与单次协调）、`seed_engine.py`（只读阶段规划与任务上下文）、`seed_store.py`（版本及事务）、新增 `seed_stage.py` / `seed_stage_web.py`（规则与普通表单）。针对性测试位于 `test_seed_stage.py`、`test_seed_pg.py` 和显式选择运行的 `test_seed_live.py`，原有测试保持原断言。

## 执行进度与中断交接

运行中的任务显示主 Agent / Worker 阶段、开始后的用时、最近可公开活动及运行日志位置。活动摘要只记录命令执行、文件修改等类型和开始 / 结束状态。计时增长仅表示仍在等待活动。日志保存在 .seed/logs/<运行 ID>.jsonl，权限为当前用户读写。数据库记录有界的摘要和日志引用，网页隐藏重复进度事件，历史任务继续可读。

默认每次模型调用最多运行 1200 秒。启动时可设置 SEED_AGENT_TIMEOUT 调整秒数。超时或非零退出会清理进程组，保留工作树、Git 改动摘要、运行 ID、活动与日志位置。网页回复后，新会话会收到中断原因和交接信息。服务本身异常退出仍需要确认旧 Worker 已退出后重试。

在项目根目录执行下面命令，可用真实本地短进程验证进度在执行中出现、公开摘要过滤、超时后的子进程清理、非零退出和新会话的交接。此验收无需模型调用。

```sh
cd seed && python3 -B -m unittest -v tests.test_seed_run tests.test_seed.SeedTests.test_retry_receives_actual_interruption_and_worktree
```

## 第一个真实需求

在网页提交「为 refresh 增加历史快照，保留当前查看方式」。验收栏可填写「同一天连续两次成功刷新，两份历史都能独立读取，current 指向第二份。模拟一次来源失败，current 内容与历史条数都保持上次成功时的值。使用本地测试数据验证，无需访问正式项目。」这是留给种子系统的第一张任务卡。

- 网页按任务显示计划、进度、决策卡、证据和提交差异。需要裁定时 Worker 写入问题、建议与检查点并退出，回复后新进程接着同一工作树开发。单 Worker 可继续执行队列里其他任务。
- 候选提交从干净工作树运行基线版本的顶层 test_*.py 和候选版本的 unittest 套件。人工核对原始验收、测试是否覆盖需求及 diff 后点击启用。测试通过与产品验收分别记录。
- 启用采用 fast-forward，要求 main 干净且基线匹配。调度器在当前规划或 Worker 执行结束、HTTP 提交响应完成后自动重启加载已启用版本，保留端口和数据库环境，继续派工。首次从旧版升级需要手动重启一次。
- main 已变化时旧候选不能直接启用。关闭旧任务，引用旧提交和需保留的工作创建新任务。工作树位于 .seed/trees/<任务 UUID>，保留供审查。
- 服务异常退出时，重启会将执行中的任务标成中断，保留修改。先检查工作树和旧 Worker 进程，再在网页填写重试说明。启动过程若 PostgreSQL 不可用会报告连接错误。
- 需要撤销刚启用的版本时，停止服务，确认 main 干净且 HEAD 是该候选，执行 `git revert --no-commit BASE..CANDIDATE`（替换为线程中的提交），检查后 `git commit -m "Revert seed activation"`，重启。此操作用于代码回滚。涉及数据库破坏性迁移的需求应单独裁定和备份。
