# .relayforge 文件格式

事实层文件都是「YAML 文件头 + 固定二级标题 + 列表项」。程序只解析这三样。

## 数据放在哪
- 项目的记录（需求、设计稿、用例、测试集、问题、会话进展、裁定、功能点、模块、用户旅程、发布记录……）放在本机 ~/.relayforge/projects/<项目 ID>/，不进 Git。整个项目共用一份，切换分支、开工作目录都看到同一份。
- 仓库里只提交 .relayforge.json：{"id": "项目名-随机串"}。项目主目录和每个工作目录里的 .relayforge 是指向外置目录的链接，写进 .gitignore 和 .git/info/exclude，不进 Git。重新克隆或挪了位置，打开时程序按项目 ID 接回本机那份记录；本机没有就是一份空的。
- 三类数据：属于项目的（上面那些对象）整个项目共用、不按分支过滤；要记分支的写在对象的文件头里：需求确认完成时 merged_into（合进哪个分支）和 merge_commit，修复的 into 和 merge_commit，发布记录的 branch、target 和 to；只留本机的（会话的原始聊天、草稿、测试环境的保密值、运行中的临时文件）本来就在 ~/.relayforge 的别处。
- 待发布：确认完成时记下的合并提交还不在远端就算这个分支待发布；只改了记录、没有代码的需求不算。发布记录只存本机，是否已发布看它的 to 提交是否已经在远端分支里。
- 备份和换电脑：rf.py data export 文件（打包成 .tar.gz，不含程序副本、页面、日志和运行中的临时文件）；在另一台电脑上打开同一个仓库后 rf.py data import 文件（只由用户触发；本机已经有记录时要 --replace，原来那份改名留着）。rf.py data where 看记录放在哪。
- 旧项目（记录还是仓库里的 .relayforge/ 目录）迁移：rf.py data migrate（只由用户触发，应用里打开旧项目时点「迁移」）。整个目录原样复制到本机、核对一个不少，然后提交一次：从 Git 里去掉 .relayforge/，加上 .relayforge.json，.gitignore 加 /.relayforge；仓库里原来那个目录挪到 ~/.relayforge/projects/<ID>.repo-copy-时间/ 留着，不删；以前写进仓库给 AI 的约定在同一次提交里拿掉（AGENTS.md 里 RelayForge 标记之间的那一段，没有别的内容就删掉文件；只有 @AGENTS.md 一行的 CLAUDE.md；.claude/skills/ 下的 rf-sync、rf-confirm），用户自己写的内容和项目里别的改动都不动。迁移以后旧版本的应用打不开这个项目。
- 给 AI 的约定：数据外置的项目不往仓库的 AGENTS.md、CLAUDE.md 里写（远程开发、别处的会话看到的仓库里没有 .relayforge，这些规则只会干扰它们）；约定放在本机记录的 .relayforge/CONVENTIONS.md，应用开会话时交给会话。以前的版本写进 AGENTS.md 的那一段（标记之间的），重新初始化时拿掉，别的内容不动。技能也一样：不往仓库的 .claude/skills/ 里写，「同步一下」「确认待确认的」的做法放在 CONVENTIONS.md 的「常用操作」里；以前写进去的 rf-sync、rf-confirm 重新初始化时拿掉。
- 会话写不进外置记录时（Codex 的沙箱只让写工作目录）：会话里的 rf.py 自动把命令交给开这个会话的应用代写，照常运行命令就行，不要想办法自己写进去。只代写记录类的命令（note、req attach/classify/steps/verdict/retest/case-add/case-edit/case-rm、issue new/attach/handback/finding、design save/skip、test new/add/edit/rm/analyze、env propose）；执行出来的身份还是这个会话，「只由用户触发」的命令照样被拒绝。会话关了以后不再代写。
- 旧项目（记录还是仓库里的 .relayforge/ 目录、没有 .relayforge.json）：这个版本不打开，提示需要迁移；下面「事实只在项目主目录里有一份」说的是旧项目的做法。

## 事实只在项目主目录里有一份（旧项目）
- 需求、设计稿、会话进展、裁定、没定的事、问题、功能点、模块、用户旅程、产品介绍，都只在项目主目录（仓库的第一个工作目录）现在签出的分支下的 .relayforge/ 里有一份，读写都以它为准。
- 需求和修复各自的工作目录（.worktrees/ 下）只改代码。那里检出的 .relayforge/ 是开分支那一刻的旧副本，不作数：不要读，也不要改。rf.py 的所有命令不管在哪个目录里运行，都自动读写项目主目录。
- 合并一个需求或修复时只合代码；分支上万一改了 .relayforge/，合并时不让它覆盖主目录的内容，并在完成记录里写明哪些没有合进来。目标分支上新多出来的提交只改了 .relayforge/ 时，不算分支没包含目标分支的最新内容。
- 事实文件的改动由程序在几个时刻攒着提交到项目主目录当前的分支上：确认立项、确认完成、放弃和恢复、手动改需求状态、用户对问题做决定、会话停下来时。只提交 .relayforge/ 下的路径，不碰用户别的改动；用户正在合并或 rebase 时先不提交，留到下一次。项目主目录里还没提交的事实不挡确认完成和确认修好了，程序先提交它们。
- 以前的布局里，进行中需求的事实在它自己的分支上；这些不搬过来，程序不再读它们：只在旧需求分支上的需求不出现在列表和看板上，留下的 .worktrees/R-… 目录和 req/… 分支不动、也不碍事。

## 通用文件头
- id：稳定编号，创建后不变。模块 M-01，功能点 RF-101，用户旅程 J-01，裁定 D-0001，文档登记 DOC-0001，需求 R-20261114-a3f1、设计稿 DS-20261114-b2c4、发布记录 P-20261118-ab12（日期加随机后缀，由程序生成，不同分支上同时新建也不会撞号），问题 I-033（顺序编号，只在项目主目录里生成，界面上写作 #033），测试集 TS-001（顺序编号，只在项目主目录里生成，见「测试集」）。
- type：module、feature、journey、decision、doc、requirement、design、issue、publish 之一。
- title：名称。
- status：current 现行、draft 草稿、superseded 已被替代、reference 参考。
- updated：最近修改日期，YYYY-MM-DD。
- supersedes：它替代了谁，编号列表，如 [D-0001]。
- superseded_by：谁替代了它；非空时文件应在 history/ 下。
- in_progress：这个对象是哪个还没确认完成的需求新加的（需求编号）。有这个字段的模块、功能点、用户旅程、裁定显示为「进行中，尚未完成」，不作为依据（除了那个需求自己的会话），需求确认完成时由程序去掉。
- changing：正在改这个现有对象的、还没确认完成的需求（编号列表），见下面的「进行中的改动」。
- dropped_with：随哪个已取消的需求移到 history/ 的；恢复那个需求时程序把它拿回来。dropped_changes：已取消、等恢复的改动来自哪些需求。

## 各类文件多出的字段
- 模块：order（在结构树里的顺序）、layer（在大图里属于哪一层，写层名；旧项目的 group 也当作层）、paths（对应的代码路径列表，相对仓库根目录）。
- 功能点：module（所属模块编号）、order、depends_on（依赖的功能点编号列表）。
- 用户旅程：module（所属模块编号）、order（在这个模块里的顺序）。
- 裁定：applies_to（适用的对象编号列表）、decided_by、decided_at。
- 文档登记：path（原文件在仓库里的位置）、related（关联对象编号列表）。
- 需求：state（draft 立项中、open 开发中、done 已完成、dropped 已取消）、merge_commit（确认完成时合并提交的编号，由程序记下，发布时靠它认出这个需求带来了哪些提交；没有代码改动的需求没有）、branch（绑定的分支）、sessions（挂在它下面的会话，按先后）、intake（立项时挂着的会话，也就是立项会话）、created（创建时间）、manual_stage（用户手动放到的栏：build 进行中或 check 待验收；没放过时不写，按计划是否做完来算）、design_skipped（跳过方案的理由，没跳过时为 null）、previous_state 和 previous_stage（取消前的 state 和 manual_stage，供恢复使用）、source_issue（由哪条问题转来）、converted_issue（转成了哪条问题）、depends_on（前置需求的编号列表，见「前置需求」）、start_sync（确认立项时把主线同步进分支的结果：ok 或 conflict，另有 start_sync_base、start_sync_commits、start_sync_files，由程序写）；确认完成以后由程序写的 tags（客观标签：涉及的功能点、模块、裁定、问题的编号；改过的文件和完成记录一样不写列表，查的时候由 git 现算）、topics（概括标签）、summarized（最近一次总结的时间，没总结过时不写）、summary_decisions（总结时提出、交给用户确认的裁定编号），完成或放弃时写的 archived 和 archive_missing（会话记录已存到本机的、存的时候原始记录已不在的会话编号），见「历史、总结和会话存档」。
- 问题：state（todo 待处理、fixing 处理中、review 待你确认、resolved 已解决、closed 不处理）、source（你、Agent、测试页）、kind（AI 初判或用户改过的类别：bug 是问题、request 可转需求、usage 已有用法、ask 待补充；还没判时为 null）、kind_by（ai 初判、user 用户纠正、probe 排查会话的结论）、feature（用户关联的功能点编号，可以为空）、deferred（以后再说时为 yes）、fix（所属的修复编号，如 F-005）、requirement（转成的需求编号）、duplicate_of（和哪条重复）、closed_as（drop 不处理、duplicate 重复、requirement 已转需求、not_issue AI 复查认为不是问题并经用户确认、manual 手动结束处理）、source_requirement（由哪个立项中的需求转来）、created；解决时由程序写的 tags（客观标签：功能点、模块、裁定、相关的需求和同批的问题）。
- 发布记录：remote（推送到的远端）、branch（本地分支）、target（远端分支）、created（第一次准备的时间）、prepared（最近一次准备的时间）、from（推送前远端分支的提交，新建远端分支时为空）、to（这次发布到哪个提交为止，不含发布记录自己的提交）、commits、facts（提交数和其中程序自己的事实提交数）、attempts（准备了几次）。
- 设计稿：requirement（画它的需求）、features（画的现有功能点编号列表）、html（同目录下的页面文件名，就是「编号.html」，改名也不变）、adopted（成为现行的时间，需求完成时由程序填写）。status：draft 是需求里还在聊的稿子，current 是功能点现在的样子，superseded 是已被替代、移到 history/ 的。

## 固定的二级标题
- 模块：负责什么、和其他模块的关系、变更记录。
- 功能点：一句话定位、在模块中的角色、在产品中的位置、用户旅程、规则与边界、还没定的事、调整时要注意、变更记录。
- 用户旅程：一句话说明、步骤、变更记录。
- 大图的层（product/layers.md）：层、变更记录。
- 裁定：决定、理由、没有选的方案、变更记录。
- 文档登记：这份文档是什么、哪些内容仍然有效、变更记录。
- 需求：需求说明、要改的功能点、验收条件、总结、变更记录。「总结」只在确认完成以后由程序写（rf.py summarize），之前没有这一节。
- 问题：现象、修复报告、变更记录。
- 发布记录：包含的需求、包含的问题、其他提交、变更记录。
- 设计稿：画的是什么、新增的功能点（画了还没有编号的新功能点，一行一个名称）、变更记录。「画的是什么」描述的是这张图，不是对产品的陈述，不加〔待确认〕；整份设计稿要等用户确认完成需求后才成为现行。
- 没有内容的标题下写一行「- 尚未讨论。」。

## 一条陈述的写法
- 一行一条，以「- 」开头，行尾标出处，如〔S-20261112-a3f1#18〕：会话编号加消息序号。
- 不是用户明确说过的，在「- 」之后加〔待确认〕。
- 用户确认后由 rf.py confirm 去掉标记、把草稿改为现行，并在变更记录里追加一行；用户否决的由 rf.py reject 把标记改成〔已否决〕，草稿对象移到 history/（superseded_by 留空）。
- 用户用一条新的陈述换掉旧的时，旧行不删，在「- 」之后加〔已替代〕；它和〔已否决〕一样不再算数。

## 进行中的改动
- 还没确认完成的需求改一个现有的功能点、模块或用户旅程：新的陈述行首加〔进行中 R-…〕，它要换掉的旧陈述行首加〔R-… 完成后替代〕（旧行照旧算数），文件头 changing 写上需求编号。用 rf.py note fact 写，不要手工改。
- 〔进行中 R-…〕的行在需求确认完成前不算数；确认完成时程序去掉这个标记，旧行改成〔已替代〕。
- 需求放弃时，〔进行中 R-…〕改成〔已放弃 R-…〕（不再算数），旧行上的〔R-… 完成后替代〕改成〔R-… 放弃前要替代〕（照旧算数）；恢复时改回来。
- 需求新加的整个对象（新的功能点、模块、裁定）不用标行，文件头写 in_progress；放弃时整个文件移到 history/，写上 dropped_with。设计稿本来就是这样：status 为 draft 时是进行中，确认完成时成为现行，放弃时移到 history/。
- 「变更记录」里每行以日期开头，只追加。

## 大图（层、模块、功能点、用户旅程、模块关系）
- 大图把产品的功能模块梳理清楚：它代表产品定位和设计目标，可以脱离代码本身，代码只是它的一种实现。
- 页面上按层分成几个标签页，每页是一棵「模块 → 功能点」的树；点一个模块，看它的用户旅程。
- 模块图只在两个地方产生和修改：初始化（bootstrap 读代码生成第一版，全部待确认）和大图编辑会话（大图页面上点「编辑」打开的那个固定会话）。
  日常的开发会话和聊天不改层、模块、功能点归属、用户旅程和模块关系；自动抽取也不抽这些。需求新增的功能点照常在需求里建。
- 分几层、每层叫什么按项目来定，写在 product/layers.md 的「层」下，从上到下一行一层：
  - 〔待确认〕用户界面：用户直接看到、直接操作的地方〔出处〕
  - 模块文件头的 layer 写层名。没写 layer 的模块归到「未分层」。
- 用户旅程在 journeys/ 下，一条旅程一个文件（J-01-名称.md），文件头的 module 是它所属的模块；按用户使用的顺序把功能点串成一条操作路径。「步骤」下一行一步：
  - 〔待确认〕点「新建需求」写一两句话｜左边多出一个需求｜用户｜RF-140〔出处〕
  - 做什么｜做完看到什么｜谁来做（「用户」或模块编号，几个用顿号隔开）｜用到的功能点编号（可以是别的模块的，可省略）。
  - 文件头 trunk: true 表示这是主干旅程：每次合并前都在合并后的代码上跑它各步骤用到的功能点下的测试集（见「测试集」的「合并前的检查」）。哪条是主干是产品判断，只由用户在应用的大图里设（rf.py map trunk J-01 [--off]，只由用户触发），AI 不得自己写这个字段。
- 模块之间的关系写在发起的那个模块文件的「和其他模块的关系」下，一行一条，在模块详情里以文字列出：
  - 〔待确认〕调用 M-10：提交后启动规划和执行｜RF-108、RF-114〔出处〕
  - 开头是关系的类型：调用、读写数据、套用规则；接着是对方的模块编号、冒号和一句说明；「｜」后面是经过的功能点编号，可省略。
- 初始化时写的出处是〔代码导入#0〕。大图编辑会话里，用户明确说的改动直接写、不加〔待确认〕；自己推断的加〔待确认〕。

## 需求（requirements/）
- 一个需求一个文件，由 rf.py req new 创建在项目主目录的 requirements/ 下；同时开出分支 req/…，并在仓库根目录的 .worktrees/ 下开出它自己的工作目录（一份完整的仓库，这个需求的代码在里面改；事实仍然只写项目主目录）。
- 需求文件的头部由程序维护；三个正文小节由会话里的 AI 按上面的写法填写：聊定的写进去，推断的加〔待确认〕。
- 「要改的功能点」一行一个，以功能点编号开头；还没有编号的新功能点写「新增：名称（属于 M-xx）」。
- 一个需求分两段：先立项（state: draft），再开发（state: open），两段各用各的会话。新建的需求都从立项开始。
- 需求文件头用 intake_cli 和 intake_model 保存立项会话配置，用 development_cli 和 development_model 保存开发会话配置，用 testing_cli 和 testing_model 保存测试会话配置。CLI 为 claude 或 codex。省略模型时由 CLI 决定。旧需求未存 CLI 时沿用应用设置。
  - 测试会话的配置是可选的，默认「跟开发一样」：文件头里没有 testing_cli 就是跟着开发会话，用开发会话的 CLI 和模型（不复制一份，开发会话的配置以后改了，测试会话跟着变；开发会话也没存就沿用应用设置）。老需求没有这个字段，同样跟着开发。需求列表里的 session_choices 只列单独设置过的，testing_follows_development 说明测试是不是跟着开发。
  - 想用和开发不同的模型来测（测试的价值在于独立），新建需求时单独选测试会话的 CLI 和模型：rf.py req new 的 --testing-cli、--testing-model；建好以后改用 rf.py req choose 需求编号 --testing-cli claude|codex [--testing-model 模型]，或者 --testing-follow（改回跟开发一样），在变更记录里追加一行。这条命令只由用户在应用里触发，AI 不得自己执行。
  - 开发会话的配置建好以后也能改：rf.py req choose 需求编号 --development-cli claude|codex [--development-model 模型]（只由用户在应用里触发），对下一次新开的开发会话生效，已经开着的、接着聊的开发会话不受影响；测试会话跟着开发的，也跟着变。立项会话的配置建好以后不能改。
  - 改了只对下一次新开的测试会话生效：已经开着的测试会话、接着聊的测试会话不受影响。测试会话启动时仍然带自己的会话令牌、测试会话的权限规则和开场白，和选哪个 CLI 无关。用 Codex 测试时，程序对它的限制比 Claude Code 少（没有 Claude Code 的权限规则，也可能连不上本机通道），界面在选项旁提示这一点。
- 立项会话只把需求聊清楚、写进需求文件（包括测试用例和验收条件的归类，见下面的「测试用例」），不改代码、不读代码细节。清晰度由程序从需求文件算出，分五级，从上往下走：
  - 想法：只有标题。
  - 方向：需求说明至少一条，要改的功能点至少一个。
  - 方案：至少一份设计稿；或者这个需求没有看得见的界面，用 rf.py design skip 写明理由跳过（显示为「跳过」，不算画了）。
  - 可验收：至少一条验收条件（标了〔已否决〕的不算）。
  - 用例：每条验收条件要么至少有一条测试用例，要么归为「只能人工看」（看界面）。
- 清晰度是从上往下没有断档的最高一级：方案既没有设计稿也没有跳过时，停在方向；但这不挡立项。
- 上一级没聊定之前不问下一级的细节；发现上一级不对可以回头改。
- rf.py req brief 需求编号（在需求的工作目录里可以省略编号；--json 输出 JSON）：程序按「要改的功能点」算出影响：引用的编号是否存在、各自的名称，不存在的编号，没写编号的行（当作新增功能点），依赖它们的功能点（看功能点文件头的 depends_on），管着它们或它们所在模块的现行裁定（看裁定的 applies_to），这些功能点现在的设计稿（文件路径），以及这个需求自己已经画的设计稿。
- 用户确认立项后执行 rf.py req start：至少要有一条验收条件，其他都可以跳过；还有验收条件既没有用例、也没标「只能人工看」时只提示（req brief --json 和 req list 的 gate.uncovered、gate.hint），不拦，变更记录里写明哪几条；文件头写 case_flow: 1；state 改为 open，在变更记录里追加一行，并把项目主目录里攒着的事实一起提交。之后开一个新的会话开发。
- 一个需求可以先后挂多个会话；state 只有用户确认完成后才改为 done。
- 用户实际操作、确认完成后执行 rf.py req done：先把分支上的代码合并进项目目录当前签出的分支（不一定是 main），只合代码；再把这个需求带来的事实转成现行（去掉 in_progress 和〔进行中〕标记、旧行改成〔已替代〕），它的设计稿成为功能点现在的样子，在需求的变更记录里写下新增和修改了哪些模块、功能点、裁定、设计稿，最后收掉工作目录和分支、提交事实。只带来了事实和设计稿、没有代码改动的需求，不用合并，直接完成。同一时间只有一个需求在合并：rf.py req done 在仓库的 .git 里加锁，应用里点了确认完成的需求按先后排队。需求的分支还没包含目标分支的最新提交（只改了 .relayforge/ 的提交不算）时，git 合得上、没有代码冲突的，rf.py req done 自己在需求的工作目录里把目标分支合进来（分支上 .relayforge/ 旧副本的冲突取目标分支的），接着合并回去；有代码冲突、或者工作目录里还有没提交的代码改动时，rf.py req done 什么都不写、什么都不合并，--json 返回要做的事；应用回到这个需求的开发会话，让 AI 提交改动、把目标分支合并进来、解决冲突并提交，有冲突时只跑这个需求的测试集（rf.py test run --req）和直接测冲突文件的项目测试，不跑整个项目的测试；AI 这一轮说完，应用再试。新需求的分支也从项目目录当前签出的分支开出。
- 用户不想做了，执行 rf.py req drop 取消立项中或开发中的需求：工作目录里没提交的代码改动提交到它的分支上（不拦着取消，也不丢），分支保留以便恢复（记下 dropped_at）。分支上没有自己的提交时一起删掉；保留的分支超过应用设置里的天数和个数（默认 30 天、20 个）时由较早的开始，在确认完成或取消需求时顺手清理；用户点了「保留」（rf.py req keep，文件头 keep_branch: yes）的不清理。删掉时文件头记 branch_removed（分支最后的提交），变更记录写一行；恢复这样的需求会从项目当前的分支重新开一个同名分支；项目主目录里的需求文件留着，state 改为 dropped，记下取消前的 previous_state / previous_stage 和一行变更记录；它带来的事实和设计稿移到 history/（dropped_with 写需求编号），它对现有对象的改动不再算数（见「进行中的改动」）；然后收掉工作目录、提交事实。已完成的需求不能取消。左侧需求列表默认隐藏已完成和已取消，可用阶段筛选重新显示；看板始终保留五列。
- 用户点击恢复时执行 rf.py req restore 需求编号：重建原分支工作目录、恢复 previous_state 和手动放过的栏，把放弃时移到 history/ 的事实和设计稿拿回来、改动重新算进行中，保留代码与原会话。旧版没有记录取消前状态的需求恢复为 draft。已有目录不会被覆盖。
- 用户在需求列表或看板上手动改状态，执行 rf.py req set 需求编号 状态（talk 立项中、build 进行中、test 测试中、check 待验收、done 已完成、dropped 已取消）。规则是严格的：已完成和已取消之后不能再改（已取消的用恢复）；已立项的不能退回立项中；从立项中改到进行中、测试中、待验收或已完成，至少要有一条验收条件（等于先立项）。改到已完成就是 req done，改到已取消就是 req drop；改到测试中就是 req to-test（交给测试）；从进行中或测试中改到待验收就是 req skip-test（跳过测试，测试中改过去记为「手动放行」）；其余（比如测试中退回进行中、待验收退回进行中）只改 manual_stage，在变更记录里追加一行并提交需求文件。改到测试中、待验收要应用的标记（见「测试环境」里的应用的标记），会话里做不了。
- 前置需求：需求文件头的 depends_on 列出要先完成的需求。它们都确认完成之前，这个需求不能立项开始开发（req start、拖到进行中都会被拦，并说明在等谁）；已经在开发的需求加了前置需求，要等它们完成后才能确认完成。只由用户设置：rf.py req depend 需求编号 前置需求编号 [--remove]（应用里的「前置需求」），或者同意一条写了先后的拆分建议（建议里一起提出的几条之间也可以有先后，用「#序号」指同一条建议里的另一条；用 takes 把来源需求的某条前置需求交给拆出去的那条来等，来源需求就不再等它）。一个需求只有一部分要等别的需求，或者想设的前置需求会互相等待时，把要等的那部分拆出去，而不是让整个需求等着。每条依赖写一句要用到对方的什么（具体到接口、数据、页面或规则），记在需求文件的「前置需求」一节，一行一条：「- 前置需求编号：要用到什么」，放在变更记录前面；设依赖时由 req depend 的 --need 或拆分建议的 needs 写入，去掉依赖时一起去掉，不要手改。被等的需求要拆分时，按这些说明讲清每样被等的东西留在哪一项。不能依赖自己、已完成或已取消的需求，不能形成环；前置需求被取消时不自动处理，由用户决定去掉这条依赖还是取消这个需求。设置、去掉都在变更记录里记一行。确认立项时，程序先把项目目录所在的分支同步进这个需求的分支（分支上还没有自己的提交时直接快进；有前置需求、又有自己的提交时合并，冲突就撤回，留给开发会话处理），结果记在 start_sync 和变更记录里。AI 觉得需求之间有先后，只能在回复里建议，不要自己执行 req depend。
- 阶段：立项中（talk）→ 进行中（build）→ 测试中（test）→ 待验收（check）→ 已完成（done），另有已取消（dropped）。进行中、测试中、待验收的 state 都是 open，由文件头 manual_stage 区分；
  manual_stage 没写时看开发会话的计划：没做完是进行中；做完了，文件头有 test_flow（立项时写 1）的进测试中，没有的（这个阶段出现以前的老需求）照原来的规则进待验收。
  - 进行中 → 测试中：开发会话把计划做完时自动进入（第一次算出来的那一刻，程序把它落成记录：文件头 manual_stage 写 test，变更记录追加一行「时间 开发会话做完了计划（N 步），进入测试中。」并提交；只写一次，之后的阶段以记录为准）；开发会话修完测试交回的问题时用 rf.py req retest "修了什么"；用户在面板上点「交给测试」（rf.py req to-test）。
  - 测试中 → 待验收：测试会话交回「可以验收了」（rf.py req verdict ok）；用户点「跳过测试，直接验收」或手动改过去（记成跳过）。
  - 测试中 → 进行中：测试会话交回「有问题」（rf.py req verdict problems），问题清单交给开发会话；用户也可以手动退回。
  - 跳过测试：进行中或测试中都能点（rf.py req skip-test），测试结论里如实记一轮「跳过测试」，变更记录里写「用户跳过了测试」。
- 三个会话的分工（立项、开发、测试）：
  - 立项会话出测试用例：用业务的话写（前提、操作、预期，不提函数名、文件、接口字段），挂在验收条件下面，想到正常、边界、异常几种情况，不凑数；
    并给每条验收条件归类：能用数据验证（data），还是只能人工看（ui，写明「应该看到什么」，具体点哪里留给测试会话）。
  - 开发会话写代码，目标是让这些用例通过；它看得到用例和归类，不能改（改要提给用户，见下面的「用例改动」）。
  - 测试会话负责对接和执行：把每条能用数据验证的用例对接成测试集里的一条或几条数据（rf.py test，每条数据挂上它对应的用例编号），
    读代码只是为了接上，不能改变用例的意思（前提、操作、预期对应到输入、调用、期望输出）；运行，逐条用例报告结果；只能人工看的验收条件，
    在界面做出来以后补成具体的检查步骤（req steps）。它可以补充用例（标成「测试补充的」，用户能看到、能删），不能减少或改动立项写的。
  - 用例没通过 → 交回开发会话修代码。任何一方认为用例本身写错了 → 不能自己改，提给用户；立项之后改用例一律要用户同意。
- 测试会话：一个需求下的第三种会话（立项、开发之外），在这个需求的工作目录里，进入测试中时由应用开出（应用没开着时，下次打开这个需求再开），之后每一轮接着用它。
  它没参与开发；有测试用例的需求，按上面的分工对接和执行；动到的功能点的旧测试集一起跑，失败的逐条判断是需求有意改了行为（test edit --why 提出改动）还是改坏了（交回）；
  环境没准备好时负责打通（项目目录内的安装和编译可以直接做，系统级的要用户同意，试出来的做法用 rf.py env propose 交回）。它不改产品代码：只写测试数据（通过 rf.py test）、接入代码和桥接文件，发现产品的问题就交回。
  没有测试用例的需求（立项时还没有这一步的老需求，或者立项一条用例都没写的）照原来的做法：测试会话自己把每条验收条件归类；能用数据验证的按验收条件写测试集、运行、写分析，
  不为了覆盖验收条件去凑（只有一条数据、或者只断言「返回了东西 / 函数存在」的不建），一个需求可以一个测试集都没有；要看界面或要人操作的写成检查步骤。
  全部验收条件都要看界面时，它只写检查步骤，然后交回「可以验收了」。
- 测试用例写在需求文件的「测试用例」一节（排在「验收归类」之后、「检查步骤」之前），由命令写，不要手工编辑；一条用例一行：
  「- 用例 编号｜验收条件原文｜名称｜类别｜前提｜操作｜预期｜来源｜状态〔出处〕」。编号在需求内按顺序分配、不复用；名称写它覆盖哪种情况；类别是 正常、边界、异常；
  来源是 立项（立项会话写的，或用户同意了的改动加的）、测试补充（测试会话补充的）、用户（用户在应用里加的）；状态是 在用、已删除（删了的行留着）。
  - 例：- 用例 1｜账单列表能按月份筛选｜月底最后一刻记的账｜边界｜10 月 31 日 23:59 记了一笔账｜在账单列表里选 2026 年 10 月｜这笔账出现在列表里〔S-20261119-ab12#4〕
- 用例改动：立项以后（需求在进行中、测试中、待验收），任何会话（立项会话接着聊、开发、测试）要改或删立项写的用例、加用例（测试补充的除外）、改已经归好的类，
  都不直接生效，记成「用例改动」一节里的一行，--why 理由必填，等用户在应用里同意或不同意：
  「- 改动 编号｜对象｜动作｜谁提的｜理由｜状态｜时间｜{"case", "check", "old", "new"}〔出处〕」。对象是「用例 3」「第 2 条验收条件」「第 1 条验收条件 新用例」；动作是 修改、删除、新增、归类；
  谁提的是会话种类加会话编号；状态是 待确认、已同意、不同意；最后一段 JSON 是程序读的旧值和新值。同一种会话对同一处还有一条待确认的，再提就换掉它。编号不复用。
  同意：马上生效（改了用例、删了用例、加了用例、换了归类），这一行改成已同意，变更记录里写一行；不同意：这一行改成不同意，应用把这句交回提出它的会话。
  测试会话新增的「测试补充」用例和改它自己补充的不用同意；没有用例的老需求，测试会话归类照旧不用同意。用户自己在应用里改用例（req case-save）不受限。
  开发会话在测试交回问题后认为是用例错了、不是代码错了，也用这条提，再 req retest：程序在「修好了」那一行里带上它提的用例改动。
  需求确认完成前，应用的确认对话框里要把待确认的用例改动处理完（和测试数据的改动一样）。
- 谁是测试会话：应用开测试会话时用 rf.py req attach 需求编号 会话编号 --test 登记（只由应用做，要应用的标记），写在文件头 test_sessions，同时也在 sessions 里；
  并且发给它一个签名的会话令牌（见「会话的身份」），种类是测试会话、属于这个需求。程序按验过签名的令牌认会话的种类，不靠会话自己说，也不信环境变量里裸的会话编号。
  需求的进展和计划只看开发（立项）会话；测试会话的进展单独显示。
- 测试的三样记录写在需求文件里，由命令写，不要手工编辑；每行字段用「｜」隔开，排在「验收条件」和「变更记录」之间：
  - 「验收归类」：每条验收条件一行，「- 数据可验｜验收条件原文｜理由〔出处〕」或「- 看界面｜验收条件原文｜理由〔出处〕」；重新归类换掉同一条的旧行。立项会话写（rf.py req classify）；立项以后改归类走用例改动。
    - 例：- 看界面｜账单列表能按月份筛选｜要在列表页上点月份下拉框看结果〔S-20261119-ab12#3〕
  - 「检查步骤」：人工验收的检查，一步一行，「- 验收条件原文｜打开哪里｜做什么｜应该看到什么〔出处〕」，同一条验收条件按先后排。
    - 例：- 账单列表能按月份筛选｜账单列表页｜在月份下拉框里选 2026-10｜只列出 10 月的账单，标题显示「2026 年 10 月」〔S-20261119-ab12#5〕
  - 「测试结论」：每一轮一行「- 第 N 轮｜时间｜结论｜会话｜总结〔出处〕」，结论是 可以验收、有问题、跳过测试（用户点的）、手动放行（测试中由用户直接改到待验收），跳过的会话写「用户」；
    有问题时下面每条问题一行「- 第 N 轮 问题 k｜哪条验收条件或哪个测试集的哪条数据｜现象｜判断」；问题按用例列时「哪条」写「用例 3「名称」」（程序据此认出是哪条用例）；开发会话修好了再测时记「- 第 N 轮 修好了｜时间｜会话｜修了什么〔出处〕」；
    交回「可以验收了」时说明了原因的没对接的用例，每条一行「- 第 N 轮 没对接 用例 k｜原因」。
    - 例：- 第 1 轮｜2026-11-19 10:20｜有问题｜S-20261119-cd34｜2 条问题〔S-20261119-cd34#9〕
    - 例：- 第 1 轮 问题 1｜测试集 TS-003 #2「月底 23:59 记的账」｜期望 ["b1"]，实际 []｜改坏了：按月筛选用了 < 月底 00:00
    - 例：- 第 2 轮｜2026-11-19 11:30｜可以验收｜S-20261119-cd34｜TS-003 共 6 条全部通过；第 2 条验收条件的检查步骤写好了〔S-20261119-cd34#15〕
  - 文件头另有 test_kicked（应用已经让测试会话开始第几轮）、test_told（第几轮的结论已经交给开发会话或提醒过用户），由应用用 rf.py req test-kicked / test-told 写（要应用的标记）。
  - 「人工验收」：待验收时用户在应用里逐条点的结果，一次点击一行，只追加：「- 通过｜验收条件原文｜时间｜谁」或「- 这里不对｜验收条件原文｜时间｜谁｜用户写的那句话」；谁是「用户」加上 git 认的名字。同一条验收条件以最后一行为准。排在「测试结论」和「变更记录」之间。
    - 例：- 通过｜账单列表能按月份筛选｜2026-11-19 10:20｜用户 张三
    - 例：- 这里不对｜导出的 CSV 最后一行是合计｜2026-11-19 10:24｜用户 张三｜合计行在 Excel 里显示成了科学计数法
- 人工验收（见「测试环境」里的「人工验收」）：待验收时，用户在需求的「人工验收」标签里由程序从这个需求的工作目录把服务跑起来，自己试，在右边逐条点「通过」或「这里不对」（rf.py req accept 需求编号 序号 ok|bad --say "那句话" --ran "当时运行的提交和代码有没有改过" --file -（当时的日志尾部），只由应用触发，要应用的标记）。
  「这里不对」：记一行，需求退回进行中（manual_stage 改为 build），变更记录追加一行，程序把那句话、这条验收条件和它的检查步骤、当时服务日志的最后几十行（所有环境的保密值打码）作为一段话交给开发会话（其中一行写当时运行的是哪个提交、启动后代码有没有改过，方便判断是不是测到了旧代码）；修好以后照现有流程 req retest 再进测试中、回到待验收。
  运行的是不是最新代码：应用在服务启动（含重启）成功时记下代码的状态（工作目录的 HEAD 提交，加上未提交改动的指纹；被 gitignore 的、.relayforge/、.worktrees/ 不算），之后代码一变就标出「启动后代码改过，运行的不是最新的」。
  每个服务有「代码变了自动重启」开关（默认开）；只在两个时机重启，不在 AI 改代码的中途：这个需求的开发会话一轮停下时、用户打开这个需求的「人工验收」标签（或测试页的人工测试）时。服务没在运行不会被启动；启动命令或准备步骤需要重新同意时不自动重启，只提示。
  启动记录：每个服务一份，存本机（$RELAYFORGE_HOME/accept/<项目标识>/<需求编号或 main>/services-history/<服务名>.jsonl，不进仓库），一行一条 JSON {t, action, reason, head, dirty, code, signal, ms}，保留最近 200 条，不含保密值。
  不强制逐条点完：用户点「我试过了，确认完成」时，完成记录里写一行「人工验收：第 1、2 条你点了通过；第 3 条最后点的是「这里不对」；第 4 条没有点。」
- 测试用例的命令（rf.py req …，在需求的工作目录里运行；谁能直接改、谁只能提给用户，程序按会话令牌认，见上面的「用例改动」）：
  - req case-add 验收条件序号 --name "覆盖哪种情况" --cat 正常|边界|异常 --given "前提" --when "操作" --then "预期" [--why "理由"]：加一条（立项会话；测试会话加的是测试补充的）。
  - req case-edit 用例编号 [--name] [--cat] [--given] [--when] [--then] [--check 验收条件序号] [--why "理由"]、req case-rm 用例编号 [--why "理由"]：改、删（立项以后要 --why，等用户同意）。
  - req classify 序号[,序号…] 数据|界面 --why "理由"：给第几条验收条件归类（立项会话；立项以后改已经归好的类要用户同意）。
  - req cases [需求编号] [--json]：只读，每条验收条件 → 用例 → 对接了哪些测试数据 → 最近结果（都通过 pass、有失败 fail、跑不起来 broken、对接了还没跑 unrun、还没对接 unlinked）。
    一条用例的结果由它名下的数据算出：有一条失败就是有失败，否则有跑不起来的就是跑不起来，否则有没跑的就是还没跑，都通过才是都通过。test list --req 的结果里也带这一份（usecases）。
  - 只由用户（应用）触发：req case-ok 需求编号 改动编号（同意）、req case-no 需求编号 改动编号（不同意）、req case-save 需求编号 --file -（以用户身份改用例：
    JSON {"op": "add"|"edit"|"delete"|"classify", "case", "check", "name", "cat", "given", "when", "then", "kind", "why"}）。
- 测试阶段的命令（rf.py req …，在需求的工作目录里运行）：
  - 测试会话用：req steps 序号 "打开哪里" "做什么" "应该看到什么"（加一步检查，--clear 清掉这一条的重写）；
    req verdict ok --summary "测了什么、结果怎样" [--unlinked "用例编号｜为什么对接不了"]，或 req verdict problems --problem "哪条｜现象｜判断"（可以写几次，或 --file 问题.json，JSON 数组 [{"where", "what", "judge"}]；按用例列时「哪条」写「用例 3「名称」」）。
    交回前每条验收条件都要归了类，归为看界面的都要有检查步骤；需求要在测试中。只有这个需求的测试会话能用。
    交回「可以验收了」还要：立项写的、归为能用数据验证的每条用例，都至少对接了一条测试数据并且在这个需求里运行过（程序按 req cases 的结果核对）；没对接或没跑的，逐条用 --unlinked 说明原因，否则交不回。测试补充的用例不在这条规矩里。没有用例的需求没有这一条。
  - 开发会话用：req retest "修了什么"（需求在进行中时，交给测试会话再测一轮；只有这个需求的开发会话能用，测试会话和没有会话令牌的会话不能用）。
  - 用户用（只由应用触发：会话里禁止，程序还校验应用的标记）：req to-test 需求编号（交给测试）、req skip-test 需求编号（跳过测试，直接验收）。
- 交回「有问题」时，应用把这一轮的问题清单作为一段话发进开发会话；交回「可以验收了」时提醒用户。确认完成时，完成记录里写一行测试结论（几轮、每轮的结论、有没有跳过）；rf.py history show 和 rf.py trace 也带上这一行。
- rf.py req start、rf.py req done、rf.py req drop、rf.py req restore、rf.py req set、rf.py req depend、rf.py req keep、rf.py req choose、rf.py req to-test、rf.py req skip-test、rf.py req accept、rf.py req case-ok、rf.py req case-no 和 rf.py req case-save 只由用户在应用里点按钮、右击菜单或拖动看板卡片触发，AI 不得自己执行；程序自己校验（见「只由用户触发的命令」）。

## 设计稿（designs/）
- 立项时把界面和交互画出来给用户看：比文字具体，用户看着提意见。设计稿是基础数据，和别的事实一样只在项目主目录里有一份；需求完成前是草稿（进行中），完成后成为现行。
- 一份设计稿两个文件：DS-20261114-b2c4-名称.md（文件头和三个小节）和 DS-20261114-b2c4.html（页面本身）。
- 页面是一个完整的单独 HTML 文件：CSS 和 JS 都写在文件里；不引用任何外部网址（脚本、样式、字体、图片、请求都不行），也不引用别的文件；图标和图片用内联 SVG 或 data:；断网也能打开。要像真的界面：有像样的示例数据，主要的按钮和切换能点。功能点已经有现在的设计稿时，在它的基础上改，保持现有界面的样子。
- 保存和修改只用 rf.py design save（在需求的工作目录里运行，存进项目主目录）：
  - design save --title "标题" --feature RF-101 --feature "新增：名称" --note "一句话说明画的是什么" --file 草稿.html（也可以从标准输入给 HTML）。
  - 程序检查页面不是空的、没有外部引用，--feature 里的编号都存在（新功能点写「新增：名称」），然后在项目主目录的 designs/ 下写好两个文件，和别的事实一起在下一个提交时刻提交；命令会打印页面文件的完整路径。
  - 按意见修改时加 --id 编号（或者用同一个标题），覆盖同一份；改名只改 .md 的名称部分。别的需求画的设计稿不能直接改：读它的 HTML，改好后另存成这个需求自己的一份。
- 立项会话不能改项目里的文件，只能写项目外面的草稿目录（~/.relayforge/drafts/需求编号/）：先用 Write 把页面写在那里，再用 design save --file 收进需求里；修改时用 Edit 改草稿，再保存一次。
- rf.py design skip "理由"：这个需求没有看得见的界面，跳过方案。画了设计稿就不再算跳过。
- rf.py design list [--json]：列出这个需求的设计稿和各功能点现在的设计稿。
- 需求完成（rf.py req done）时，程序把它的设计稿改为 current、填上 adopted，「新增的功能点」按名称对上这个需求新建的功能点后补进 features。某个功能点现在的设计稿，是覆盖它的 current 设计稿里 adopted 最晚的那份；一份旧的 current 设计稿如果它画的功能点都有了更新的设计稿，就整份移到 history/（.md 和 .html 一起），status 改为 superseded，superseded_by 写替代它的设计稿。只替代了一部分功能点的旧稿还是 current，仍然是其余功能点现在的样子。
- 大图里功能点的详情显示它现在的设计稿：缩小的预览、放大看和单独打开；页面在沙箱里运行，碰不到外面。

## 问题（issues/）
- 问题是使用中发现的毛病：产品该是什么样没变、只是现在不是那样。产品该是什么样要变的，是需求。记的人不用自己分，AI 先初判，判错了用户可以纠正，两边可以互相转。还没合并的需求里发现的毛病不算问题，在那个需求的会话里说。
- 问题只存在项目主目录的 .relayforge/issues/ 下，跟着主目录现在签出的分支走，不跟着需求和修复的分支走：从哪个工作目录运行 rf.py issue（包括会话里记问题、交回修复报告、需求转问题），读写的都是主目录，需求和修复的分支上不存任何问题数据。改动和别的事实一样，由程序在几个时刻（用户对问题做的决定、会话停下来时）攒着提交到主目录当前的分支上，只提交 .relayforge/ 下的文件。
- 一条问题三样东西：说明文件 I-033-名称.md（文件头和三个小节）；对话记录 I-033.jsonl（一行一条：谁说的、说了什么、当时的判断，只由程序读写）；截图在 issues/shots/I-033/ 下，不进 Git。一次修复是 issues/fixes/F-005.json：带哪几条问题、分支、工作目录、会话、谁已经确认了。交给 AI 排查的问题还有 issues/probes/I-033.json：排查会话的编号。
- 「现象」一行一条，写记的人看到的现象；「修复报告」是修复会话交回的两项，「- 改了什么：…」和「- 怎样验证：…」，再交回时旧的两行加〔已替代〕。出处写会话编号加消息序号，不在会话里时写问题编号加对话序号，如〔I-033#1〕。问题文件记的是现象和对话，不是对产品的陈述，不加〔待确认〕。
- 问题文件只用 rf.py issue 读写，不要手工编辑：
  - issue new "一句话现象" --desc "怎么操作、看到了什么" --source Agent [--feature RF-101] [--image 截图]：任何会话发现了和眼下的事无关的毛病，都可以记一条，记完接着做自己的事，不用顺手去修。
    - Agent 提报前用 issue list --json 查所有来源的已有问题，再用 issue show 编号 核对候选的现象和复现证据。
    - 确认同一故障时，issue new 加 --duplicate-of 原单编号 --steps "复现步骤" --observed "实际结果"，把证据、截图和会话出处追加到原单的对话，保留原单创建来源。
    - 有相似候选但证据不足时，issue new 加 --possible-duplicate 候选编号 --duplicate-reason "相似之处和缺少的证据"，正常建单并在新单对话中显示入口。没有候选就正常建单。
  - issue list [--json]、issue show #033：看问题。
  - issue triage #033：AI 初判，由应用在后台调用。只给模型产品事实（事实摘要、功能点清单和各自的用户旅程、问题的描述、截图路径和对话），不读代码。模型只输出 {"kind","reason","question","howto"}，程序先检查再写：类别必须是四种之一，待补充要带一个具体的问题，已有用法要带用法说明；不合格就什么都不改，只记一次「没判出来」，界面上可以重试。
  - issue reply #033 "补充"：用户补充一句。待处理的问题补充以后，应用会带着补充再初判一次。
  - issue set #033 feature RF-101|none、defer、undefer、dismiss "原因"（写 #18 就是标成和 #18 重复）、reopen、kind bug|request（用户纠正类别）、solved（已有用法解决了）：用户的决定。
  - issue fix #033：开始修复。和需求一样开一个分支 fix/f-005 和工作目录 .worktrees/F-005；一次修复可以带几条问题（一起修）：几条共用一个分支、一个工作目录、一个修复会话，写成 issue fix #033 #034 #035；这几条必须都是待处理、判成「是问题」（或用户按问题直接修）、没放在「以后再说」里、没在分析，否则一条都不开始，错误里写明是哪几条、为什么。
  - issue handback #033 --changed "改了什么" --verify "怎样验证" [--no-regression "为什么写不成"]：修复会话修好、自己验证过、把改动提交到当前分支以后交回，问题变成待你确认。交回前要留下回归数据：这次修复在测试集里加的数据（新建的测试集，或给已有测试集加的条目）至少有一条在这个修复眼里跑过而且通过了，以后再坏，合并前的检查会拦住；实在写不成测试集（只能看界面、要真实的外部服务……）的，用 --no-regression 写清理由。修复报告里写一行回归数据在哪，或者为什么没有。一起修的几条逐条交回，各写各的修复报告；修复会话改了代码、同批里还有处理中的问题没交回，停下来时会被叫回去，叫回去的话里写明是哪几条。
  - issue confirm #033：用户确认修好了。一起修的几条各自单独确认，同一次修复的问题都确认后，修复分支才像需求完成一样合并进主目录现在签出的分支，这几条一起变成已解决；先确认的那条还留在待你确认，只在修复记录的 confirmed 里记下，界面显示「已确认，等同批的 #029」（issue 的 --json 里是 confirmed、confirmed_waiting、waiting_for 和 siblings）。同一时间只合并一个；修复分支还没包含目标分支的最新提交时，没有代码冲突的由程序自己在修复的工作目录里合进来；有代码冲突、或者还有没提交的改动时什么都不落，--json 返回要做的事，应用回到修复会话让 AI 提交、把目标分支合并进来、解决冲突（有冲突时只跑 rf.py test run --fix 和直接测冲突文件的项目测试），它说完再试，这时每一条的确认都保留；合好了才合并回去，问题变成已解决。目标分支上新多出来的提交如果只是程序记的问题文件（.relayforge/issues/），不算没合并进来，需求的确认完成也一样。
  - issue unconfirm #033：用户撤回自己的确认，只在这次修复还没合并时可以，同批别的确认不受影响。只由用户触发。
  - issue reject #033 "还有什么问题"：用户说还有问题，只有这一条回到同一个修复会话（同批别的条保留各自的确认）。
  - 属于还没完成的修复的问题（处理中、待你确认），不能被不处理、以后再说、改类别、标已解决、重新打开：错误里说明要先等这次修复完成，或者用「还有问题」把它退回修复会话。
  - issue probe #033：用户把一条待处理的问题「交给 AI 排查」。只记下这条问题有了排查会话（issues/probes/I-033.json：会话编号按先后），对话里加一行；排查会话本身由应用开：只读，在项目主目录里（看的是主线上的代码），能读代码、能跑、能复现，不能改任何文件，也不能运行由用户决定的命令（issue fix、set、reply、confirm、unconfirm、reject、to-req、probe，req start、done、drop、set）。一条问题一个排查会话，再打开时接着上次的，聊天记录不在了才另开。开始修复时排查会话收起来，修复会话的开场白里带着它的结论。只有待处理的问题能交；issue attach #033 会话编号 把会话挂上去。只由用户（应用）触发。
  - issue finding #033 --kind bug|request|usage|ask --text "结论" [--steps "怎么复现"] [--where "问题在哪"] --verified "实际复现、验证过的" --inferred "只是推断、没验证的"：排查会话记下结论，然后停下。对话里加一条 t=finding（和只看产品事实的初判分开：它读过代码），问题的类别跟着改成它给的（kind_by 为 probe），问题回到「等你决定」，按这个类别给出平常的按钮。除了 ask，--verified 和 --inferred 都必须写，分开写：实际跑过、看到的是前者，读代码推出来的是后者，没有复现过就写「没有复现」，没有推断的写「没有」；判成 bug 还要写 --steps。只有交给过 AI 排查、还在待处理的问题能记；已经在修复里或已关闭的会被拒绝。下一步（开始修复、转需求、解决了、不处理）由用户决定，排查会话不得自己执行。
  - issue reply 加 --to-probe：用户的话交给了开着的排查会话，对话里记成「说给排查会话」，不再触发只看产品事实的初判。
  - 排查会话停下来时的检查：这一轮操作了三次以上（或聊天里下了「根因是……」「结论……」这样的结论）却没有记结论、回复的最后一句也不是问你的问题，就被叫回去：要么用 issue finding 记下，要么说清卡在哪并问一个问题。被叫回一次以后不再拦。
  - 修复会话的开场白（issue brief）里，有排查结论的问题会列出「排查结论」：结论、复现步骤、问题在哪、实际复现过的和只是推断的；修复的人从它出发，推断的部分要自己确认。
  - issue review：问题页的「刷新」，让 AI 在后台复查当前分支上所有「待处理」的问题（别的状态不参与）。程序另起一个进程，在当前提交的一份代码副本里逐条让模型实际排查（读代码、重跑相关的测试、复现），再归并描述同一个故障的问题。每条结论是 gone 不存在、stale 已过期、merge 可合并（带要并入的原单）、still 仍存在（带复现步骤和实际结果）、unclear 没查清之一；另外，某条交给模型以后又有了新回复或改动（比如用户补了证据），模型没看到，这条结论作废、记为 recheck 要重查，留在待处理，不能确认。进度和结果在仓库共用的 .git 目录下的 relayforge-issue-review.json 里，不进 Git；issue review-status 读它。复查进行中或有结果还没处理时再发起，只交回同一次复查。复查不改任何问题的状态；查完以后每条的结论和依据在它的对话里记一条 t=review（修复会话的开场白也会带上）。中途出错或中断：写明原因，什么都不改，可以再发起。只由用户（应用）触发；issue review-discard（关掉结果、不处理）也是。
  - issue review-apply：用户勾选「不存在」「已过期」「可合并」的结果后一次确认（只认应用的标记）。不存在的转入已取消（closed_as: not_issue），已过期的转入已处理，可合并的转入已取消并标为重复（duplicate_of 指向原单，原单的对话里记一行）。逐条核对：复查之后这条问题或它要并入的原单变过（状态、对话、设置），就不按这次的结论改，提示重新复查，其余的照常处理。
  - issue to-req #033：转为需求。新建一个立项中的需求，带上描述、截图和对话（需求文件头记 source_issue）；问题移到不处理，标为已转需求。
  - issue from-req 需求编号 [--feature RF-101]：立项中的需求其实是现有功能的毛病，转为问题。问题照常记在项目主目录里（来源：你，现象是需求说明的原话，文件头记 source_requirement），需求留着，文件头记 converted_issue、变更记录里记一笔。同一个需求再转一次得到的是同一条问题。
- rf.py issue confirm、rf.py issue unconfirm、rf.py issue reject、rf.py issue probe 只由用户在应用里点按钮触发，AI 不得自己执行。
- 立项时 rf.py req brief 算出的影响里，也列出要改的功能点身上还没解决的问题。

## 测试集（tests/）
- 一个测试集 = 一份测试数据（JSON）+ 一段只负责读数据和调用的接入代码。比对由程序做，不由接入代码做；入参、期望、实际输出都是程序真实记录的。一种行为一个测试集。
- 测试集同时挂需求（或修复）和功能点：需求完成后它留在功能点下面。功能点不再是现行的（移到 history/ 或被替代）时，它名下的测试集算过期：不再运行、不删除，列表里标出来；用户也可以手动标成过期或恢复。
- 三个地方：
  - .relayforge/tests/TS-001.json：数据，进 Git，只用 rf.py test 读写，不要手工编辑。
  - .relayforge/tests/stats/TS-001.json：很小的计数（跑过几次、失败过几次、最近 10 次的结果和当时代码、数据的指纹）和 AI 写的分析，进 Git。
  - .relayforge/tests/results/TS-001/范围.json：最近一次的完整结果（每条的输入、期望、实际输出、差异、耗时），不进 Git；范围是 main（主线）或需求、修复的编号，各留各的最近一次。
- 数据文件的字段：id、type（testset）、title、feature（功能点）、requirement / fix（来源需求或修复，用户可以改挂靠）、checks（对应的验收条件原文）、status（current 在用、stale 用户标的过期）和 stale_reason、lang（python、node、java）、entry（接入代码，相对代码根目录；Java 也可以写类的全名）、classpath 和 build（只有 Java 的测试集有，都是可选的，见下面）、in_progress（还没完成的需求或修复新建的）、created、updated、next（下一条数据的序号）、cases、changes（待确认的改动）、log（变更记录，只追加）。
- 一条数据（cases 里的一项）：n（序号，不重复使用）、name（覆盖哪种情况，必填）、cat（正常、边界、异常）、input、expect（期望输出，JSON）或 raises（期望它报错：报错信息里含这段话）、by（ai 或 user）、unseen（AI 新加、用户还没看过）、in_progress（给已经落定的测试集新加、还没完成的需求或修复的编号）、added、source（出处）、usecase（对接的测试用例，「需求编号#用例编号」，比如 R-20261119-ab12#3）。
  - 例：{"n": 4, "name": "月底 23:59 记的账", "cat": "边界", "input": {"bills": [{"id": "b1", "booked_at": "2026-10-31T23:59"}], "month": "2026-10"}, "expect": ["b1"], "by": "ai", "unseen": true}
- 程序拒绝重复数据：输入和已有的某条完全相同的不加（期望也相同的是重复，期望不同的是互相矛盾），报告跳过了几条、和哪条相同。
- 接入代码：一段只读数据、调用被测代码的程序，不含任何测试数据，不做比对；准备动作（建数据等）也在 run 里按 input 做；返回值要能转成 JSON。`test new` 没给 --lang 时按 --entry 的扩展名定（.py 是 python，.js .mjs .cjs 是 node，.java 或 com.acme.RfBills 这样的类全名是 java），看不出来就要写 --lang。
  - Python：一个 .py 文件，导出 run(input)。例：
    - from bills import list_bills, load_bills
    - def run(input): load_bills(input["bills"]); return [b.id for b in list_bills(month=input["month"])]
  - Node：一个模块（.js、.mjs、.cjs），导出 run(input)，可以是 async。CommonJS（module.exports.run、exports.run、module.exports = {run}）和 ES 模块（export function run、export default）都行：按扩展名和离它最近的 package.json 的 type 判断，判断不了（.js 又没写 type）就先当 CommonJS，不行再当 ES 模块。返回值要能 JSON.stringify：undefined 当作 null，函数、BigInt、NaN、循环引用算这一条失败；抛异常或 Promise 被拒绝也算这一条失败，记下信息和栈。被测代码写到 stdout 的（console.log、process.stdout.write）转到标准错误；只用 Node 自带的模块。用哪个 node：环境变量 RELAYFORGE_TEST_NODE，否则 PATH 里的 node，找不到时整个测试集跑不起来并说明原因。例：
    - const { listBills } = require('../src/bills');
    - exports.run = async (input) => (await listBills(input.bills, input.month)).map((b) => b.id);
  - Java：一个类，有 public static Object run(Object input)，或把参数、返回值写成具体类型（Map、List、String、int、long、double、boolean、BigDecimal、枚举、数组、record、有无参构造器加 setter 或 public 字段的 Bean 都能从 JSON 值对上）。输入用 Map（JSON 对象）、List、String、Number（整数是 Long，有小数是 Double）、Boolean、null 表示；返回值同样用这些，另外接受数组、Collection、Optional、枚举（转成名字）、record 和有 getter 的 Bean（转成对象，属性按名字排序）；别的类型这一条报错，不猜。必须是 public static 方法，有好几个 run 重载时用第一个对得上输入的。接入代码写成 .java 源文件（路径相对代码根目录，包名从 package 行读），或写类的全名（类已经编译好）；不收 .class 文件的路径。驱动自带很小的 JSON 读写，不依赖 Jackson、Gson 等库，用反射调用。例：
    - import java.util.*; import com.acme.Bills;
    - public class RfBills { public static Object run(Object input) { Map<String, Object> in = (Map<String, Object>) input; return Bills.ids((List<Map<String, Object>>) in.get("bills"), (String) in.get("month")); } }
  - Java 的 JDK：java 和 javac 用环境变量 RELAYFORGE_TEST_JAVA_HOME 下的 bin，否则 JAVA_HOME，否则 PATH；找不到（或只有 JRE）时整个测试集跑不起来并说明。驱动源码（relayforge/drivers/RelayForgeDriver.java）运行时编译到缓存目录，不要求用户预先编译。
  - Java 的类路径，按顺序取第一个有的，不合并：1. 测试集里的 classpath 字段（test new --classpath，可以写多个，相对路径相对代码根目录，jar 目录可以写 lib/*；用户或 AI 明确给才写）；2. 环境变量 RELAYFORGE_TEST_CLASSPATH；3. 自动识别，从接入代码往上找最近的 pom.xml 或 build.gradle[.kts]：Maven 项目用 target/classes、target/test-classes，加上 mvn -q dependency:build-classpath 的结果（mvn 在 PATH 里，或项目里有可执行的 mvnw；结果按 pom.xml 的修改时间缓存，pom.xml 变了才重取；要联网，失败时报错并提示改写 classpath）；Gradle 项目用 build/classes/java/main、build/classes/java/test 和 build/resources/*，依赖部分自动取不到：build.gradle 里有依赖声明时报「请在测试集里写 classpath，或先运行 gradle 把依赖导出来」并给出一个导出的办法，没有依赖声明就照用；4. 都不是（没有 pom.xml、build.gradle）：用代码目录本身。
  - Java 的编译：项目本身没编译（没有 target/classes 或 build/classes）时，这个测试集跑不起来并提示先编译；RelayForge 不替用户跑 mvn compile 之类的完整构建（慢，也有副作用）。除非测试集里写了 build 字段（test new --build "mvn -q compile"，可选）：写了就在每次运行前先在代码目录里运行它（最多 10 分钟），失败也算跑不起来。build 和准备步骤一样，第一次执行、或命令 / 执行目录改了以后，要用户在应用里看过实际的命令和目录、点同意才执行（应用运行测试集前先问 rf.py test run --prep-check，没同意的 build 和准备步骤一起在同一个确认框里给用户看；用户点同意时应用调用 rf.py test approve-build TS-001 --print 指纹 [--dir 代码目录]，只认应用的标记，指纹按命令加执行目录算：这个项目的主目录和 .worktrees/ 下的工作目录算同一个目录，--dir 指到别处的另算；命令或目录在用户看过以后变了就不算同意。同意记在本机的 approved 里，和准备步骤的同意在一起）。没同意时这个测试集跑不起来，原因写「构建命令还没经你同意」；AI 的会话运行时、项目自己的测试命令经桥接文件运行时也一样不执行。build 是这个测试集自己的、每次都执行；测试环境的「准备步骤」（见「测试环境」）是整套环境的、可以只在某些文件变了以后才执行。两样都有时先执行准备步骤，再执行 build。以后建议都写成准备步骤，build 留着兼容已有的测试集。用户在应用里（查看器的「测试代码」）可以改语言、接入代码、classpath 和 build（rf.py test config）。接入代码是 .java 源文件时：类路径上对应的 class 存在而且不比源码旧就直接用；不存在或比源码旧，就用 javac 把它编译到缓存目录（类路径同上，放在最前面），再加载；编译不过时跑不起来并给出 javac 的输出。
  - 缓存放在 RELAYFORGE_HOME（默认 ~/.relayforge）/cache/testsets/ 下，不进仓库：java-driver/（编译好的驱动，键是驱动源码加 javac）、java-entry/（编译好的接入代码，键是代码目录、接入代码、类路径）、maven/（依赖类路径，键是项目目录）。可以随时删掉，下次运行重建。
- 执行：程序读数据 → 在代码目录（主目录，或某个需求、修复的工作目录）里启动语言驱动 → 驱动加载接入代码、逐条调用、交回每条的实际输出或异常和耗时 → 程序逐条和 expect 做深度相等比对（按 JSON：true 不等于 1，1 和 1.0 相等）→ 写结果。三种结果：
  - 通过；失败：跑了但输出和期望不同（记下差异），或者这一条抛了异常（记下异常）；跑不起来：接入代码加载失败、驱动崩了或超时（默认 120 秒），这个测试集的所有条都算跑不起来，记下错误。
- 驱动协议（三种语言一样；驱动在 relayforge/drivers/ 下：python_driver.py、node_driver.mjs、RelayForgeDriver.java）：当前目录是代码目录；标准输入一份 JSON {"protocol": 1, "root": 代码目录, "entry": 接入代码, "cases": [{"n", "input"}…]}；标准输出一行一个 JSON：{"t":"ready"}，或 {"t":"load_error","error","trace"} 后退出；每条 {"t":"case","n","ok":true,"output","ms"} 或 {"t":"case","n","ok":false,"error","trace","ms"}；最后 {"t":"done"}。Java 驱动另外收到一个 "class": 接入代码的类全名（程序算好的）。被测代码打印的东西一律转到标准错误（被测代码自己起的、直接继承标准输出的子进程除外）。没有 ready、没写完所有的 case、中途退出、超时，都算跑不起来。
- 提示只用程序能算的固定规则：跑不起来（最近一次）；从没失败过（跑过 20 次以上，一次没失败）；时过时不过（同一份代码和数据，最近几次结果不一样）。
- 进行中：
  - 还没确认完成的需求（或修复）新建的测试集，文件头 in_progress 写它的编号；给已经落定的测试集新加的数据，那一条带 in_progress。主线上的会话不把它们当依据，主线上运行也不跑它们。确认完成时去掉标记；放弃时，它新建的测试集移到 history/tests/（dropped_with），它加的数据标 dropped_with、提出的改动标 dropped；恢复时拿回来。
  - AI 改动或删除已经落定的数据（别的需求留下的、已在用的）不直接生效：记成 changes 里的一条（id、case、op 是 edit 或 delete、old 旧值、new 新值、why 理由、by 提出的需求或修复、state、at、source），理由必填。用户同意（state 变成 approved，在这个需求眼里生效，需求确认完成时落定；提出它的需求已经完成或是主线上提的，同意就直接改）或不同意（丢弃，变更记录里留一行）。新加数据不用确认；AI 改自己进行中加的数据也不用确认。
  - 运行某个需求的测试集，用「这个需求眼里的数据」：落定的、它进行中新加的、它提出的还没被否决的改动。范围包括它新建的测试集、挂在它名下的，以及它动到的功能点（要改的功能点、它新加或修改的功能点）下已有的测试集；结果里区分哪些是它新建的（origin: new）、哪些是以前就有的（existing）。
  - 用户在应用里直接改数据不用确认（rf.py test save）。
  - 进入测试以后，测试会话为这个需求新建的测试集和新加的数据（数据文件里 made_in: test），对开发会话来说视同已经落定：开发会话改它、删它也要写 --why，记成待确认的改动，等用户同意；测试会话自己改不受限，开发会话自己加的（made_in: develop）也不受限。谁在改按会话的种类认（见「需求」的「谁是测试会话」）。
  - 需求确认完成时，完成记录里写一行：几个测试集（新建几个、原有几个）、多少条、最近一次运行通过、失败、跑不起来各多少条。有失败不挡确认完成。修复确认修好了时，同样的结论写进修复记录的 tests 和问题的变更记录。
- 合并前的检查（合并闸门，程序做，不用会话做）：需求确认完成（修复确认修好了）合并时，工作目录已经包含目标分支的最新提交（必要时程序刚合进来），程序就在那里、合并之前跑一遍选出来的测试集，不跑全量：
  - 本需求的（和 test run --req 一样的范围）；依赖它的（功能点文件头 depends_on 写着本需求动到的功能点的那些功能点下的，只往外一层）；主干（标为主干的用户旅程用到的功能点下的）。
  - 这份代码上已经测过、而且通过了的（最近一次完整结果的代码指纹和数据指纹都一样）不再跑；按最近一次的耗时估，超过 5 分钟的从主干、依赖它的里往后去掉，去掉的写进记录，留给全量（test run --all）。在项目主目录里跑的全量会记一份摘要（tests/results/_full.json，不进 Git：什么时候、在哪个提交上、哪些没过）；测试页和发布前会显示上次全量是什么时候、之后又合进来几次、哪些没过，只提醒，不挡发布。程序不在后台自己跑全量：它会在你的项目目录里执行准备步骤和项目代码。
  - 主线上最近一次运行就失败了同样那几条的，算原来就失败，不挡合并。其余没过的挡住合并：程序把没过的测试集和条目交回这个需求（修复）的会话修，它说完一轮再检查。测试环境的准备步骤、测试集的构建命令还没经用户同意时，不替用户执行，合并停下来等用户同意。
  - 用户可以在应用里选择跳过检查直接合并（rf.py req done / issue confirm 的 --skip-gate，只由用户触发）。完成记录里写一行检查的结论（跑了几个、复用几个、原来就失败的、留给全量的、是否跳过）。
- 命令（rf.py test …，在需求或修复的工作目录里运行时自动按那个需求或修复）：
  - test new "测什么行为" --feature RF-101 --entry tests/rf/bills.py [--lang python|node|java] [--classpath 路径 …] [--build 命令] [--check "验收条件原文" 或 --check 2]：新建，空的。
  - test add TS-001 --name "覆盖哪种情况" --cat 正常|边界|异常 --input JSON --expect JSON（或 --raises "报错里的话"）[--usecase 用例编号]；批量：--file 数据.json（JSON 数组，或 {"cases": [...]}，每条可以写 "usecase": 3；- 表示标准输入）。
    有测试用例的需求，测试会话加或改的每条数据都要挂上一条存在的、在用的用例（--usecase）；用例编号是这个需求的，程序存成「需求编号#用例编号」。没有用例的需求、修复和主线不要求。
  - test edit TS-001 3 [--name/--cat/--input/--expect/--raises] [--why "理由"]，test rm TS-001 3 [--why "理由"]：改落定的数据时 --why 必填，记成待确认的改动。
  - test run [TS-001 …] [--req R-… | --fix F-… | --feature RF-101 | --all] [--case 3] [--dir 代码目录] [--timeout 秒] [--env ENV-001 | --no-env] [--prep-check] [--json]：不写目标时，在需求或修复的工作目录里跑它的全部，在主目录里跑全部在用的。--case 只跑一条（并进上一次的结果，不算一次运行）。过期的、别的需求进行中的不跑，列在 skipped 里。运行前先执行测试环境里要执行的准备步骤（见「测试环境」）；--prep-check 不运行，只列出要执行、但用户还没同意的准备步骤（应用先拿它问用户）。
  - test analyze TS-001 --text "哪些过了、哪些没过、为什么"：运行后写分析，标明是 AI 写的。
  - test list [--req R-… | --fix F-… | --feature RF-101] [--stale] [--json]、test show TS-001 [--req R-…] [--json]：只读，给应用和会话看。
  - test bridge [--lang python|node|java] [--path 路径]：按项目里在用的测试集用到的语言，在代码里生成桥接文件，让项目自己的测试命令也跑到测试集（每个测试集一个测试，每条数据一个子项；用同一个执行器和比对，不记结果；找不到 .relayforge/bin/rf.py 时跳过）。没有测试集时生成 Python 的。--path 只能配一种语言。
    - Python：tests/test_relayforge_testsets.py，unittest / pytest 跑。
    - Node：tests/relayforge-testsets.test.mjs，node --test 跑（调 python3 .relayforge/bin/rf.py test bridge-run --lang node --json；python3 不在 PATH 时用环境变量 RELAYFORGE_PYTHON 指定）。
    - Java：src/test/java/RelayForgeTestSetsTest.java（项目的 pom.xml 或 build.gradle 里有 JUnit 5 才生成，没有就不生成并说明），JUnit 5 跑：每个测试集一个 DynamicContainer，每条数据一个 DynamicTest，调 test bridge-run --lang java（输出是制表符分隔的行，不需要 JSON 库）。
  - test bridge-run --lang node|java [--json]：桥接文件自己调用的，不用手工运行：跑这种语言在用的测试集，不记结果，输出每个测试集和每条数据的结果。
  - 只由用户（应用）触发，AI 不得自己执行：test approve / reject TS-001 改动编号（同意 / 不同意 AI 的改动）、test stale TS-001 [--reason]、test revive TS-001、test move TS-001 [--feature RF-102] [--req R-…|none]（改挂靠）、test save TS-001 [--case 3|new] [--req R-…] --file 数据.json（以用户身份保存整份或一条）、test seen TS-001 [--case 3]（AI 新加的标为看过了：应用里只有用户点「看过了」或「这些我都看过了」才调用，点开一条不算）、test config TS-001 --file -（以用户身份改 lang、entry、classpath、build；JSON {"lang", "entry", "classpath": [...], "build"}，没给的不变，classpath 和 build 只有 Java 能写；改了 build 以后第一次执行照样要同意）、test approve-build TS-001 --print 指纹 [--dir 代码目录]（同意执行构建命令，只认应用的标记，终端里也不行）。程序自己校验（见「只由用户触发的命令」）。
- 需求的测试集由测试会话写（见「需求」的测试会话：有测试用例的需求，按用例对接，每条数据挂着它对应的用例），开发会话不负责新建，可以为了开发方便跑已有的；问题的修复会话自己写。新测试一律写成测试集；新测试一律写成测试集；实在表达不了的（界面、并发、时序之类）才写普通的代码测试，并用 rf.py note 说明原因；跑完写分析。动到的功能点的旧测试集失败时，逐条判断是需求有意改了行为（用 test edit --why 提出改动，等用户确认）还是改坏了（修代码）。
- 会话停下来时的检查：需求或修复的会话这一轮用编辑工具新增或修改了看起来像测试的文件（tests/ 目录下、test_*.py、*_test.py、*.test.js、*.spec.ts、*Test.java 之类），却既没有运行 rf.py test、也没有用 rf.py note 说明原因（说明里提到「测试」），就被叫回去；测试集的接入代码和桥接文件不算。被叫回一次以后不再拦。
- 测试会话停下来时的检查：这一轮改了的文件（和这一轮开头比：工作目录里的改动、新提交的，加上用编辑工具写的），只要有一个既不是测试集的接入代码、也不是桥接文件、也不在测试目录下（tests/、test/、__tests__/、spec/、src/test/ 之类，或像测试的文件名），就被叫回去：撤回这些改动，把问题用 rf.py req verdict problems 交回。被叫回一次以后再停下来不再拦。

## 测试环境（envs/）
- 一个项目可以有几套测试环境（本机、测试服…），一套一个文件 .relayforge/envs/ENV-001.json，进 Git；只用 rf.py env 读写，不要手工编辑。编号不变，改名只改 name。删除不真删：移到 history/envs/，status 写 removed。
- 标了保密（secret: true）的值只存在这台电脑上：$RELAYFORGE_HOME（默认 ~/.relayforge）/envs/<项目标识>.json，权限 600、目录 700，不进仓库。仓库里的文件对保密的项只留名字和 "secret": true，没有 value。换一台电脑时保密的值要重新填一次。项目标识和会话存档一样：项目主目录的名字加它完整路径的一段散列。
- 本机的部分分三个文件（都是 600、目录 700），按 AI 的会话能碰到的程度分开：envs/<项目标识>.json 只有保密的值，应用开的会话（沙箱里）读不了也写不了；env-consents/<项目标识>.json 是用户的决定（同意执行的命令 approved、允许 AI 的会话带上保密值 ai_secrets、正在用哪一套 use、当前测试用户 user，以及哪些保密项填了值 secret_keys，只有打码），会话能读不能写；env-state/<项目标识>.json 是上次读配置、连通检查、AI 的提议、准备步骤上次执行的情况，会话能读能写。以前这些都在 envs/<项目标识>.json 里，程序第一次在会话外读到时自动拆开。会话里看到的保密项只有「填了没有」；用户允许了 AI 的会话带上保密值时，会话里运行测试集前由应用代取（rf.py env ai-values，只在允许时给）。Codex 的会话用它自己的沙箱，读得到保密值的文件（写不了），所以对 Codex 会话保密值只靠不放进它的环境。
- 本机文件里还有：use（这台电脑上正在用哪一套）、user（每套环境当前的测试用户）、scans（上次读配置文件的结果，配置文件可能是不进仓库的本机文件，所以读出来的地址也只放在本机）、checks（上次连通检查的结果）、proposals（AI 交回、还没处理完的建议）、approved（用户同意执行过的准备步骤命令，键是命令和执行目录的指纹）、prep_runs（准备步骤每条在每个代码目录里上次执行的结果、输出的最后部分，和执行成功时那些文件的指纹）、ai_secrets（用户允许 AI 的会话运行时带上保密值的环境）。
  - 例：{"project": "/Users/me/bills", "use": "ENV-001", "user": {"ENV-001": "U1"}, "secrets": {"ENV-001": {"vars": {"DB_PASSWORD": "…"}, "request": {"header:X-Api-Key": "…"}, "users": {"U1": {"jwt": "eyJ…"}}}}, "scans": {…}, "checks": {…}, "proposals": {…}}
- 一套环境的字段：id、type（testenv）、name、note（一句说明）、services、config、deps、vars、request、users、next_user、prep、next_prep、created、updated、log（变更记录，只追加，不记任何值）。
  - services：怎么启动，若干个服务 {"name": "后端", "command": "mvn spring-boot:run", "port": 8080, "dir": "相对项目的工作子目录，可以空", "accept": [{"name": "DATA_DIR", "value": "{{scratch}}/data"}], "auto_restart": false}。人工验收和人工测试由应用照着启动（见下面的「人工验收」）。
    auto_restart 是「代码变了自动重启」，默认开，文件里只在关着时写 "auto_restart": false（没有这个字段就是开）；它不算启动命令的一部分，改它不用重新同意。
    accept 是「验收时额外带的环境变量」（可以没有），让验收用的实例不碰真实的数据和项目；值里可以用占位符 {{req}}（需求编号，主线是「主线」）、{{worktree}}（这个需求的工作目录，主线是项目主目录）、{{scratch}}（程序为这次验收准备的临时目录）、{{project}}（项目主目录）、{{project_copy}}（项目主目录的副本）。只放目录、标记这类不保密的设置，名字像保密项的不收（保密的放 vars）。
  - config：用项目里的哪个配置文件（相对路径）。外部依赖（数据库、缓存、外部服务的地址）由程序从这个文件读出来，不在这里重填；配置文件照旧由用户自己维护。
  - deps：只放用户在工具里手改的依赖 {"key": "配置里的键（盖过配置文件的同一项），或 user:序号（新加的）", "name", "type", "address"}；地址里的口令一律打码。界面上的依赖表 = 配置文件读出来的（来自配置文件）+ 这里的（在这里改的）。
  - vars：环境变量 {"name": "DB_URL", "value": "…", "secret": false} 或 {"name": "DB_PASSWORD", "secret": true}。运行测试集时加进驱动进程的环境；值里的 ${NAME:默认值} 占位符读配置文件时也用它们代入。
  - request：请求的通用设置 {"items": [{"in": "header" 或 "query", "name": "Authorization", "value": "Bearer {{user.jwt}}", "secret": false}], "before": "发请求之前运行的 JS", "after": "收到返回之后运行的 JS"}。值里 {{变量名}} 是环境变量，{{user.键名}} 是当前测试用户的值。脚本这一步只存，还不执行。
  - prep：准备步骤，有顺序，运行测试集之前由程序执行 {"id": "P1", "note": "装依赖", "command": "npm ci", "dir": "web（相对项目的执行目录，可以空）", "when": "always（每次运行前）或 changed（watch 里的文件变了以后）", "watch": ["web/package-lock.json"]（相对代码根目录，可以用 * 和 **）, "timeout": 600（秒，1 到 3600）}。id 由程序给，不重复使用。命令里不写保密值，用环境变量。
  - users：测试用户 {"id": "U1", "name": "测试用户 A", "note": "普通用户", "fields": [{"key": "jwt", "secret": true}, {"key": "uid", "value": "u_1001", "secret": false}]}；键名用户自己起（jwt、uid、aid、talent_id、tenant_id…）。id 由程序给，不重复使用。
- 外部依赖的读取（只用标准库）：Spring 的 application*.yml / .yaml（自带的缩进式读取：映射、列表、带引号和不带引号的值、注释、--- 分隔的多份文档；锚点和别名、多行文本 | >、行内 { }、标签 !! 不支持，跳过那一段并报告第几行）、.properties、.env。认得的键：spring.datasource.url（及 *.url、jdbc-url）、spring.r2dbc.url、spring.data.redis.* / spring.redis.*、spring.data.mongodb.*、spring.rabbitmq.*、spring.kafka.bootstrap-servers、spring.elasticsearch.uris、DATABASE_URL / DB_URL / JDBC_URL / *_DATABASE_URL、REDIS_URL、REDIS_HOST + REDIS_PORT、DB_HOST + DB_PORT、MONGODB_URI、AMQP_URL / RABBITMQ_URL、KAFKA_BOOTSTRAP_SERVERS；键以 url、uri、base-url、endpoint 结尾、值是 http(s):// 的记成 HTTP 接口；xxx.host 旁边有 xxx.port 的记成 TCP 服务。认不出来的不猜。
- 连通检查：对每个依赖只做 TCP 连接（主机和端口从地址里取，每个最多等 2 秒），结果是能连上、连不上、没配（没有地址、占位符没代进去、嵌入式数据库）。不登录、不发业务请求、不写数据。
- 测试集运行（rf.py test run）带上环境：默认用这台电脑上正在用的那套，--env ENV-002 指定别的，--no-env 不带；它的环境变量加进驱动进程（和准备步骤）的环境。结果里只记用的是哪套环境（id、name），不记值；结果和输出里出现的保密值一律换成 ••••••（只替换 3 个字以上的：太短的替换会把正常内容也打码，界面上也写明了）。
- 保密值只在用户自己运行时带上：应用调用 rf.py 时带一个只有应用知道的标记（启动时随机生成，只放进应用调用 rf.py 的那个进程的环境变量 RELAYFORGE_APP_TOKEN，不放进它开的会话；$RELAYFORGE_HOME/apps/<应用的进程号>.json 只存它的 SHA-256，rf.py 还要看自己的父进程是不是应用；在沙箱里运行的 rf.py 一律不认这个标记：应用开的会话里的命令都在系统的沙箱里，会话写不了登记目录，在沙箱里自己伪造的登记也不算）。没有这个标记的一律按 AI 的会话处理：运行测试集和准备步骤时只带不保密的变量，除非用户在应用里给这套环境勾了「允许 AI 的会话运行时带上保密值」（只记在本机；勾上的风险是 AI 写的代码能读到这些值）。因为这样跑不起来时，错误里写明「这次没有带保密值（变量名）：在应用里运行，或在测试环境里勾选……」。准备步骤的同意、这个开关和取明文（env reveal）也要这个标记，会话里做不了。
- 准备步骤（prep）：Agent 负责把路打通一次，程序负责以后每次照着跑。运行测试集之前，程序按顺序执行这次需要执行的步骤（always 的每次都执行；changed 的在这个代码目录里没成功执行过、命令改了、或 watch 的文件变了才执行），在代码目录（主目录，或需求、修复的工作目录）下的 dir 里，用 shell 执行，最多 timeout 秒。第一次执行某条命令、或命令文字（或执行目录）变了以后，要用户在应用里看过命令和执行目录、点同意（同意记在本机，按命令和目录的指纹）才执行；没同意的那一步不执行，这次运行的测试集都算跑不起来，原因写明是哪一步。某一步失败（退出码不是 0 或超时）也一样：这次的测试集都算跑不起来，原因写明是哪一步、命令、执行目录和输出的最后部分（保密值打码）。执行情况和输出只记在本机，不进仓库。
- 「让 AI 来处理」：测试集跑不起来、准备步骤失败、连通检查有连不上的依赖时，应用把程序写好的一段话（rf.py env handoff）交给一个会话：是哪个测试集或哪一步、完整的错误和输出的最后部分、当前环境的名字和不保密的设置（保密的只有名字）、它能做什么（装东西分三级：项目目录里的安装和构建预先放行；系统级的安装和改电脑状态的每次都要用户同意，装之前先说装什么、为什么、装到哪；发布、部署、推送和读取保密值的途径禁止）、做完怎么交回。在进行中的需求（或修复）里交给它的开发会话，否则新开一个日常聊天。会话试出来的做法用 env propose 交回；用户采纳以后点「再跑一次」。交过去的话里不会有任何保密值（程序把这个项目所有环境的保密值都打码）。
- 命令（rf.py env …）：
  - 只读，会话可以用：env list [--json]、env show [ENV-001] [--json]（保密的值是 null，has_value 说明填没填）、env scan ENV-001（重新读配置文件）、env check ENV-001（检查连通）、env resolve [ENV-001] [--user U1]（这次请求会带上哪些请求头和地址参数，保密的打码）、env prep [ENV-001] [--dir 代码目录]（准备步骤、同意了没有、下次要不要执行、上次的结果）、env handoff set TS-001 [--req R-…|--fix F-…] / prep ENV-001 [--step P1] / check ENV-001（「让 AI 来处理」交给会话的话）。
  - 会话可以用：env prep-run [ENV-001] [P1 …] [--dir 代码目录 | --req R-…] [--due]（手动执行一遍，不管要不要执行；--due 只执行这次要执行的；只执行用户同意过的命令；会话里不带保密值）。
  - 只读，会话也可以用：env plan [ENV-001] [--req R-…] [--service 名]（人工验收这次怎么启动：每个服务的命令、目录、端口、验收时带的变量（占位符代进去以后）、同意了没有、要执行的准备步骤；保密的打码，不建目录、不复制项目）。
  - 会话交回建议：env propose ENV-001 --file -（JSON：{"summary": "读了哪些文件、试了什么", "prep": [{"note", "command", "dir", "when", "watch", "timeout", "why"}], "services": [{"name", "command", "port", "dir", "why"}], "config": {"file": "路径", "why"}, "vars": [{"name", "value"（只有明显不保密的才写）, "secret", "why"}], "testsets": [{"id": "TS-001", "classpath": [...], "build", "entry", "lang", "why"}]}）。程序不收保密项的值；名字里有 password、secret、token、key 之类的一律算保密。建议存在本机，接在还没处理完的建议后面，等用户在应用里逐条采纳或忽略；采纳的准备步骤第一次执行前仍要用户同意，采纳的测试集设置按 test config 改。
  - 只由用户（应用）触发，AI 不得自己执行：env new 名称 [--note]、env copy ENV-001 [--name]、env rename ENV-001 新名字 [--note]、env rm ENV-001、env save ENV-001 --file -（整份保存，含准备步骤）、env use ENV-001|none（选用哪一套）、env user ENV-001 U1（选当前测试用户）、env reveal ENV-001 [--resolve] [--user U1]（取明文，要应用的标记）、env adopt / ignore ENV-001 [序号…]（采纳或忽略 AI 的建议）、env approve ENV-001 [P1 …] [--service 服务名 …]（同意执行准备步骤、人工验收的启动命令，要应用的标记）、env ai-secrets ENV-001 on|off（允许 AI 的会话运行时带上保密值，要应用的标记）、env launch [ENV-001] [--req R-…] [--service 名] [--copy reuse|fresh]（应用启动服务前取启动的全部设置，带保密值，建临时目录、需要时复制项目，要应用的标记）、env accept-clean [--req R-…]（清掉验收的临时目录和项目副本）。
- 人工验收（需求的「人工验收」标签）和人工测试（测试页，对着项目主目录）：应用的主进程直接启动、停止、重启服务、收日志，不经过模型。
  - 在哪里跑：需求的工作目录（加上服务的 dir），主线是项目主目录。带上这套环境的环境变量（是用户在应用里点的，带保密值）和服务的 accept（占位符代进去）；应用自己的 RELAYFORGE_* 变量一律不带过去（验收实例不会拿到正式实例的项目和数据目录）。
  - 本机的位置（不进仓库）：$RELAYFORGE_HOME/accept/<项目标识>/<需求编号或 main>/ 下：scratch/（{{scratch}}，每个需求一个，停掉以后可以用 env accept-clean 清掉）、project-copy/（{{project_copy}}）、services.log（日志文件，保密值打码以后才写）。
  - 项目副本：只在有服务用到 {{project_copy}} 时才做。git clone --local --no-hardlinks 项目主目录当前签出的分支（对象是复制的，不借用真实仓库），去掉 origin（推不回去），再把主目录现在的 .relayforge/（包括还没提交的事实）盖上去；不用 git worktree（它和真实仓库共用分支）。默认沿用上次的副本，启动时可以选「重新复制」。不是程序做的副本（没有 .git/relayforge-accept-copy.json）的目录不覆盖。
  - 同意：服务的启动命令第一次执行、或命令和目录改了以后，要用户在应用里看过命令、目录和验收时带的变量、点同意（env approve ENV-001 --service 服务名，要应用的标记；同意记在本机的 approved 里，键是 "svc:" 加命令和目录的指纹，和准备步骤的同意分开）。启动之前先按「准备步骤」的规矩执行这次要执行的（还没同意的一起问）。
  - 启动：每个服务一个进程组（detached），停的时候整组停（先 SIGTERM，3 秒后 SIGKILL）。同一个范围（需求或主线）的同一个服务只有一个实例；不同需求可以同时各起各的。配了端口的：启动前端口已经能连上就如实报「端口被占用」；启动后每隔一会儿做 TCP 连接，连上才算运行中，一直连不上（默认 90 秒）算启动失败并停掉。没配端口的（比如桌面应用）进程活着就算运行中，几秒内就退出的算启动失败。
  - 日志：每个服务的标准输出和标准错误合在一起按时间显示，可以只看一个服务、清空；内存里每个范围留最近 2000 行。
  - 停掉：切换项目、应用退出、需求确认完成或放弃（工作目录收掉之前）时，应用把它启动的进程整组停掉。每个进程在 $RELAYFORGE_HOME/run/services/ 记一份（应用的进程号、进程号、ps 给的启动时间）；应用异常退出后，下次启动时记录的主人已经不在、进程还在而且启动时间对得上的，整组停掉。
  - 启动失败时「让 AI 来处理」：env handoff start ENV-001 --service 服务名 [--req R-…] --file -（应用给出启动的情况：命令、目录、退出码或原因、日志尾部，已打码），交给进行中的需求的开发会话，或新开一个日常聊天；它试出来的做法照旧用 env propose 交回。
- JWT：测试用户的值像 JWT 时，界面显示解出来的内容（载荷里的字段、过期时间、是否已过期）；只做 base64 解码，不验签。

## 知识保鲜（rf.py fresh）
- 功能点只在需求流程里更新；修复、直接在主分支上的提交、改别的功能点的需求都可能让它的描述和代码对不上。程序算哪些功能点「可能过时」，由你决定核对哪个。
- 功能点对应哪些代码：改过这个功能点的已完成需求、修复改过的文件（不算测试文件），按次数加权；还没被任何需求改过的「对应不上代码」。rf.py fresh files RF-101 [--json]，只读。
- 可能过时：从上次核对到的提交（功能点文件头 checked_at，没有就是最近一次改它的需求或修复的合并提交）往后，有提交改了它对应的代码、又不属于「要改的功能点」里有它的需求或修复；只改了注释、空白、测试文件的不算。rf.py fresh drift [RF-101] [--json]，只读。
- 核对只在你在大图上点「核对」时做：开一个只读的核对会话（会话的种类是 check），它用 rf.py fresh brief 看改动，读代码，用 rf.py fresh propose RF-101 --file - 交回 JSON：{"verdict": "changed|unchanged", "summary", "items": [{"section", "op": "replace|add|remove", "old", "new", "why", "evidence"}]}（只有为这个功能点开的核对会话能交回）。建议存在 .relayforge/fresh/RF-101.json。
- 只由用户（应用）触发：fresh adopt RF-101 [序号 …]（写进功能点，出处记成这次核对，旧的那句标〔已替代〕）、fresh ignore、fresh done（建议都处理完以后，checked_at 记成核对时的提交，同样的提交不再让它显示可能过时）。AI 不得自己改功能点文件来「采纳」。
- 开发中改到了「要改的功能点」以外的功能点的代码：rf.py conflicts 的 outside 列出来，需求面板上标出，经收件箱告诉开发会话一次，只提示不挡开发；确实要改就把它加进要改的功能点（完成时它的描述才会一起更新）。

## 只由用户触发的命令
- 下面这些命令由用户决定，AI 不得自己执行（AGENTS.md 第 14、17、19、21、22、23 条）。除了会话的权限规则禁止，rf.py 自己也校验（backend/relayforge/core/trust.py 的 USER_COMMANDS 和 APP_ONLY）：
  - req start、done、drop、set、restore、choose、to-test、skip-test、accept、case-ok、case-no、case-save；
  - issue confirm、unconfirm、reject、probe、fix、set、reply、to-req、from-req；
  - test approve、reject、stale、revive、move、save、seen、config；
  - env new、copy、rename、rm、save、use、user、adopt、ignore；
  - publish run、pull；data import（从导出的包恢复记录）、data migrate（把旧项目的记录迁到本机）；summarize、archive（程序在确认完成以后、打开项目时调用）。
- 校验的规则：有应用的标记（见「测试环境」里的应用的标记）照常执行；没有标记、但是人在终端里直接敲的，也允许，这时变更记录（需求、问题、发布记录的「变更记录」，测试集和测试环境的 log）里这一行注明「（用户在终端里执行）」；
  其余一律拒绝，说明「这个操作只能由你在应用里做」。「人在终端里直接敲的」指：标准输入和输出都是终端，并且不在任何 AI 会话里。
- 被拒绝时，说明的最后会写「如果你是 AI 的会话：……」，告诉会话该改做什么（比如做完了就停下来告诉用户、修完用 issue handback 交回）。照着做，不要换一种写法或工具再试；Claude Code 和 Codex 的会话在执行前就会被拦下并收到同样的说明。
- 「是不是在 AI 会话里」只有一个判断（trust.ai_session_reason）：环境里有会话的变量（CLAUDECODE、CLAUDE_CODE_ENTRYPOINT、CLAUDE_CODE_SESSION_ID、CLAUDE_PROJECT_DIR、CODEX_THREAD_ID、CODEX_SANDBOX、
  RELAYFORGE_SESSION_ID、RELAYFORGE_SESSION_SIG 等，值非空），或者上层进程里有 claude、codex、Node 跑的 Claude Code / Codex、RelayForge 开会话用的 pty_bridge.py。脚本、管道、git 钩子不是终端，不允许。
- 只认应用的标记、终端里也不行的（APP_ONLY）：env approve（同意执行准备步骤和启动命令）、env ai-secrets、env reveal、env launch、env accept-clean、test approve-build、req test-kicked、req test-told、split（应用检查会话的拆分建议、执行「同意拆分」），以及 req attach --test：要用户在应用里看过实际的内容再点，或者是应用自己的记账。
- 刻意不校验的：rf.py confirm 和 rf.py reject（确认、否决待确认的条目）。它们由 rf-confirm 技能在用户明确表态以后由 AI 执行，应用里没有别的入口；收紧它要先给应用加上确认待确认条目的界面。

## 会话的身份
- 程序要知道「这是哪种会话」（开发、测试、修复、排查、立项、大图编辑、日常聊天）和它属于哪个需求、修复或问题时，只认应用签过名的会话令牌，不认环境变量里裸的会话编号（会话可以在命令前改写环境变量）。
- 应用开每个会话时发一个令牌，放在会话的环境变量 RELAYFORGE_SESSION_SIG 里（名字里不带 TOKEN、KEY、SECRET：Codex 默认会把名字里带这几个词的环境变量从命令的环境里去掉）：
  base64url(内容) "." base64url(HMAC-SHA256(密钥, 前一段))，内容是 {v, sid 会话编号, kind 种类, owner 需求 R-… / 修复 F-… / 问题 I-…, iat 签发时间, nonce}。
- 密钥只在应用进程的内存里，每次启动重新生成，不写进任何文件。rf.py 验证时从自己往上找祖先进程里登记过的应用（$RELAYFORGE_HOME/apps/<进程号>.json 里的 socket），
  通过这个本机的 unix socket（文件，不是网络端口）问应用；应用验签名，并说出这个令牌发给了哪个会话进程，rf.py 再确认那个进程是自己的上层进程（别的会话的令牌拿过来用不上）。
- 没有令牌、应用没在运行、签名不对、进程对不上的，一律按最低的身份（日常聊天）算；需要更高身份的命令（req steps、verdict 要测试会话，req retest 要开发会话，req case-add、case-edit、case-rm、classify 要这个需求的立项、开发或测试会话）会说明「请在应用里重新打开这个会话」。
- 结束检查（钩子）里的会话编号由 Claude Code 自己交给钩子，照旧对上 test_sessions；RELAYFORGE_SESSION_ID 照旧给提交挂会话、找聊天记录用，只是记录，不是权限判断。

## 开发会话的 Subagent
- 用户在需求的立项对话中回复「这个需求可以用 subagent」授权，也可回复「这个需求可以用 subagent，请用 Codex」或「这个需求可以用 subagent，请用 Claude Code」。立项时可回复「撤回 subagent 授权」。
- 应用在本机设置中按项目和需求分别保存授权和 CLI、模型选择。单需求和全局配置都不授予权限。应用信任的立项会话聊天记录才参与授权交接，`subagent decision` 由应用使用。
- 已授权的开发会话可以用 `rf.py subagent status` 看生效的 CLI、首选模型和可选模型，用 `rf.py subagent run "子任务说明" [--model 模型 --reason "选择依据"]` 委派并收到 JSON 结果。按任务复杂度选模型，用户的首选模型合适时可以优先使用。
- 委派前检查所选 CLI 的安装和登录状况。不可用时暂停，向用户说明原因，等重新登录或在需求右侧明确改选后再次执行同一条命令。

## 边做边记（rf.py note）
- 会话在干活的过程中自己记，一轮里有新进展就记一两条，不要攒到最后：
  - note doing "现在在做什么、卡在哪"
  - note assessment '{"highlights":[{"title":"要解决什么","text":"一句说明"}],"decisions":["需要用户拍板的问题"],"decided":["AI 已决定的事项"],"refine":["待细化的事项"]}'：立项会话更新右栏评估，选填字段，每次替换整份。重点可用 text 写说明、scenarios 写两项 `{"title":"场景","text":"路径和结果"}` 对照，或 steps 写影响路径。严重风险用 `"risk":{"status":"pending","title":"风险是什么","consequence":"可能后果","evidence":"缺少的证据"}`，核实后改成 confirmed 并填写核实依据。评估存在需求文件头 intake_assessment（来源 intake_assessment_source），不参与清晰度和立项门槛计算。
  - note plan "第一步" "第二步" …（第一次定下计划，或计划变了）
  - note step 2 done "一句话结果"（状态：done、doing、todo、dropped；也可以用步骤的标题指定；几步一起标写 step 1,2,3 done）
  - note change "方向变了：原来…现在…"
  - note touch RF-101 M-02（这个会话在改的功能点和模块）
  - note decision "标题" "用户定下的一件事"（--reason 写理由；是推断而不是用户说的，加 --guess）
  - note open "一个还没定的问题"
  - note say|feature|check "…"（在需求的工作目录里：写进需求说明、要改的功能点、验收条件；推断的加 --guess）
  - note new-feature "名称" --module M-01 --reason "一句话定位"（需求里新加一个功能点：在需求的工作目录里运行时标为这个需求进行中）
  - note fact RF-101 "新的陈述" [--head 规则与边界] [--replaces "要换掉的旧陈述里的一段话"]（改一个现有的功能点、模块或用户旅程：在需求的工作目录里运行时写成〔进行中〕的改动，见「进行中的改动」）
  - note same（这一轮确实没有任何要记的）
- 只记对用户有用的：做到哪了、定了什么、什么没定。试错和调试的细节不记。
- 出处由命令自动标成当前会话和最近一条用户消息。
- 在需求的工作目录里运行时，记下的裁定也标为这个需求进行中（文件头 in_progress），确认完成后才算现行。

## 发布（publishes/）
- 确认完成、确认修好了之后，代码只合并进了项目目录当前分支，没有推送。推送可能触发部署，所以只由用户在应用里点「发布」触发，AI 不得推送：不运行 git push，也不运行 rf.py publish run 和 rf.py publish pull。
- rf.py publish status [--json] [--fetch] [--remote 远端]：看现在的分支和上游、领先落后几个提交、还没发布的是什么（程序算出的：包含哪几个已完成的需求和已解决的问题；程序自己提交的事实有几个；其他提交），以及挡住发布的事（项目目录里有合并或变基没做完、不在任何分支上、远端比本地新）和要注意的事（有没提交的代码改动，不会被发布）。落后几个只到上次抓取远端为止，加 --fetch 先抓取（有超时，不会问口令）。AI 可以读。
- 哪个需求、哪个修复带来了哪些提交：确认完成和确认修好了合并时，程序把合并提交的编号记在需求文件头的 merge_commit 和修复记录 issues/fixes/F-xxx.json 的 merge_commit 里，合并提交带进来的分支上的提交都算它的。这个功能出现之前完成的，按合并提交的标题（合并需求：……（R-…）、合并修复：……（F-…））找；没有合并的，按完成那个事实提交找。没有上游分支时，「没发布」指不在这个远端任何分支上的提交。
- rf.py publish run [--remote 远端] [--json]：只由用户触发。先把攒着的事实提交，再写好发布记录并提交，然后把当前分支推送到它的上游：不强推、不推标签、不推别的分支（明确写出 本地分支:远端分支，用户的 git 配置也改变不了）。当前分支还没有上游时，只有一个远端就推到它、新建同名分支并设置上游；有好几个远端必须用 --remote 说明；没有远端就拒绝。推送被拒绝（远端有新提交）、没有权限、连不上、推送前的钩子没通过、远端的规则拒绝，都用大白话说明，不会换个办法重试；退出码 10 被拒绝、11 没权限、12 连不上或超时、13 推送前钩子没通过、14 远端拒绝、15 其他；--json 在标准输出给 {ok, code, error, detail}。
- 两边分叉了（本地和远端都有对方没有的提交），发布对话框里有「让 AI 来合并」（「先拉取」因为做不了快进而没成时也有）：先抓取一次、确认还在分叉，再在项目目录里新开一个日常聊天，开场白让 AI 把远端分支合并进当前分支、理解两边再解决冲突（.relayforge/ 下两边的事实都保留、一条记录都不丢）、能跑测试就跑、提交合并，不推送，最后用大白话说清哪些冲突了、怎么解决的。这个聊天能 git merge 和 git commit，照旧不能推送。合并好了回到发布对话框点「检查远端」，不再落后就可以发布。项目目录里有合并没做完时，对话框说明是哪一种没做完（合并、变基、拣选），应用知道是哪个聊天开的就有「回到那个聊天」。
- rf.py publish pull [--json]：只由用户触发。先抓取，再只做快进。做不了快进（本地和远端都有对方没有的提交）就什么都不动、退出码 16，并说明可以点「让 AI 来合并」；程序自己不做合并或变基。
- rf.py publish list [--json]：以前的发布记录，新的在前。
- 发布记录一次发布一个文件：publishes/P-20261118-ab12-分支名.md，文件头 type: publish，标题「包含的需求」「包含的问题」「其他提交」「变更记录」。它在推送之前写好并提交，随这次推送一起出去，所以发布成功之后没有任何新提交，「没发布」的数目是 0。记录里不写「已发布」：是否已发布由程序判断，看写它的那个提交是不是已经在远端分支里。推送没成功时记录留在本地，下一次发布（同一个远端、同一个目标分支）更新同一份、attempts 加一，不会越攒越多。

## 切换分支（rf.py branch）

- 应用左上角项目名称后面是项目主目录的分支。点开列出本地分支，可以按名称筛选；RelayForge 为需求、修复开的分支不列。
- 分支名后面括号里的数，是这个分支待发布到远端的需求数，和右上角「待发布到远端」同一个口径：分支有上游时，它领先上游的提交里带了几个确认完成的需求。没有上游的分支不报数。
- 切换只动项目主目录。需求和修复的工作目录各自签出自己的分支，开着的会话照常继续；之后确认完成时，代码合进项目主目录当时签出的分支。
- 当前分支有待发布的需求时，切换前先问一次；那些需求留在原分支上，等切回来再发布。
- 切换用 git switch，不强制。Git 拒绝时（会覆盖没提交的改动、分支已经在别的工作目录签出、有没做完的合并），当前分支和本地改动原样不动，界面说明原因和 git 的原话。
- 数据外置的项目：分支上如果还提交着旧的 .relayforge/ 目录（记录搬到本机之前的样子），不切过去，以免把本机记录的链接换成旧文件。
- rf.py branch list 谁都能看；rf.py branch switch 只由用户在应用里触发，AI 的会话不切项目主目录的分支。

## 追溯：提交、需求、会话（rf.py trace、rf.py why）
- 需求和修复的工作目录（.worktrees/ 下）里的每一个提交，由 git 自己带上出处，不靠 AI 记得：
  - RelayForge-Requirement: R-20261118-ab12（需求的提交）或 RelayForge-Fix: F-003（修复的提交，这次修复带着的每条问题再有一行 RelayForge-Issue: I-012）；
  - RelayForge-Session: S-20261118-7f3a：做这个提交的会话，编号和 .relayforge/sessions/ 里的文件名一致。
  - 需求确认完成、修复确认修好了的合并提交（在项目主目录里，由程序写）也带需求或修复那几行，不带会话。
  - 这些行不要手工写、也不要删。项目主目录里用户自己的提交不带这些行。
- 怎么做到的（后端 backend/relayforge/sessions/trailers.py 开头有完整的说明）：每个需求或修复的工作目录有自己的 core.hooksPath（git config --worktree，共享配置里 extensions.worktreeConfig 为 true），
  指向它私有目录里的一套钩子。它先原样运行用户自己的同名钩子（用户的钩子照常运行、照常能拦住提交），prepare-commit-msg 再加上面的行：
  git commit -m、--amend、--no-verify、合并、拣选都会走到，不管是哪个工具提交的；已经有同样的行不再加；这一步出任何错都不会让提交失败，最坏是没有这些行。
  开出工作目录时、会话挂上时、应用打开会话时（以前开的工作目录也补上）由程序安装，rf.py trailers install 可以手动补；项目主目录永远不装，不改它的 git 行为。
- 会话编号怎么知道：应用启动会话时放进环境变量 RELAYFORGE_SESSION_ID（实测它能传到 Claude Code 的 Bash 工具运行的命令里），Claude Code 自己的 CLAUDE_CODE_SESSION_ID 是第二选择，都没有就用挂在这个需求或修复下最新的会话。
- rf.py trace R-… | F-… | I-… [--json]：只读，程序算，不调用模型。它的提交（哈希、日期、说明、会话）、改了哪些文件（行数）、挂了哪些会话（和进展文件）、合并提交、有没有发布（和发布用同一个办法：合并提交在不在远端的分支里）。
  认提交的顺序：提交说明里的行；这个功能出现之前完成的，按合并提交的第二个父提交一路上的提交（和发布认「哪个需求带来了哪些提交」是同一个办法）；还没合并的，看它自己的分支。
- rf.py trace --commit 哈希：从一个提交出发，它属于哪个需求或修复，再给出同样的内容；不属于任何一个的说清楚。
- rf.py why 文件[:行|:起-止] [--json]：这个文件（或这几行）最近是哪些提交改的（整个文件用 git log --follow 跟着改名，几行用 git blame -M -C），各属于哪个需求或修复：需求给出标题、需求说明、验收条件、它记下的裁定（带着它的会话出处的，或还在进行中的）、会话和每个会话进展文件的完整路径；修复给出问题的现象和修复报告；不属于任何一个的提交单独列出。带会话出处、本机还有那个会话聊天记录的提交，再给出产生它的那一轮：用户那一轮说了什么，从这一轮里上一个提交到这个提交之间读了什么、跑了什么、改了什么、哪一步失败或被拒绝、同一步失败了几次（最多 12 步，和 history session --steps 同一份数据；按提交号认，输出里没有提交号的按提交标题认，并注明）。输出有上限（最多展开 6 个需求或修复，每项几条）。
- rf.py trace、rf.py why 只读，应用开的每一种会话都预先放行。改一段不知道原因的代码之前，先用 rf.py why 看，再决定怎么改。
- `rf.py usage R-… | F-… | I-… | --session 会话编号 [--json]` 从本机的原始聊天记录或存档统计 token。每次查询一个目标。需求按立项、开发和测试统计，合并前沿用开发会话时计入该会话。问题按自己的排查会话和所在批次的修复会话统计。同批问题共享修复用量。
- 用量按会话种类和模型汇总。输入包括缓存读取及写入，输出包括记录里的输出 token。总数为输入加输出。Claude Code 的同一条回复只计一次，可读取的子代理记录也纳入。Codex 按累计计数的增量统计，只有单次计数的旧记录按单次计数累加。缺少模型时显示「模型未知」，缺少记录或计数时标明缺失。应用预先放行这条只读命令。
- 需求确认完成、修复确认修好了时，程序在完成记录里写这次工作有多少个提交、多少个文件（需求的变更记录一行「改动：N 个提交、M 个文件」；修复记录 F-xxx.json 的 commits 和 files），只写个数，完整的列表用 rf.py trace 现算。
- 应用里：已完成的需求的右边面板和已解决的问题的对话底部，有一小块「改动」：N 个提交、M 个文件（文件列表折叠着）、挂的会话、有没有发布；只读。

## 历史、总结和会话存档（rf.py history、rf.py summarize、rf.py archive）
- 想知道以前怎么做过、为什么这么定，用 rf.py history（只读，程序算，不调用模型，应用开的每一种会话都预先放行）：
  - history search 词… [--tag 标签] [--feature RF-101] [--file 路径] [--kind req|issue|decision|session|test] [--limit N]：在需求（含已完成、已取消）、问题、裁定（含 history/ 里被替代、被否决的）、会话进展、测试集（名称、数据的名称、功能点、来源需求）、总结和标签里查；几个词要同时出现。每条给编号、标题、状态、日期和命中的几行。
  - history show R-… | I-033 | D-0001 | S-… | TS-001：一条的完整摘要：需求说明、要改的功能点、验收条件、总结、标签、相关裁定、提交概况、有哪些会话（本机有没有聊天记录）。
  - history session 会话编号 [--grep 词] [--tail N]：当时的聊天，谁说了什么；工具的输出不放进来，一条消息、整次输出都有长度上限。读的是这台电脑上的存档，没有存档就读 Claude Code 还没清理的原始记录，都没有就说清楚。
  - history session 会话编号 --steps [--grep 词] [--tail N]：同一份记录的步骤视图。用户说一次话是一轮，每轮列出读了哪些文件、跑了哪些命令、改了哪些文件（增删行数）、记了什么进展、哪一步失败或被拒绝、同一步失败了几次、产生了哪些提交、用时和 token；--tail、--grep 按轮算。命令和文件照录（看着像密钥的值遮成 ***），工具的输出仍然不放进来，只看成功还是失败。消息编号和不加 --steps 时一样。
  - `history session 会话编号 --steps --offset 0 --json` 从头分页读取回放。后续页使用结果的 `next_offset`。每页按轮次排列，并标出聊天记录里的程序消息和被拒绝的操作。
  - history session 会话编号 --brief：续接用的简要版，最后 3 轮、每轮最后 8 步、4000 字以内；没有记录时什么也不输出。应用另开一个会话接替同一件事（开发、修复、测试的后续会话）时，把它放在开场白末尾，告诉新会话上次做到哪、卡在哪。
  - 进行中的照规矩标出来（需求还没确认完成、文件头 in_progress、行首〔进行中 R-…〕、〔待确认〕），不作为依据。
- 会话记录另存到本机：Claude Code 的原始聊天记录在 ~/.claude/projects/ 下，会被它自动清理。需求确认完成、放弃，修复合并（问题解决）时，程序把挂在上面的会话（修复还包括它的问题的排查会话）的原始记录连同子代理的记录压缩复制到这台电脑的 ~/.relayforge/archive/项目标识/需求或修复编号/ 下（目录只有自己能读）。它不进仓库：聊天里可能有密钥，体积也大。仓库里只在需求文件头的 archived、archive_missing（修复记录 F-xxx.json 里同名的两项）记会话编号，在变更记录里写一行「会话记录已存到本机：…；原始记录已不在：…」，不写本机路径。复制失败不挡确认完成。rf.py archive sweep 把已经完成、还没存过或后来又聊长了的补存一次，应用打开项目时调用；原始记录已经不在的如实记成「原始记录已不在」。
- 客观标签由程序算，不经模型：需求确认完成时，从需求文件（含完成记录里新增、修改的编号）、它的会话进展（会话文件头的 modules、features）、引用它的会话的裁定、rf.py trace 算出的文件，把编号写进需求文件头的 tags；问题解决时写进问题文件头（只经 rf.py issue 的程序）。改过的文件不写进文件（和完成记录只写个数一样），history search --file 查的时候由 git 现算。
- 总结：需求确认完成以后，应用在后台运行 rf.py summarize R-…（不挡完成）：用和问题初判一样的办法调一次无界面模型，输入是需求文件、它的会话进展、已经记下的裁定、原始聊天里用户说的话和 AI 的文字回复（截断，不带工具输出），一次产出概括标签（文件头 topics）、几句话的总结（「总结」一节，每行出处〔R-…#总结〕；它是对这次工作的概括，不是对产品的陈述，不加〔待确认〕）和聊到了但没记下的决定。
  - 没记下的决定一律是推断：照抽取的老路写成收件箱记录（inbox/，tool 为 summarize），由程序合并成草稿裁定、行首〔待确认〕，出处是那个会话的那条消息〔S-…#n〕，编号接着现有的往下排；用户用 /rf-confirm 或 rf.py confirm 确认、rf.py reject 否决。程序和模型都不确认。提出过的编号记在需求文件头 summary_decisions。
  - 同一个需求再总结一次（应用里的「重新总结」）：替换上次的总结和概括标签，已经记下的、提出过的、被否决过的决定不再提出；变更记录追加一行。
  - 没装模型命令、调用失败或回答不合格时，需求照常是已完成，只是没有总结（应用显示「还没总结」和「重新总结」）。rf.py summarize 和 rf.py archive 是程序用的，不给会话预先放行。

## 导入已有项目（bootstrap）
- 运行 rf.py bootstrap [--json]：程序先读仓库（文件清单、README、依赖文件、入口、大文件开头，不含 .env、密钥和被 git 忽略的文件），再让模型给出产品介绍、模块（带代码路径）和功能点。
- 写入的全是推断：对象 status 为 draft，每条陈述带〔待确认〕，出处统一写〔代码导入#0〕，表示「导入时从代码里读出来的」。模块的 paths 只保留仓库里真实存在的路径。
- 项目里已有模块或功能点时拒绝运行，加 --force 才追加。之后用 rf.py pending 查看，用户确认或否决。

## 会话状态（sessions/，由程序生成）
- 一个会话一个文件，文件名是会话编号；不管会话在哪个工作目录里跑，文件都在项目主目录里。文件头多出 session_id、branch、upto（已经读到第几条消息）、named（名字是用户起的）、ended（结束日期）、modules 和 features（这个会话在动的模块和功能点编号）。
- 二级标题：任务目标、正在处理、计划、方向调整。
- 「计划」和「方向调整」的出处后面带上那条消息的时间，写作〔会话编号#消息序号 @日期 时间〕。
- 「计划」每行以状态开头：[x] 做完、[~] 正在做、[ ] 还没做、[-] 不做了；标题和说明之间用「｜」分隔。
- 平时由会话用 rf.py note 边做边更新；/rf-sync 和 rf.py sync 是事后让另一次模型调用读聊天记录来补的办法。
