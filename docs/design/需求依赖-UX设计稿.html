需求依赖：UX 设计稿

没有需求组，也没有父子需求：每个需求还是普通需求。开发中发现需求太大，就把一部分拆成新的需求，原需求继续完成自己那部分。需求之间可以有「前置需求」：前置需求完成之前，这个需求不能开始开发。程序会说清楚它在等谁，看板上也能看到。

基于 2026-11-21 的界面设计，只是方案，还没有实现。示例沿用演示项目 FlowNote 的需求，示意图按现有界面的布局和配色画。

整条链路

下面用一个连续的例子走一遍：开发「任务截止日期提醒」时，AI 发现「逾期任务的每日汇总」可以独立交付。

① AI 建议拆分→② 同意拆分，调整验收条件→③ 看板上看到依赖→④ 悬停看前后关系→⑤ 打开被挡住的需求→⑥ 拖动被拦住→⑦ 前置需求完成→⑧ 确认立项，自动同步
另外：⑨ 手动添加、去掉前置需求边界 1：前置需求被取消边界 2：原需求等拆出去的需求边界 3：开工同步有冲突规则一览以后

8

确认立项：先把 main 同步进来，再开开发会话你确认程序同步

这个需求的分支是建卡那天从 main 开出来的，里面没有前置需求的代码。所以点「确认立项」后，程序先把 main 的最新内容合进它的分支，再开开发会话。它此时通常还没有自己的提交，直接快进，几乎不花时间。

边界情况

!

边界 1：前置需求被取消

程序不替你决定。被挡住的需求显示红色的「前置需求已取消」，面板里给出两个选择。如果之后又恢复了那个前置需求，一切恢复原样。

立项中
逾期任务的每日汇总✕ 前置需求《任务截止日期提醒》已取消
《任务截止日期提醒》已取消，这个需求等不到它了。
去掉这条依赖 也取消这个需求
!

边界 2：原需求要等拆出去的需求

比如开发 A 时发现「统一的日期工具」要先做，并且别的需求也会用到，于是把它拆成 C，选「当前需求等它」。A 已经在开发中，拦不住它开工，所以改为拦它确认完成：C 合进 main 之后，A 才能完成，合并也就自然按先 C 后 A 的顺序。

!

边界 3：开工时同步 main 有冲突

正常情况下不会遇到：立项阶段不改代码，分支上还没有自己的提交，同步就是快进。如果分支上已经有提交（比如以前开过开发会话），同步可能冲突。这时沿用现在合并时的处理办法：把冲突交给这个需求的开发会话解决，解决完再开工。面板上显示「正在同步 main，会话在处理 2 个冲突文件」。

以后（这次不做）

  • 看板上画连线：需求少的时候直观，需求一多线就会交叉。这一期先用悬停高亮（第 4 步）。
  • 左侧按文件夹归类：把相关的需求放进同一个文件夹，只是归类，和依赖无关，不影响先后，也不改变流程。建议和依赖分开设计：文件夹表示「属于一类」，依赖表示「谁等谁」。
