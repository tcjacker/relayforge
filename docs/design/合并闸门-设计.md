# 合并闸门：合并前在合并后的代码上跑回归

状态：已做（2026-11-23）：`testsets/gate.py`、`flows.py`、`merge.js`、大图上的「设为主干」。来源：对照 Multica 之后定的方向——RelayForge 守「交付流程加项目知识」这一层；这一层里最该先补的是「合进去以后还对不对」没人验。

## 现在的问题

- 点「确认完成」前，应用在需求分支上跑这个需求的测试集（`testsBeforeDone`）。但合并时：
  - 分支落后目标分支、又没有冲突时，`merge_blockers` 在需求的工作目录里自己把目标分支合进来（`sync_target`），然后直接落到主分支。合出来的这份代码谁也没测过。
  - 有冲突时交给 AI 合并，测不测、测哪些靠 AI 自觉。
- 测试范围只看需求「动到的功能点」，依赖这些功能点的功能点（功能点文件头的 `depends_on`）不算。
- 跑全量又太慢：合并队列同一时间只合一个，每个都跑全量，后面的全堵着。

## 做法

### 什么时候、在哪跑

在 `flows.req_done`（修复是 `issue_confirm`）里，`merge_blockers` 之后、`land_branch` 之前。此时需求的工作目录已经包含目标分支的最新提交（必要时程序刚合进来），它的 HEAD 就是合并后的代码。在这个工作目录里跑，不另开目录。

放在后端，应用和命令行走同一条路；合并锁本来就保证同一时间只合一个。

### 跑哪些（回归用例的选择）

按优先级三类，过期的、别的需求进行中的照旧不跑：

1. **本需求的**：它新建的、挂在它名下的、它动到的功能点下已有的测试集（就是现在 `test run --req` 的范围）。
2. **依赖它的**：功能点文件头 `depends_on` 里写着本需求动到的功能点的那些功能点（只往外一层）下的测试集。
3. **主干**：标为主干的用户旅程（旅程文件头 `trunk: true`）上，各步骤用到的功能点下的测试集。主干由用户定（应用里在旅程上点「设为主干」，`rf.py` 里是只由用户触发的命令）；还没有标主干时这一类为空，结果里说明。

**这份代码上测过的不再跑**：测试集最近一次在这个需求（修复）眼里的完整结果，代码指纹（`code_print`）和数据指纹都和现在一样、而且通过了，就直接用那次的结果。分支在确认前刚跑过、合并时目标分支没动过，就几乎不花时间。

**时间预算**：按每个测试集最近一次的耗时估，默认 5 分钟。超了的话第 1 类全跑，然后第 3 类、第 2 类，同一类里最近失败过的、时过时不过的排前面；没排上的列出来，留给全量（`rf.py test run --all`，发布前或者你手动跑）。

### 结果怎么处理

- **都过了**：照常合并。完成记录里写一行：跑了几个（本需求、依赖、主干各几个）、复用了几个、没排上的几个。
- **有失败或跑不起来**：不合并。
  - 先排除「主线上本来就失败」的：同一个测试集最近一次主线（scope main）运行就失败了同样的几条，标为「原来就失败」，不挡合并，写进记录。
  - 其余的交回这个需求（修复）的会话：经收件箱（会话没开着就在后台跑一轮），说清楚哪几个测试集、哪几条、怎么单独重跑（`rf.py test run TS-… --case n`）。它说完一轮以后合并队列自动再试，和现在「合并前的同步」是同一套（交回次数有上限，到了就停下来等你）。
- **准备步骤或构建命令还没经你同意**：不替你执行，合并停下来，提示到应用里同意后再点「重新检查并合并」。
- **你决定跳过**：合并队列里停住的那一项上有「跳过检查，仍然合并」（只由你在应用里点，`req done --skip-gate` 登记为只由用户触发），完成记录里写明跳过了、当时哪些没过。

## 不做的

- 不在合并时跑全量。
- 不另开临时工作目录预演合并（需求的工作目录在 `merge_blockers` 之后已经是合并结果）。
- 不自动标主干：主干是产品判断，由你定。

## 改动的地方

- 后端：`testsets/gate.py`（选范围、复用、预算、跑、判断原来就失败）；`flows.py` 的 `_merge` 和修复的合并接上；`req done` / `issue confirm` 的 `--json` 多一种结果 `gate`；旅程的 `trunk` 字段和设为主干的命令；FORMAT.md。
- 应用：`merge.js` 处理 `gate`（交回会话、停住、跳过）；合并队列的界面显示闸门的结果和「跳过检查」；大图的旅程上「设为主干」。
