# 找回、介入、解释：现状和差距

状态：分析，还没有排期。开工时逐项立项确认。
来源：2026-11-21 的讨论。现状部分按代码整理，没有运行应用核对；和主流产品的对比按对这些产品的一般了解写，没有逐项查证。

这份文档回答三个问题：

1. Agent 能不能找回过去的工作；
2. 用户能不能在执行中介入；
3. 系统能不能解释一次协作究竟发生了什么。

结论：第一、第三个基本能做到，第二个只做到「能在终端里插话」。RelayForge 在「事后查得清为什么这样做」上走得比大多数产品远，主要差在「执行中看得见、拦得住、退得回」。

## 一、找回过去的工作

### 已经有的

- 接着上次的会话继续：每个需求、修复、日常聊天都记着它挂的会话。再打开时，Claude Code 用 `--resume`，Codex 用 `resume` 接上（`app/src/main/sessions.js` 里 `start` 的各分支）。
- 提交带出处：需求和修复的工作目录各有一套 git 钩子。每个提交都带上 `RelayForge-Requirement` / `RelayForge-Fix` / `RelayForge-Issue` / `RelayForge-Session`，不靠 Agent 记得（`backend/relayforge/trailers.py`）。
- Agent 可以自己查：
  - `why 文件[:行]`：这几行最近是哪些提交改的、属于哪个需求或修复，并给出当时的需求说明、验收条件、裁定和会话进展（`backend/relayforge/trace.py`）。
  - `history search / show / session`：查以前的需求、问题、裁定、会话进展和测试集，看当时的聊天（`backend/relayforge/history.py`）。
  - 这两个命令在所有会话里免确认放行（`app/src/main/claude-settings.js` 的 `TRACE_ALLOW`、`HISTORY_ALLOW`）。开场提示也告诉了 Agent 什么时候用（`app/src/main/prompts.js` 的 `WHY_GUIDE`、`HISTORY_GUIDE`）。
- 聊天记录另存：需求完成或放弃、修复合并时，把挂着的会话的原始记录压缩复制到 `~/.relayforge/archive/`。只存在本机，不进仓库。打开项目时会补存漏掉的（`backend/relayforge/archive.py`）。
- 完成后打标签、写总结：客观标签由程序算。概括标签、几句话的总结和「聊到了但没记下的决定」由模型调用一次产出，没记下的决定记成待确认的裁定（`backend/relayforge/summary.py`）。

### 还差的

- 只能按字面查：history 是直接扫文件、按词匹配，不建索引，也没有语义检索。换个说法就可能查不到。
- 要 Agent 自己想起来查：开工时不会自动把相关的历史需求、裁定和踩过的坑放进上下文，全靠提示里的建议。
- 没有回退点：只有 git 提交这一层。Agent 做到一半改坏了，没有办法退回到「第 N 轮对话之前」的代码状态。
- Codex 少一块：Claude Code 每轮结束时会检查「干了活却没记」，后台补记会话进展（`backend/relayforge/hooks.py`、`notes.py` 的 `stop_check`）。Codex 本身也有钩子（Codex CLI 的 hooks，2026-11-22 核实），RelayForge 已经给 Codex 会话接上（`app/src/main/codex-hooks.js`、`rf.py hook codex`）；这几项检查也已经能读 Codex 的聊天记录（`core/transcript.py` 的 `claude_shaped`，2026-11-22）。（更正：这里原先写成「Codex 会话启动时没有对应的机制」，被误读成「Codex 不支持钩子」。）

## 二、执行中介入

### 已经有的

- 会话跑在嵌入的终端里（`app/resources/pty_bridge.py`），用户可以随时插话、按 Esc 打断，权限确认由 CLI 自己弹出。
- 状态提醒：Claude Code 的钩子（`UserPromptSubmit`、`Stop`、`PermissionRequest`、`Notification` 等）报告会话在干活、说完了，还是停下来等你（包括等你批准权限）。应用据此发系统通知、在 Dock 上显示数字（`app/src/main/attention.js`、`backend/relayforge/status.py`）。
- 程序把关的关口：改测试用例、改测试期望、确认问题修好、合并、发布等，Agent 只能提出，要用户在应用里点同意。权限规则里直接拒绝 Agent 自己执行（`claude-settings.js` 的 `REQ_USER_DENY`、`USER_DENY`、`PUBLISH_DENY` 等）。

### 还差的

- 介入只有终端一种方式。没有：
  - 把 Agent 的计划拿出来让你批；
  - 逐个改动审阅、接受或退回；
  - 在看板上暂停一个会话，或者给它改方向；
  - 给正在跑的会话排队补一句话，等它这一轮说完再交给它。
- ~~Codex 看不到「在等你」~~：已解决（2026-11-22）。Codex 会话的钩子（PermissionRequest、Stop、Interrupt 等）报告状态，和 Claude Code 一样能提醒「在等你批准」；钩子没在报状态时（还没信任、旧版 Codex）才退回读聊天记录（`codex-turns.js`）。
- 只能在本机：没有手机或远程查看和批准，人离开电脑，会话就只能停着等。

## 三、解释一次协作

### 已经有的

- `trace R-… | F-… | I-…`：一个需求、修复或问题的提交、改过的文件、挂的会话、合并提交、有没有发布。界面里也能看（`app/src/main/trace.js`）。
- 每条记下的陈述都有出处：`S-…#n`，指到是哪个会话的第几条消息（`backend/relayforge/sessions.py` 的 `here_source`）。
- 进行中的事实和待确认的裁定有明确标记，不会被当成依据（`backend/relayforge/inflight.py`）。
- `history session` 把会话渲染成可读文字，工具调用只列名字和次数。

### 还差的

- 没有一次会话的执行时间线：看不到每一轮调了哪些工具、跑了什么命令、改了什么、结果怎样、哪一步你批准过。`history session` 有意不放工具的输入和输出。
- 没有用量：每个需求、每个会话花了多少 token、多少钱、多长时间，没有记。
- 偏重有提交的工作：放弃的尝试、日常聊天里定下的东西，只能靠「边做边记」和完成时的查漏，解释力弱一些。
- 子代理只能看个大概：子代理的记录随会话一起存档，但没有单独展示它做了什么、交回了什么。

## 四、和主流产品对比

| 能力 | 主流产品的大致情况 | RelayForge |
|---|---|---|
| 接着上次的会话继续 | Claude Code、Codex、Cursor 都有 | 有，而且按需求自动挂好 |
| 回退到某一步之前 | Claude Code 的 `/rewind`、Cursor 的回退点 | 没有 |
| 长期记忆、跨会话检索 | Devin、Windsurf 等有语义化的记忆 | 有，但只能按关键词查 |
| 代码 → 提交 → 会话 → 需求 → 裁定 | 很少有产品打通；Copilot coding agent 只把会话日志挂在 PR 上 | 打通了，全部由程序算，可复查，是长处 |
| 执行过程回放 | Devin 有时间线，Copilot 有会话日志页 | 没有 |
| 结构化介入（批计划、审改动） | Claude Code 的计划模式、Cursor 的改动审阅 | 只能用终端 |
| 后台或云端跑、手机上批准 | Codex 云端任务、Cursor 后台 Agent、Jules | 没有，只在本机 |
| 两种工具一样好用 | — | Codex 也接上了钩子（状态、等批准、执行前拦截、停下来时的检查） |

## 五、建议的先后

1. 会话的执行时间线：按轮次列出用户说了什么、调了哪些工具、改了哪些文件、在哪里等过批准。主要从聊天记录里由程序算出来，不经模型；「等批准」那部分要先补记。给谁看、在哪看、数据从哪来，见第六节。
2. 每轮对话前的代码快照和回退：需求和修复本来就有自己的工作目录，可以在每轮开始时由钩子记一个快照（例如不进分支的 git 引用），时间线上每一轮都能「退回到这之前」。只退代码，聊天不动；退之前给清单，由用户确认。
3. 给 Codex 补齐：「在等你批准」的提醒已经靠 Codex 的钩子做了（2026-11-22）；「这一轮干了活却没记」等停下来时的检查也已经能读 Codex 的聊天记录。
4. 应用里的介入入口：在时间线或看板上给一个暂停、补一句话、换个方向的入口，最后都落到同一个终端会话里，不另起一套。
5. 语义检索和开工时自动带上相关历史：现在按关键词查加上标签已经能用，放最后。做的时候先从「开工时按功能点和文件自动列出相关的历史需求和裁定」开始，这一步不需要模型。

用量统计可以在做时间线时一起做：聊天记录里带有用量，按会话和需求汇总即可。

## 六、会话时间线：给谁看、在哪看

来源：2026-11-21 的讨论。

### 它是什么

把一个会话的每一轮按顺序列出来，不用翻原始聊天就能看懂。每一轮记：

- 用户说了什么；
- Agent 依次读了哪些文件、跑了哪些命令（成功还是失败）、改了哪些文件（增删行数）；
- 在哪里停下来等批准，批准了还是拒绝了，等了多久；
- 记下的进展和裁定；
- 这一轮产生的提交；
- 最后回复的开头几行；
- 这一轮的用时和 token。

子代理折叠成一行，展开看它做了什么、交回了什么。

### 给 AI：查历史时捞出来

AI 不看完整时间线，太长，会占满上下文。它要的是压缩过的过程教训：

- 哪个命令或测试反复失败过，最后怎么解决的；
- 试过又放弃了哪种做法、为什么放弃；
- 用户拒绝过哪一步、当时怎么说的。

做法：

- 给 `history session` 加一种步骤视图（例如 `--steps`）。
- `why` 指到某个提交时，顺带给出产生它的那一轮的步骤摘要。
- 和现有的 `why` / `history` 一样，由程序算、只读、所有会话里免确认放行，不用改界面。
- 续接会话时，把上一个会话最后几轮的步骤摘要放进开场提示，让 Agent 知道上次做到哪、卡在哪。

### 给人：主要是事后复盘

会话还在跑时，终端里本来就实时显示它在做什么，时间线这时的价值不大，最多是帮忙发现原地打转（比如同一个测试连着失败好几次）。真正缺的是事后：会话结束、终端关了以后，中间过程就看不到了。

所以人看的入口放在已有的「改动」块里（`app/src/renderer/scripts/trace.js`），不放在正在跑的终端旁边：

- 已完成的需求，右边面板的「改动」块里，每个会话可以点开看它的时间线：一轮一行，点开才看步骤。
- 每个提交可以点，跳到产生它的那一轮。
- 已解决的问题，对话底部的「改动」块同样处理，修复会话也能点开。
- 进行中的需求也给同样的入口，用来回看前几个会话做了什么。

人也可以不等界面，直接在聊天里让 AI 用上面的命令查了讲给自己听。

### 数据从哪来

- 聊天记录（Claude Code 和 Codex 的 `.jsonl`）：每次工具调用的输入、结果、时间和 token 用量都有。读了什么、跑了什么、改了什么、失败、回复、用量，都能由程序算出来。需求完成后这些记录已经另存到本机（`archive.py`），会话原始记录被清理了也能用。
- 等批准：现在没有长期记录。钩子事件（`backend/relayforge/status.py`）只给提醒用，判断成「在干活 / 等你」写进 EVENTS，状态文件 24 小时后清掉。聊天记录里能看出拒绝过哪一步，看不出批准过哪一步、等了多久。要上时间线，得先把「等批准、批准、拒绝」按会话长期记下来。
- Codex：聊天记录里有每一轮的开始和结束，等批准目前读不到，和第二节说的是同一个缺口。

### 先后

1. AI 用的步骤视图（命令）：不改界面，马上能用。已做（2026-11-21）：`rf.py history session 会话编号 --steps`，开场提示里也提到了。`why` 顺带给出产生每个提交的那一轮的步骤摘要（从这一轮上一个提交到这个提交之间的步骤），也已做。另开开发、修复、测试的后续会话时，开场白末尾自动带上上一个会话最后 3 轮的步骤（`history session 会话编号 --brief`），也已做；接着原来的会话聊（`--resume`）时它本来就有完整的聊天，不带。
2. 「改动」块里给人的入口：复用同一份数据。
3. 补记批准事件，让「等批准、批准、拒绝」出现在时间线上。

前两步只靠聊天记录就能做，不依赖第 3 步。
