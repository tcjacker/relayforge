现状部分按代码整理（`app/src/main/sessions.js`、`testing.js`、`testsets.js`、`issues.js`、`splits.js`、`merge.js`、`attention.js`、`backend/relayforge/requirements/`），CLI 的能力按本机 `claude --help`、`codex exec --help` 和公开资料整理，标了「待核实」的要先试过再开工。

## 先说明两点

- **同一个需求内部不能拆成多个子任务并行**：这不算短板。设计上就是交给 Claude Code、Codex 自带的子代理去拆，RelayForge 不另起会话。
  需求层面的先后和拆分已经有了：
  - 前置需求（需求文件头的 `depends_on`，只由用户设置）：前置需求没完成，这个需求不能离开「立项中」；已经开始开发的，前置需求没完成就不能确认完成（`requirements/record.py` 的「前置需求」一节）。看板上能看到谁在等谁。
  - 拆分建议（`requirements/splits.py`）：会话提出拆分时写清每条和来源需求的先后（after / before / none）、几条之间谁等谁（`#序号`）、从来源需求接走哪条前置需求（takes），以及每条先后要用到对方的什么（needs）。用户同意以后程序建需求、设依赖。
- **只在本机单进程运行**：这是设计目标（一个人自己用的轻量应用），不改。

剩下两件要做：程序和会话之间的通道，以及需求之间的冲突要更早发现。

## 一、程序和会话之间的通道

状态（2026-11-23）：第 5 步的「程序消息」面板已实现，涵盖开发、测试、修复、排查和日常聊天。超时重送、提醒以及将投递时间记入会话后台记录仍待实现。

### 现状

会话之间不直接说话，所有交接都由程序转。程序往会话里交东西只有两种方式：

1. 会话没开着：作为开场白的最后一段（`sessions.open` 的 `say`）。
2. 会话开着：`sessions.type()` 往伪终端里「粘贴」一段文字，300 毫秒后补一个回车。

用到第 2 种的地方：

| 谁发 | 发什么 | 代码 |
|---|---|---|
| 测试阶段 | 再测一轮（测试会话）；测试交回的问题清单（开发会话） | `testing.js` 的 `kick`、`tell` |
| 测试集 | 用户不同意 AI 对测试数据的改动 | `testsets.js` 的 `tell`、`tellReject` |
| 问题 | 用户在问题里补充的话；退回修复「还有问题」 | `issues.js` |
| 拆分 | 用户同意拆分后的回执和先后 | `splits.js` 的 `approve` |
| 合并 | 同步目标分支、解决冲突的说明 | `merge.js` 交给界面，界面打开会话时作为第一句 |

会话的状态：Claude Code 由钩子报告（`rf.py hook event` 写进 EVENTS，`attention.js` 读出 running / waiting(reply|answer|approve) / idle）；Codex 没有钩子，从它的聊天记录里读这一轮开始、完成、中断（`codex-turns.js`）。

### 问题

1. **输入时不看对方在干什么**。`type()` 不管会话是在干活、在问用户问题，还是停在权限确认框上。停在确认框上时，粘贴进去的文字和回车可能被当成对确认框的回答。
2. **没有回执**。送没送到、对方有没有读到，程序不知道。只有测试阶段用需求文件头记了「这一轮的结论交出去了」（`test-kicked` / `test-told`），其余几处应用一重启，在途的就丢了。
3. **不标来源**。程序发的话和用户打的字在会话看来一样，有几处还用用户的口吻写（「我点了确认完成」）。会话分不清哪些是用户的指示、哪些是程序的通知。
4. **两种 CLI 原先不对等**：RelayForge 没给 Codex 接钩子，读不到「在等批准」。（更正，2026-11-22：Codex 有同名的钩子，已经接上，见 `app/src/main/codex-hooks.js`。）
5. **依赖终端的细节**：括号粘贴、回车的时机，CLI 的界面一改就可能出错。

### 目标

- 程序发给会话的每一句话：有记录、标来源、只在对方能收的时候送、送到了有回执、应用重启不丢、同一件事不重复发。
- 终端照旧是主界面：用户随时能直接看、直接插话。不自己重写聊天界面。
- 两种 CLI 尽量对等；做不到的地方写清楚降级成什么。

### 设计

#### 1. 统一的会话状态

新增一个只读的「会话现在在干什么」（主进程里一个函数，按 `run` 给出）：

| 状态 | Claude Code 从哪来 | Codex 从哪来 |
|---|---|---|
| `running` 在干活 | 钩子：UserPromptSubmit、PostToolUse… | 钩子：UserPromptSubmit、PostToolUse（没信任时退回聊天记录的 `task_started`） |
| `reply` 说完了，等用户 | 钩子：Stop | 钩子：Stop（同上，退回 `task_complete`） |
| `answer` 在问用户问题 | 钩子：Notification / 问用户的工具 | 钩子：Stop 时最后一句是问句 |
| `approve` 在等权限确认 | 钩子：PermissionRequest | 钩子：PermissionRequest（已实测） |
| `exited` 已退出 | 进程退出 | 进程退出；按 Esc 打断是钩子 Interrupt |

带上进入这个状态的时间。收件箱、后台记录、以后的「卡住提醒」都只看这一个地方，不再各自读 EVENTS。

#### 2. 会话收件箱：程序发话的唯一出口

新增 `app/src/main/inbox.js`，上面表格里所有直接调 `type()` 和「作为第一句」的地方都改成 `inbox.post()`。`type()` 只留给用户在终端里打字（`input`）。

一条消息：

```json
{ "id": "m-…", "to": "R-1 或 test:R-1 或 fix:F-3", "session": "会话 ID（发出时已知就填）",
  "from": "testing | merge | issues | testsets | splits", "key": "去重用，如 test-told:R-1:3",
  "text": "…", "created": "…", "state": "queued | sent | seen | dropped", "sent": "…", "seen": "…" }
```

- 存在本机：`~/.relayforge/inbox/项目/messages.json`，写法和合并队列一样（先写临时文件再改名）。应用重启后照样投递。
- `key` 相同的只留一条。测试阶段现在的 `busy` 集合和「重启不重发」靠它统一解决（需求文件头的 `test-kicked` / `test-told` 继续保留，它们是给界面和 rf.py 看的阶段记录）。
- 每条话前面加来源：「〔RelayForge 程序 · 测试结论〕……」。所有会话的开场白里加一句：带这种标记的是程序转来的通知，不是用户的指示，不能当作用户同意了什么。原来用用户口吻写的文字一并改掉。

#### 3. 什么时候送

| 对方的状态 | 做法 |
|---|---|
| `reply` | 马上送 |
| `running` | 排队，等这一轮说完（变成 `reply`）再送 |
| `answer` | 不送。它在等用户回答问题，程序的话会被当成回答。排队，并在界面上提示「有一条程序消息等它回答完你的问题再送」 |
| `approve` | 绝不送，排队 |
| 没开着 | 排队；用户打开它（或程序按现有规则在后台打开它）时，作为开场白的最后一段一起送 |
| 已退出 | 同「没开着」 |

同一个会话一次只送一条：送出去以后等它这一轮说完，再送下一条。多条排队的合成一段，按先后列出。

#### 4. 怎么送

**Claude Code：用钩子送，不往终端里粘贴正文。**

- 会话这一轮说完时，Stop 钩子本来就是同步的（`rf.py hook event`，现在用它做「这一轮干了活却没记」的检查）。在这里加一步：读这个会话在收件箱里排着的消息；有的话返回 `{"decision": "block", "reason": "〔RelayForge 程序 · …〕……"}`，Claude Code 会把 reason 交给模型、接着干活。这样消息不经过终端输入，不会撞上权限确认框，也不依赖粘贴和回车。
  - 钩子是 rf.py，收件箱由应用写。钩子读文件即可（只读），送出去的结果由应用从聊天记录里核对（见下面的回执）。
  - 和现有的检查合在一起：几道检查和收件箱的消息一起放进同一个 reason。
  - 防止来回打转：Claude Code 在被拦过一次之后的下一次 Stop 会带上 `stop_hook_active`。收件箱不因此不送，但同一条消息只送一次（按 id），一次 Stop 链里最多送一批。
- 会话早就说完了、正停着等用户（Stop 已经过去了）：只往终端里输一行固定的短句「〔RelayForge〕有 1 条新消息」并回车，把它唤醒；UserPromptSubmit 钩子看到这一句，用 `additionalContext` 把消息正文带进去。终端里只输固定短句，正文走钩子。
  - 待核实：UserPromptSubmit 钩子的 `additionalContext` 在当前版本里是否交给模型、在聊天记录里怎么落。

**Codex：和 Claude Code 一样用钩子送。**（更正，2026-11-22 实测）

- Stop 钩子返回 `{"decision": "block", "reason": …}`，Codex 把 reason 当作接着做的提示，下一次 Stop 带 `stop_hook_active: true`。
- UserPromptSubmit 钩子返回 `hookSpecificOutput.additionalContext`，模型能拿到。
- 实测里模型会自己掂量钩子交来的话：reason 里写「再执行某条命令」，它看到了但判断不是用户的指示，没有照做。所以程序消息要写成通知（发生了什么、你可以怎么做），不要写成命令。
- 钩子还没被信任、或者旧版 Codex 没有钩子时，退回往终端里输：只在这一轮已经完成后送。

#### 5. 回执

两种 CLI 都会把收到的话写进聊天记录（Claude Code 的钩子反馈和用户消息、Codex 的用户消息）。每条消息的标记里带上它的 id（例如「〔RelayForge 程序 · 测试结论 · m-3f2a〕」），应用读聊天记录看到这个 id，就把它标成 `seen`。

- 送出去 2 分钟还没看到：再看一次会话状态，能送就重送一次，还不行就在界面上提醒用户。
- 会话旁的「程序消息」面板列出来源、入队时间、状态、送出方式和正文。长正文单独折叠，排队时会话标签或列表项有黄点。用户可在面板撤回仍在排队的消息，撤回后保留记录。
- 后台记录也把每条消息的 id 和送达时间记进那一轮（待实现）。

#### 6. 迁移顺序

1. 统一会话状态；`type()` 先加一道闸：对方在 `approve` / `answer` 时不送，改为排队。这一步就消除了「打进权限确认框」的风险。
2. 收件箱（存储、去重、来源标记、开场白里的说明），把表格里五处改成 `inbox.post()`。
3. Claude Code 的 Stop 钩子送达和回执。
4. Codex 用同一套钩子送达（钩子已接上）。
5. 界面：会话面板上的「程序消息」。

### 第二阶段（可选）：无人值守的会话改用无界面模式

有一类会话本来就不需要人盯着：测试会话「再测一轮」、合并前的同步、以后的后台修复。它们可以不开终端，用结构化的方式跑，事件和审批都变成程序能直接处理的数据：

- Claude Code：`--bg` 在后台开会话（本机 `claude --help` 里有：`claude agents` 列出、`claude attach` 接上、`claude logs` 看输出、`claude stop` 停），或者 `-p --input-format stream-json --output-format stream-json` 一问一答地跑，同一个会话 ID 用 `--resume` 接着聊。
- Codex 用 `codex app-server --listen stdio://`。协议经 Codex CLI 0.171.0 的 `app-server generate-json-schema` 核实，模型、工作目录、沙箱和审批策略随线程传入。

用户点开这样的会话时可看到过程，点「在终端里接管」后用同一个会话 ID 以交互模式接上。

这一步改动大，而且会丢掉「随时在终端里看着它干活」，所以放在第一阶段之后，只用在无人值守的那几类会话上，开发会话和立项会话不变。

做成的样子（2026-11-22）：

- 哪些会话：测试会话的再测一轮（收件箱发给没开着的 `test:` 会话）、合并前的同步（会话没开着时）、问题的修复会话（开始修复时，和以后发给没开着的 `fix:` 会话的话）。会话开着时照旧经收件箱，不改成后台。第一次的测试会话、开发会话、立项会话、排查会话不变。
- 怎么跑：和交互会话同一套参数和开场白，Claude Code 加 `-p --output-format stream-json --verbose`，Codex 经 `initialize` / `initialized` 握手，再用 `thread/start` 或 `thread/resume` 和 `turn/start`，聊天记录沿用原生线程编号。输出整理成一行一行的过程（说了什么、跑了什么命令、哪一步出错），点开这个会话时先看到它做到哪了；它在跑时终端不收键盘。已信任的钩子照常运行，负责状态、执行前守卫和停下来时的检查。
- 这一轮结束：钩子报过「说完了 / 在问你」的以钩子为准，钩子不能用时看最后一句是不是问句；按会话停下来通知原来的流程（合并重试、测试阶段……），进程退出时不再报第二次。说完了而收件箱里还有没交出去的话，就带着它们再跑一轮。
- 要人确认（human-in-the-loop）：
  - Claude Code 要你批准时，PermissionRequest 钩子在无界面会话里（环境变量 `RELAYFORGE_HEADLESS`、`RELAYFORGE_APPROVALS`）把请求写成 `~/.relayforge/approvals/<项目>/<编号>.json` 等着（`core/approvals.py`），应用每 1.5 秒读一次，右下角出卡片、弹系统通知；你点批准或拒绝，写回 `<编号>.decision`，钩子把决定交给 CLI。等 50 分钟没人理就按拒绝回答，告诉会话写清楚要做什么、停下来等用户。钩子的超时设成 3600 秒。实测：Claude Code 在 `-p` 模式下会触发这个钩子，批准以后命令照常执行。
  - 在问你时，卡片显示问题和回复框。Codex 运行中可用 `turn/steer` 插话，或直接回答它发来的问题请求。一轮已经结束时用你的话在后台再跑一轮。
  - 在终端里接管时，先拒绝等待中的批准。Codex 的 app-server 进程树关闭后，再用交互终端继续原线程。
- Codex 把命令、文件修改和权限的批准请求交给同一张卡，按 RPC 请求编号返回用户的决定。审批策略照设置里的「无界面会话的审批」：自动用 `never`，根本不能申请越出沙箱；「每次问我」用 `on-request`，越界时申请、由你本人批准。
- 后台 Codex 的收件箱消息通过 `turn/steer` 发送，收到 RPC 回执才标为送出。等待批准或回答、或者这一轮已结束时先排队，也可以随下一轮送出。

### 风险

- Stop 钩子送达的语义：Claude Code 把 reason 当作钩子的反馈交给模型，模型是否会把它当成用户指示，要靠来源标记和开场白里的说明来约束；需要实测几种消息（问题清单、同步合并、不同意改动）。
- CLI 升级可能改变钩子输出的格式或聊天记录的格式：回执和状态读取都要有「读不出来就降级」的路径，降级到现在的做法并提醒用户。
- 收件箱和需求文件头的阶段标记是两套记录，要写清楚：阶段标记决定「该不该发」，收件箱决定「发出去没有」。

## 二、需求之间的冲突：从合并时发现，提前到开发时发现

### 现状

- 已知的先后（谁要用到谁的结果）由前置需求和拆分建议处理，用户决定。
- 两个互不依赖、同时在做的需求改到同一处，要到第二个确认完成、进合并队列、同步目标分支时才发现；冲突交给它的开发会话去解决（`merge.js`）。
- 只看得到文字上的冲突。各自测试都通过、合在一起才坏的情况，靠合并后会话自己跑测试兜底，程序不核对结果。

### 设计：三层，都由程序算，不调用模型

#### 第 1 层：改动重叠（便宜，随时算）

对每个进行中的需求和修复（有自己工作目录的）：

- 已提交的改动：`git diff --name-only <它和主分支的合并基点>..<它的分支>`
- 还没提交的：在它的工作目录里 `git status --porcelain`

两两求交集，得到「R-A 和 R-B 都改了 `app/src/main/sessions.js`」。

什么时候算：会话说完一轮时（`attention.onSettled`）、有提交时、主分支前进时（有需求或修复合并了），去抖 10 秒，在后台跑。

#### 第 2 层：预演合并（真冲突）

本机 git 是 2.50，支持 `git merge-tree --write-tree --name-only A B`：不碰任何工作目录，直接算出 A 和 B 合并的结果、有没有冲突、冲突在哪些文件。

- **每个进行中的分支对主分支**：主分支一前进就算一遍。会冲突的，标上「需要同步」。
- **重叠的两个分支之间**：只对第 1 层发现有重叠的那几对算，看它们彼此合并会不会冲突。

只覆盖已提交的改动；还没提交的部分由第 1 层的文件重叠提示。

#### 第 3 层：立项时预测（最早）

功能点没有记文件，但历史里有：提交带着需求编号，需求写着要改哪些功能点。所以：

- 这个需求要改的功能点 → 以前改过这些功能点的需求 → 它们的提交改过哪些文件（`trace` 已经能算）→ 预计会动到的文件。
- 和其他进行中的需求实际改的文件、预计会动的文件比对。

在两个时点给出：用户点「确认立项」时，以及开发会话开工时。只是提示，用户决定。

### 发现以后怎么办

程序只提示和建议，不自动改依赖、不自动改代码。

| 发现了什么 | 做法 |
|---|---|
| 主分支前进后，某个进行中的分支和它会冲突 | 通过收件箱告诉这个需求的开发会话（它这一轮说完时送）：「主分支刚合进了 R-B，和你在 `x.js`、`y.js` 上冲突，先把主分支合并进来、解决冲突、跑测试再继续」。也就是把合并时才做的同步提前，冲突还小的时候就解决 |
| 两个进行中的需求改了同一个文件，但还不冲突 | 看板卡片上标出「和 R-B 都在改 `x.js`」；开发会话开工和每次说完一轮时，收件箱里给它一句提醒（只送一次，文件集合变了再送） |
| 两个进行中的需求彼此会冲突 | 看板上标红；建议用户：让其中一个等另一个（设成前置需求，现有功能），或者先把其中一个做完合并 |
| 立项时预测会撞上进行中的需求 | 立项确认框里列出来；建议设前置需求，或者在立项里把会撞上的部分拆出去（现有的拆分建议） |

### 合在一起才坏的情况（语义冲突）

文字上不冲突、各自测试都通过、合并后才坏，前两层查不出来。现有的兜底是合并时让会话跑测试。可以加强一步：合并队列在合并前，用 `git merge-tree` 预演出的结果建一个临时工作目录，由程序跑一遍项目的测试和这个需求的测试集，结果交给用户确认；失败就退回开发会话。这一步成本高（每次合并都要装依赖、跑测试），单独立项讨论。

### 成本和边界

- 进行中的需求通常只有几个，第 1、2 层每次是几次 git 命令，在后台跑，去抖。
- 只看有自己工作目录的需求和修复；立项中的需求只参与第 3 层。
- 结果只存在内存里，随时可以重算；界面上的标记和收件箱的提醒是唯一的输出。

### 迁移顺序

1. 第 1 层和第 2 层的计算（主进程一个模块，`git merge-tree` 和 `git diff`），看板和需求面板上显示。
2. 主分支前进后提前同步：通过收件箱告诉会冲突的开发会话（依赖第一部分的收件箱）。
3. 第 3 层：立项确认时的预测提示。
4. （单独讨论）合并前由程序在预演结果上跑测试。
