# 测试与验收：设计思考

状态：讨论稿。「问题」功能已合进主线；2026-11-18 对齐了做法和先后（见第〇节），先出交互稿给用户确认，再开工。
来源：2026-11-17 的讨论。标「已定」的是讨论中明确说定的，标「建议」的是整理时补上的，开工立项时需要逐条确认。

## 〇、2026-11-18 对齐后的调整（和后文不一致时以这一节为准）

以下都是用户在 2026-11-18 明确同意的。

1. **需求的验证在需求自己的验收会话里做。** 点「去验证」是在这个需求下面另开一个验收会话（和立项、开发并列），不再跳到测试页。右侧面板列出验收条件、对应的用例、每条的结果。
2. **验收会话不改代码。** 它跑用例、解释失败、陪人逐条试；发现不对，把那一段交回开发会话去修。
3. **用例由程序执行，不靠模型。** 验收会话只是调用执行命令并解读结果。
4. **测试页（左边导航的一个页）管全局用例的维护和执行**，对着主线：全部用例按功能点排列，整套跑或单个跑，看历史结果，清理没价值的。需求没完成前，它带来的用例标「进行中」，确认完成后才进入全局用例。
5. **AI 写的测试统一登记。** 程序自动找出项目里所有测试，没登记的列出来；Agent 写测试时必须登记测试目标和关联的功能点，一轮里写了测试却没登记，结束检查会拦住；人在测试页标「留」或「不要」，标了不要的交给一个会话去删或替换。
6. **多一个价值信号**：某个功能点出了问题，而它的用例当时全都通过，说明这些用例没有保护到，标出来。
7. **逐条结果**：第一版支持 Python 的 unittest、pytest 和 Node 自带测试的逐条结果，其他框架先按整套算。
8. **全局用例什么时候跑**：以人手动点为主；另外在人点「确认完成」之前，程序自动跑一遍这个需求涉及的功能点的用例，跑不过就提示，但不拦。
9. **先后顺序改了**（替代第十三节的表）：

| 顺序 | 内容 | 做完能用到什么 |
|---|---|---|
| 1 | 用例登记和测试页 | 看到项目里全部测试、每条的目标和结果，能跑、能标留或不要 |
| 2 | 需求的验收会话 | 「去验证」开验收会话，逐条对验收条件，不对就交回，留证据，手动放行 |
| 3 | 后端接口测试和环境 | 启动服务、接口列表、发请求、存成用例、密钥 |
| 4 | 接进问题 | 修复时先存重现用例，固定检查失败一键记成问题 |

   原因：用户日常用的项目（RelayForge 自己）不是后端服务，先做接口测试自己用不上；而登记和验收会话不依赖接口测试。

10. **用例是数据，不是代码（用户提出并确认）。** 单元测试和接口测试用同一种结构化的用例文件：准备和入参、调用（函数或请求）、校验。一条一个文件，统一放在 `.relayforge/tests/`。程序的执行器读用例、调用目标、拿到真实返回、逐条比对、写下运行过程；界面读的是同一份文件和运行记录。
    - 剩一薄层代码：「先有三张账单」这类准备动作写成有名字的代码，用例里按名字引用并传参数。（用户同意）
    - 校验只用固定的几种（等于、包含、条数、开头是、不为空、报出错误等），不允许自定义判断代码；表达不了的，AI 说明原因后才能写普通的代码测试。
    - 执行器第一版做 Python、Node、Java。（用户定）
    - 项目原来的测试命令也要能跑到这些用例：程序生成桥接文件。
    - 已有的旧测试不动，归到「旧式测试」，只显示代码和通过或失败；以后按需请 AI 改写。（用户同意）
    - AI 的规矩：新测试一律写成这种用例；写了普通代码测试却没说明原因，结束时被拦住。
    - 这一条替代第六节「代码里的测试：登记它在哪」的做法，也替代上面第 5、7 条里关于登记和逐条识别的说法。
11. **用例分类型并标明要不要启动**：单元测试（不用启动）、接口测试（要启动服务）、页面测试（要启动服务和浏览器）、手动检查（人来做）、旧式测试。
12. **每次运行留下执行过程**，界面按步骤展示：入参 → 调用或请求 → 得到的返回 → 逐条校验的期望和实际 → 结论和判定规则。
13. **「有提示」只用程序能算的固定规则**，不用 AI 判断：旧式测试、没对应验收条件、从没失败过、没拦住问题、时过时不过。
14. **验收分两层**：程序跑这个需求的全部自动用例（需要时用需求的代码启动服务）；然后服务开着，人自己试，逐条点通过或这里不对。没有自动用例的验收条件写成手动检查的步骤。前端靠页面测试加人在浏览器里试；Mac 和手机应用只有单元测试能自动，由程序启动、人按手动检查的步骤操作。

15. **2026-11-18 用户重新定了整体结构（和上面第 1、4、10、11、12、14 条不一致时以这一条为准）：**
    - **测试集**：需求进入验证环节时，AI 按需求生成测试集。一个测试集 = 一份测试数据（JSON，每条有名称、输入、期望输出）+ 一段只负责读数据和调用的测试代码。
    - **在需求里**：能看到这个需求用了哪些测试集；点开看完整的数据；运行后看到每个测试集、每条数据的结果，效果接近刷题网站跑代码（输入、期望输出、实际输出，失败的标出来并说明为什么）。关掉后能看到分析：哪些过了、哪些没过、为什么。
    - **测试页**：做测试集的管理和维护。每个测试集挂在哪个需求下面，可以改；用户可以手动改测试集里的数据，也可以让 AI 再生成别的类型的数据。
    - 以上是单元测试这一层。
    - **人工验收**：单独的一页，把整个服务跑起来。后端用类似 Postman 的方式发真实请求；前端在嵌入的页面里直接操作、把流程走通；前后端都有时在同一页走通，并采集对应的日志。

16. **2026-11-18 用户确认和补充：**
    - 不做单独的验收会话；验收时有问题回开发会话问。
    - 测试集同时挂需求和功能点，需求完成后留在功能点下面。
    - 先做测试集（第 1 项），再做人工验收的后端部分，然后是页面嵌入和联调。
    - 「让 AI 改测试数据」放在测试集查看器的一个标签页里，用对话驱动。
    - 测试页分三块：测试集管理、人工测试（和需求里的人工验收同一套界面，不绑需求）、测试环境。
    - 测试环境：用户可以设置并选择测试环境（启动命令、端口、环境变量、数据库和第三方服务的地址、测试用的登录身份）；保密的值只存本机。
    - 测试环境里要有外部依赖：这个项目要连哪些数据库和外部服务。地址默认从用户项目里自己的配置文件（比如本地的 YAML）读出来显示，并检查能不能连上；配置文件照旧由用户维护，不要求在工具里重填。
    - 接口说明由 AI 读代码生成说明文件，并且要有刷新能力：随时让 AI 重新读代码生成。

17. **数据量大和测试集过期（2026-11-18 用户同意）：**
    - 数据多时只让人看需要看的：比例条加数字；需求面板只列有失败或有新数据的测试集，其余收成一行；查看器默认只显示需要看的（失败、跑不起来、AI 新加的），按正常、边界、异常分组，可搜索；测试页按功能点分组，默认筛选「需要看的」。
    - 从源头控制数量：每条数据要写明覆盖哪种情况；程序拒绝输入完全相同的重复数据；测试集按「一种行为一个」来分。
    - 需求动到某个功能点时，它已有的测试集在验证环节一起跑。旧测试集里失败的，开发会话逐条归类：需求有意改了行为，还是改坏了。
    - **AI 改动已有数据的期望要用户逐条确认**：程序单独列出旧值、新值和理由；新加数据不用确认。改动在需求完成前是进行中的，主线上的旧数据不变。
    - 结果分三种：通过、失败（跑了但结果不对）、跑不起来（测试代码出错，没执行到）。
    - 功能点下线或被替代时，它的测试集自动标成过期：不再运行、不删除；也可以手动标成过期或恢复。

18. **人工测试的通用请求设置（2026-11-18 用户提出）：** 测试环境里可以设置通用的请求头和地址参数，以及发请求之前（pre-request）和收到返回之后（after-request）注入的 JS 脚本。发请求的界面要能看到这次自动带上了什么。建议的做法：脚本能读写环境变量、改这次请求、读返回、再发别的请求；在隔离环境里运行，碰不到本机文件；保密的值只存本机；每个接口还可以有自己的请求头、参数和脚本。属于第 2 项。

19. **兼容 Postman 的导入（2026-11-18 用户定）：** 能导入 Postman 导出的集合文件和环境文件。集合里的请求变成存下来的接口用例，文件夹保留成分组；环境里的变量变成一套测试环境的变量，标了 secret 的只存本机；pre-request 和 tests 脚本一起导入。脚本的写法兼容 Postman 常用的 `pm.*`（environment / variables、request、response、sendRequest、test / expect 的常用部分），用到不支持的写法时逐条列出，不静默忽略。导入前先给用户看会新增什么。属于第 2 项。

20. **测试用户的信息要能编辑、要能绑定用户编号（2026-11-18 用户提出）：** 测试环境里的每个测试用户带一组键值，键名由用户自己起（jwt、uid、aid、talent_id、tenant_id 等，不固定叫 user id），值都可以直接编辑。JWT 可以粘贴修改，界面显示解出来的内容和过期时间。通用请求头里用 `{{user.键名}}` 引用当前选的用户的值；发请求时选「以谁的身份」，这些请求头跟着变。保密的值只存本机。属于第 2 项。

21. **引入 Agent 做衔接（2026-11-18 用户提出并确认）：** 不假设测试环境一上来就齐全。原则：Agent 负责把路打通一次，程序负责以后每次照着跑。
    - Agent 介入的地方：第一次准备环境（装依赖、编译、试出启动命令和类路径）；测试集跑不起来时的「让 AI 来处理」；人工验收启动服务失败时；本机缺数据库等依赖时帮忙在本机起一个。
    - 程序仍然自己做：每次运行测试、比对结果、记录过程，不经过模型。
    - Agent 打通后把做法存成这套环境的「准备步骤」，下次程序直接照着执行；步骤失效了才再叫 Agent。
    - 限制：项目目录内的安装（装依赖、编译）预先放行；**系统级的安装（装 JDK、起 Docker 容器、改系统配置）每次都要用户点同意**；密钥 Agent 不读不填；它改环境设置只能提建议，用户采纳才生效。
22. **测试集界面的三点（2026-11-18 用户确认）：** 测试页的「需要看的」算上「有改动等你确认」的测试集；用户点「不同意，这是改坏了」时程序自动把这句话交回开发会话；AI 新加的数据必须点「看过了」按钮才算看过，点开不算。

23. **单独的测试阶段和测试会话（2026-11-19 用户确认，替代第 16 条里「不做单独的验收会话」中关于测试的部分）：**
    - 阶段变成：立项中 → 进行中 → 测试中 → 待验收 → 已完成。
    - 测试会话是独立的会话，没参与开发，只拿着验收条件：把验收条件逐条归类（能用数据验证 / 要看界面）；能用数据验证的写测试集、运行、写分析；要看界面的写成人工验收的检查步骤，**不为了覆盖验收条件去凑测试集**（只有一条数据、或只断言「返回了东西」的不该建）；把动到的功能点的旧测试集一起跑并归类失败；环境没准备好时负责打通并以建议交回。
    - 测试会话不改产品代码，只写测试数据和接入代码；发现问题交回开发会话，需求退回进行中，修完再进测试中。
    - 可以跳过：用户点「跳过测试，直接验收」，记录里如实写。全部验收条件都要看界面时，测试会话只写检查步骤，直接进入待验收。
    - 进入测试之后，开发会话改测试会话写的数据要用户确认（和改旧数据一样）。
    - 先不做「先写测试再开发」。
24. **本地应用的验收（2026-11-19 用户确认）：** 桌面应用类型的项目，人工验收是从这个需求的工作目录启动应用，人自己操作；界面改动不写单元测试。验收用的窗口默认用单独的数据目录、打开演示项目或临时副本，不碰真实项目，可选「用当前项目的只读副本」；窗口标题标明是验收用。替换现在的「跑起来让我验收」。排在后端接口和 Postman 之前做。
25. **安全补强（2026-11-19 用户确认）：** 测试集的构建命令第一次执行前也要用户同意；只由用户触发的命令全部由程序自己校验（不只靠会话的权限规则）。

26. **测试阶段的四点（2026-11-19 用户确认）：** 测试会话交回结论前必须每条验收条件都归了类、看界面的都有检查步骤（保留）；开发会话新建测试集每次问用户，不彻底禁止（保持）；计划做完自动进测试中要在变更记录里写一行（待做）；会话的身份改成应用发给每个会话的签名，不再只靠环境变量里的会话编号（待做，和第 25 条的安全补强一起做）。

27. **人工验收的四点（2026-11-19 用户确认和补充）：** 在左边换到别的需求时已启动的服务不停（切换项目、退出应用、确认完成或放弃时才停）；「人工验收」标签在待验收之前也显示（淡显），逐条验收只在待验收时出现；端口一直连不上时停掉进程并标成失败；不加单实例锁。**用户补充：代码改了以后要重启，避免测到的不是最新代码；要有启动记录，让用户看到重启过。** 待做：服务启动时记下代码的状态，代码变了就标出「运行的不是最新的」；在开发会话一轮停下时、以及用户打开人工验收标签时自动重启（每个服务可关）；每个服务一份启动记录（时间、动作、原因、提交编号、退出码），存本机，日志里也插一行。

28. **三个会话的协作分工（2026-11-19 用户提出并确认，替代第 23 条里「测试会话按验收条件写测试集」的做法）：**
    - **立项会话出测试用例**，不了解代码细节：用业务的话写（前提、操作、预期），挂在验收条件下面，并标明每条验收条件是能用数据验证还是只能人工看。每条验收条件至少有一条用例，或者明确标「只能人工看」；不满足时确认立项会提示，但不拦。
    - **开发会话**写代码，目标是让这些用例通过；它能看到用例，不能改。
    - **测试会话负责对接和执行**：把用例对接成能跑的测试数据和接入代码（读代码只是为了接上，不能改用例的意思），执行，逐条用例报告结果；看界面的用例由它在界面做出来以后补成具体的检查步骤。它可以补充用例（标成「测试补充的」，用户能看到、能删），不能减少或改动立项写的。它不改产品代码。
    - 用例没通过 → 交回开发会话修代码。任何一方认为用例本身写错了 → 不能自己改，提给用户；**立项之后改用例一律要用户同意**。
    - 每条测试数据挂着它对应的那条用例。测试集、执行器、改数据要确认、人工验收都沿用。
29. **需求上的会话选择（2026-11-19 用户确认）：** 建好以后可以改测试会话和开发会话的 CLI 和模型（对下一次新开的会话生效）；立项的不放开。
30. **本仓库自己的测试（2026-11-19 用户确认）：** 这一批由子代理写的新测试保持为普通的代码测试，不补成测试集。

## 一、要解决什么

用这个工具的人不看代码。那么一个功能做完了，靠什么判断它做对了？

现在的做法是点「跑起来让我验收」，由 Agent 现想怎么启动，再用文字告诉人去终端里敲什么。这把人又推回了代码那一层，而且每次都要花用量、结果也不稳定。

另一个现象：AI 很喜欢写测试用例。它们散在代码各处，没有人知道每一个在保护什么、有没有价值，时间长了变成只增不减的负担。

所以要做的是：**给人一个可以持续测试的环境，把测试用例管起来，并且让它成为需求和问题走到「交给人验证」时进入的地方。**

## 二、几条原则

1. **测试方式是内置的，不是临时生成的。**（已定）不同类型的软件有不同的测试方式，由工具内置。原因：要记录测试的全过程，测试区必须由工具自己控制；内置的也更稳定、更安全。
2. **内容由 AI 生成，人只负责看、试、判断。**（已定）接口定义、测试用例都由 AI 直接生成；人可以自己改、自己加，但不是前提。
3. **数据全部结构化。**（已定）接口、用例、运行记录、证据都是有固定格式的数据，存在仓库里（密钥除外）。
4. **和需求、问题联动，不是孤立的页面。**（已定）
5. **AI 自测通过不等于验收通过。** 页面上明确区分哪些是 AI 跑的、哪些是人试的。确认完成只有人能点。（建议，沿用现有原则）
6. **按三层分工**（沿用 D-0075）：有客观答案的由程序算；只有聊天和开发过程里才有的由执行的 Agent 边做边记；另起 Agent 分析只用来查漏。

```
  ↓
开发        Agent 把这些用例做到能跑过
  ↓
AI 自测     Agent 自己跑一遍，结果记下来
  ↓
交给人      进入测试页，环境里跑的是这个需求自己的代码
  ↓
人验证      对着验收条件逐条试；不对就点「这里不对」，记录交回会话去修
  ↓
确认完成    存下证据，合并
  ↓
合并之后    这些用例成为对应功能点的固定检查
  ↓
哪天跑不过  记成一个问题 → 修 → AI 重跑 → 人在同一个测试页验证 → 好了
```

问题的修复走后半圈，和需求用同一个测试页、同一套动作。

## 四、内置的测试方式

| 类型 | 人怎么试 | 能记录到什么 | 期次 |
|---|---|---|---|
| 后端服务 | 接口列表，点开看入参和返回，直接发请求 | 每个请求和返回，完整 | 第一期 |
| 前端页面 | 页面嵌在应用里，直接点 | 点击、输入、请求、报错、截图，完整 | 后续 |
| 命令行工具 | 终端 | 命令和输出，完整 | 后续，很小 |
| Mac 端应用 | 启动它 | 日志、截图；点击难以记录 | 后续 |
| 手机应用 | 在模拟器里启动 | 日志、截图、录屏；点击难以记录 | 后续 |

一个项目可以同时有几种（比如前后端都有）。类型在导入项目时由程序判断，人可以改。

## 五、环境

- **第一期只在本机跑。**（已定）
- **环境由工具负责，人不用配置。**（已定）服务由应用启动，端口自动识别，请求地址自动填好；识别不出时让人填一次。
- **环境跟着代码目录走。**（建议）可以对着主线启动，也可以对着某个需求或问题自己的那份代码启动；几个可以同时开着，各用各的端口。
- **启动命令**记在项目里，由程序从项目文件里读出候选或由 Agent 提议；第一次执行前给人看实际的命令。（建议）
- **以后改成每次打一个 Docker 镜像来测。**（已定为后续方向）所以环境要做成可替换的：测试页只依赖四件事——启动、地址和端口、日志、停止。
- **外部依赖**（数据库、第三方服务）第一期不解决。（已定）要提醒人：测试会真的改到服务连着的数据库。
- **密钥和登录凭证存在本机文件里，不进 Git 仓库。**（已定）用例里只引用名字；存证据前抹掉。

## 六、结构化的数据

| 对象 | 是什么 | 主要内容 | 谁产生 |
|---|---|---|---|
| 接口 | 服务对外的一个接口 | 地址、方法、用途、入参（名称、类型、是否必填、示例）、返回的字段、是否需要凭证、属于哪个功能点 | 有现成接口说明时程序读；否则 AI 读代码生成，标待确认；改接口时 Agent 同步更新 |
| 用例 | 一项可以执行、有预期结果的检查 | **测试目标**（一句人话：它在保护什么）、类型、怎么执行、预期、关联的功能点和验收条件、来源（哪个需求或问题、AI 还是人） | AI 生成为主；人可以改、可以把刚发过的请求存成用例；也可以导入 |
| 测试集 | 一组用例 | 按功能点、按需求组织 | 程序按关联关系归组 |
| 运行记录 | 某次执行的结果 | 谁跑的（AI 还是人）、对着哪份代码、每项通过与否、请求和返回 | 程序 |
| 操作记录 | 人在测试页里做了什么 | 按时间的步骤 | 程序 |
| 证据 | 确认完成时留下的 | 验收条件、对应用例、AI 自测结果、人实际试了什么、有没有手动放行 | 程序，在确认完成时生成 |

**每个用例必须写测试目标。**（已定）说不出在保护什么的用例，本身就是该清理的信号。

**用例有两种类型，统一登记：**（建议）

- **接口检查**：一个请求加预期结果。应用可以直接执行。
- **代码里的测试**：AI 写在项目测试框架里的那些。文件仍然放在框架要求的位置，不搬动；登记的是「它在哪、怎么跑、目标是什么、关联哪个功能点」。程序能自动找出项目里有哪些测试，目标和关联由写它的 Agent 登记。

这样「AI 写的测试用例统一放在一个地方管理」指的是统一登记和查看，而不是把文件挪到一起。

## 七、判断用例有没有价值

进入验证页时，人能看到这个需求相关的全部用例，每一个都有：测试目标、对应哪条验收条件、最近的结果。（已定：在这里才能确认用例到底有没有价值）

程序可以直接算出一些信号，帮人判断（建议）：

- 没有关联任何功能点或验收条件的；
- 没写测试目标的；
- 目标和别的用例重复的；
- 从来没失败过、也没人看过的。

人可以标「留」或「不要」。标了不要的，由 Agent 删掉对应的测试并更新登记。

## 八、导入已有的测试配置

允许把以前 AI 生成的、或项目里已有的测试配置引进来，跑一跑、观察。（已定）

| 来源 | 怎么进来 |
|---|---|
| 现成的接口说明文件 | 程序直接读 |
| 常见格式的请求集合、请求文件 | 程序转换 |
| 项目里已有的代码测试 | 程序找出来登记，目标和关联待补 |
| 其他形式（脚本、文档里的示例） | AI 协助整理 |

导入的内容一律标待确认。

## 九、和需求的联动

1. 立项后端需求时，验收条件直接写成用例（请求加预期结果），在代码还没写的时候就定下来。
2. 开发的 Agent 做完后必须自己把这些用例跑一遍并记下结果，才算可以交给人。
3. 看板的「待验收」改成按「用例都由 Agent 跑过且通过」来判断，不再靠 Agent 自己说做完了。
4. 「跑起来让我验收」换成「去验证」：打开测试页，里面跑的是这个需求的代码，列着验收条件、对应的用例和 Agent 自测的结果。
5. 人逐条试。点「这里不对」，刚才那段记录交回这个需求的会话去修；修完重新自测。
6. **留一个手动放行的口子。**（已定）Agent 怎么都跑不过时，人可以手动放行进入验证。证据里如实记为「手动放行」，不记成「AI 自测通过」。
7. 确认完成时生成证据。
8. 合并以后，这些用例成为对应功能点的固定检查。

记录不整段交给 Agent：程序把它存成文件，人指出哪里不对时，Agent 只读相关的那一段。

## 十、和问题的联动

依赖「问题」功能。

1. 在测试页点「这里不对」时，如果是主线上的东西，连同记录记成一个问题。
2. 固定检查跑不过时，可以一键记成问题。
3. 修复问题时，先把能重现它的那个请求存成一项用例；修完 Agent 重跑，再交给人在测试页验证。
4. 人确认「好了」之后，这项用例留下来，防止以后再坏。

## 十一、证据自然分出的等级

不需要人维护，是流程里自己产生的。每个功能点上能看到它的每一项走到了哪一级，每一级都有记录可查。

| 等级 | 怎么来的 |
|---|---|
| 有对应的用例 | 立项时写下，或后来补的 |
| AI 自测通过 | Agent 跑的运行记录 |
| 人验证过 | 人在测试页里的操作记录 |

## 十二、明确不做的（第一期）

前端页面、手机和桌面应用、Docker 镜像、多套环境切换、登录流程的自动处理、用例之间传递数据、模拟服务、HTTP 以外的协议、AI 临时生成测试页面。

## 十三、建议的拆分和先后

前提：「问题」功能合进主线。

| 顺序 | 需求 | 内容 |
|---|---|---|
| 1 | 测试环境和后端接口测试 | 启动和停止、识别端口、接口列表、发请求、用例和测试集、执行和判断、密钥、运行记录 |
| 2 | 用例统一登记 | 代码里的测试纳入登记、测试目标、价值信号、导入已有配置 |
| 3 | 接进需求的验收 | 第九节 |
| 4 | 接进问题 | 第十节 |

第 2 项可以和第 1 项合并，取决于立项时对大小的判断。

## 十四、还没定的

1. 接口定义没有现成说明文件时，AI 生成的时机：导入项目时一次生成，还是第一次打开测试页时？
2. 代码里的测试，能不能做到逐个用例显示通过与否，取决于项目用的测试框架能输出什么，第一期可能只能做到「整套跑一遍」。
3. 手动放行需不需要写原因。
4. 用例标了「不要」之后，是马上删，还是攒到某个时刻一起清。
5. 「测试页」在左边导航里叫什么。
6. 对主线的固定检查什么时候跑：人手动点，还是每次合并之后自动跑一遍。
