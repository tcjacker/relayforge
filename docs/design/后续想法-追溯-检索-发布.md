# 后续想法：追溯、检索、发布

状态：想法已记下，还没有排期和细化。开工时逐项立项确认。
来源：2026-11-17 的讨论。标「用户提出」的是用户说的，标「建议」的是整理时补的做法。

## 一、需求、提交、会话挂在一起

用户提出：开发一个需求要和提交挂钩，会话也挂在一起。以后回溯「这里为什么这么开发」时，能从提交查到当时的原因、对应的会话、改了哪些文件。

建议的做法：

- 把关联写进 Git 本身：在需求和修复的工作目录里，每次提交时由程序自动在提交说明末尾加上属于哪个需求、是哪个会话做的。Agent 不用记得。
- 确认完成时，程序把这个需求的全部提交和改过的文件列进完成记录。
- 给 Claude Code 一个查询命令：给一个文件或某一行，查出是哪个需求改的、当时的需求说明和相关裁定。
- 这些都由程序算出来，不经过模型。

## 二、历史需求和会话的查询

用户提出：给 Claude Code 一个能力，可以查历史的需求和会话；会话归档（进入完成状态）时打标签，方便以后查找，相当于一个倒排索引。

建议的做法：

- 一个只读的查询命令，所有会话里都放行，包括立项会话。
- 标签分两类：客观的（涉及哪些功能点、模块、文件、裁定、问题）由程序算；概括的（关于什么、踩过什么坑）在确认完成时调一次模型来总结。
- 确认完成时的这一次模型调用，同时产出三样：标签、几句话的总结、聊到了但没记下的决定（交给用户确认）。这就是一直没做的「另起一个 Agent 查漏」那一层。

要注意：会话的原始聊天记录不在项目里，在 Claude Code 自己的目录下，而且会被它自动清理。想长期能回到当时的聊天，确认完成时要把这个需求的会话记录另存一份；建议存在本机、不进仓库（可能含密钥，体积也大），仓库里留总结和标签。

## 三、发布

用户提出：代码合并回项目目录的当前分支之后，不会自动提交并推送。需要再加一次提交，然后由用户手动推送到远端分支。因为有的服务一推送就会触发部署，所以交给用户来处理。

建议的做法：

- 顶栏显示有几个提交还没发布。
- 点「发布」先给出清单：推送到哪个远端的哪个分支，包含哪几个已完成的需求和已解决的问题。用户确认后才推送。
- 只有用户能触发，AI 不得自己推送。
- 推送被拒绝时不强推，说明原因，由用户决定是否先拉取。
- 每次发布包含哪些需求由程序知道，可以自动生成一份发布记录。

## 四、建议的先后

发布最小，而且每做完一个需求都缺这一步，排最前；其次是提交挂上需求和会话；最后是历史查询、完成时总结打标签、会话记录另存。
