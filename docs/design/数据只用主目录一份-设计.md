# 数据只用主目录这一份：设计

状态：已定，待开发。
来源：2026-11-17 的讨论。

## 一、要改成什么

应用里所有的数据——需求、设计稿、会话进展、裁定、没定的事、问题、功能点、模块、用户旅程——都只有一份：**项目目录当前分支下的 `.relayforge/`**。读从这里读，写也写到这里，以这一份为基准。（已定）

需求和修复各自的工作目录里只改代码，不再各自带一份事实。

目的：避免多分支开发时事实文件互相冲突。之前已经多次发生：裁定编号相撞，合并时摘要和会话记录冲突。

## 二、现在是怎样的

进行中的需求，它的需求文件、设计稿、会话记录、期间记的裁定都写在自己的分支上，确认完成时随代码一起合并进主目录。列需求时要去扫每个工作目录。问题模块已经是只写主目录的做法。

## 三、带来的后果和处理办法

三条都已经由用户同意。

### 1. 事实会走在代码前面

需求还在开发，它新增的功能点、裁定、设计稿就已经写进了主目录，但代码还没合进来。

处理：这些内容标明是哪个进行中的需求带来的，显示为「进行中，尚未完成」；确认完成时才转成现行。设计稿现在就是这样（草稿，完成后才成为功能点现在的样子），把同一个办法推广到功能点和裁定。

### 2. 放弃一个需求时要收尾

它带来的功能点、设计稿已经在主目录里。

处理：放弃时把这些移到历史里，注明是随哪个需求放弃的。需求文件本身留着，状态标为已取消。恢复一个已取消的需求时，把它们拿回来。

### 3. 事实文件的改动由谁提交

处理：统一由程序提交，但不是每改一下就提交一次，而是在几个时刻攒着一起提交：立项、确认完成、放弃、会话停下来时。问题模块也改成同样的节奏。提交只带 `.relayforge/` 下的路径，不碰用户其他的改动。

### 4. 工作目录里那份旧副本

工作目录是从分支检出来的，里面仍然有一份 `.relayforge/`，那是开分支那一刻的旧内容。

处理：所有读写事实的命令都自动指向主目录，不管在哪个目录里运行；规则里写明事实只在主目录，工作目录里的那份不作数。合并一个需求时只合代码，分支上 `.relayforge/` 不应该有改动；万一有，合并时不让它覆盖主目录的内容，并提示。

## 四、不变的

- 立项、确认完成、放弃、确认修好了这些关仍然只有用户能过。
- 推断的内容仍然标待确认。
- 不删除内容，被替代或放弃的移到历史。
- 确认完成时的合并流程（先在开发会话里合并目标分支，合好了才合并回来）不变，只是合的只有代码。

## 五、需要注意的

- 已有的、正在进行中的需求，它们的事实现在在各自的分支上。按用户的决定，这些不搬到主目录（可以丢掉）：改造后程序不再读它们，这样的需求不出现在列表和看板上；留下的 `.worktrees/R-…` 目录和 `req/…` 分支程序不删，也不碍事。已经在主目录里的（以前完成并合并的需求等）照常显示。
- 用户在项目目录里切换了分支，看到的就是那个分支上的数据，这是用户自己的选择。
- 提交攒在本地，发布之前只在这台电脑上。
