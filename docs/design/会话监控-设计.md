# 会话监控：后台记录，过一段时间让 Agent 分析

状态：第一版已做（分支 `feat/agent-monitor`）。
来源：2026-11-22 的讨论。起因是想核实我们对 Agent 的假设，用数据说话，而不是靠讨论和差距分析推着走。

## 要什么

用户正常使用时，后台默默记录每个会话做了什么。过一段时间，再让 Agent 读这些记录分析：

1. **指令遵循**：Agent 有没有照开场白里写的规矩做。
2. **工具使用**：哪些工具和命令从来没被用过，推荐了也没人用的是哪些。
3. **打转**：它在哪里原地打转、卡住、空等。

第一版只做了「需要时手动跑命令、现场去读原始记录来算」，这条路不可靠：第一次跑就发现 61 个会话的原始记录已经找不到了。CLI 会清理原始记录，没完成的需求也不会另存。所以改成边用边记。

## 后台记录（主体）

- **开关**：在设置里，叫「后台记录」，默认关闭。是应用级设置（`~/.relayforge/settings.json` 的 `monitor`），所有项目共用。
- **什么时候记**：会话每说完一轮就记一次。
  - Claude Code：钩子报「回复完了」或「在问你」时；
  - Codex：应用读到聊天记录里这一轮结束时。

  两种都经 `attention.onSettled` 交给 `app/src/main/monitor.js`，它再调用 `rf.py monitor record`。会话关掉或退出时，把没说完的最后一轮也记下来，标成 `done: false`。
- **等批准**：应用看到「停下来等你批准」到会话又动起来的这段时间，随下一次记录一起交给 `rf.py`，记到它落在的那一轮上。那一轮还没说完时，先存在 `state.json` 里。
- **存在哪**：`~/.relayforge/monitor/项目名-哈希/`，只在本机，不进仓库。
  - `events-年-月.jsonl`：一行是一轮，只往后追加；
  - `state.json`：每个会话记到了第几轮，所以不会重复记，漏记的也会在下一次补上；
  - `README.md`：字段说明，以及分析时可以看哪些角度，给以后读这个文件夹的 Agent 看。
- **一行里有什么**：
  - 会话编号、种类、属于哪个需求或修复、用的哪种 CLI；
  - 第几轮、开始和结束的时间、实际干活和停着的秒数；
  - 用户的话和 AI 回复的开头；
  - 打断次数、token、等批准；
  - 停住的地方；
  - 每次工具调用：工具、做了什么、文件或命令、结果状态、被拦下的原因、真正执行的 rf.py 命令、是否提交、改了哪些文件。
- **不记什么**：工具的输出不记；命令和话里像密钥的部分打码；一轮最多记 200 次调用。
- **代价**：每轮解析一次这个会话的记录，在真实会话上大约 0.3 秒，在后台跑，不影响会话。几个会话同时说完时，用文件锁一个一个写。
- **怎么用**：过一段时间，跟任何一个 Agent 说「读 `~/.relayforge/monitor/` 分析一下最近 Agent 的问题」就行。

## 现场核对（辅助）

`rf.py monitor`（不带 record）对还在的原始记录现场按规矩算一遍。它和后台记录用的是同一份解析，适合想马上看一眼、或者开发 RelayForge 自己时用。下面的「原则」「三个部分」两节说的就是它的规矩和判断方法。分析后台记录时可以照着同样的方法。

## 原则

- **全部由程序从会话记录里算，不调用模型。** 结果可以复查，同样的记录每次算出来都一样。
- **只看得到行为。** 能看到跑了什么命令、改了哪些文件、结果是成功、失败还是被拦下、用了多长时间。看不到 Agent 为什么这么做。所以只核对能从行为上判断的规矩。
- **只读。** 不改任何记录，也不预先放行给会话用。这是给人看的，也给开发 RelayForge 的人看。
- **规矩和开场白一一对应。** `sessions/monitor.py` 的 `RULES` 每一条都对着 `app/src/main/prompts.js` 里的一句话。改开场白时要同步改 `RULES`。

## 数据从哪来

- **会话清单**：
  - 需求的会话：按 `intake`、`test_sessions` 分成立项、测试、开发；
  - 修复的会话；
  - 问题的排查会话；
  - 大图会话；
  - 日常聊天的进展记录。
- **会话内容**：Claude Code 和 Codex 的原始记录，或者完成后另存到本机的副本（`session_where`）。
- **解析**：复用 `sessions/steps.py` 的事件流，和 `history session --steps` 用的是同一份解析。在这之上，监控又多区分了几件事：
  - **被规则拦下**：Claude Code 的权限规则、`rf.py` 的用户关口、Codex 的沙箱。只认失败的调用、而且只在结果开头找拦截说明，避免把输出正文里恰好出现的字当成拦截。
  - **用户拒绝**：和被规则拦下分开算。
  - **用户打断**：Claude 的 `[Request interrupted by user]`，Codex 的 `turn_aborted`。
  - **不算用户说话的消息**：上下文压缩后自动插入的续接消息、Codex 的环境说明和规则说明。
  - **真正执行了的 rf.py 命令**：只认出现在命令开头，或者 `;`、`&&`、`|`、换行、`$(` 之后的。写在 grep 里、引号里的不算，因为开发 RelayForge 自己时，代码里到处都是这些字。

## 三个部分

### 一、规矩做到了没有

每条规矩对每个会话给出三种结果：做到、没做到、不适用。

- 一行代码都没改的会话，不看「提交了没有」。
- 最后一次动静在 2 小时以内的会话，可能还没做完，「做完时要交回」的那几条先不算（`AT_END`）。

| 会话 | 规矩 |
|---|---|
| 开发 | 先读需求文件；动手前用 `note plan` 写计划；边做边记；改了代码就提交；不运行 `req done`；不手工改 `.relayforge` 下的记录 |
| 修复 | 第一次改代码前跑过命令（先复现）；用 `issue handback` 交回；边做边记；提交；不运行 `issue confirm / unconfirm / reject`；不手工改 `.relayforge/issues/` |
| 测试 | 用 `test run` 跑测试集；用 `req verdict` 交回结论；不手工改记录 |
| 排查 | 只读；用 `issue finding` 记结论；不运行处理问题和需求的命令 |
| 立项 | 聊定的事用 `note say / feature / check` 记进需求；不手工改需求文件 |

「不手工改」只算真的改成功了的。被规则拦下的尝试不算违规，记在「打转」里。

### 二、工具

- **每个工具、每条 rf.py 命令**：调用次数、用过它的会话数、失败次数、被拦下次数。
- **开场白推荐的命令**（`GUIDED`，比如 `why`、`history`、`design list`、`req cases`、`issue new`）：在该用它的会话里，有几个真的用了。

### 三、打转

| 现象 | 怎么判断 |
|---|---|
| 被拦下后还在重试 | 同一个工具对同一个目标被拦下 2 次及以上 |
| 同一步反复失败 | 同一条命令（或同一个文件的同一种操作）在一个会话里失败 3 次及以上 |
| 反复改同一个文件 | 一轮里改了同一个文件 8 次及以上 |
| 等了很久 | 一轮中间 10 分钟以上没有任何动静，并且有工具调用还没返回结果：命令跑得久或挂住了，或者在等你批准 |
| 模型停着没动 | 一轮中间 10 分钟以上没有动静，并且该模型出下一步了（工具刚返回，或者你刚说完） |
| 很长的一轮 | 实际干活超过 30 分钟（不算停着的时间），或者一轮里工具调用超过 150 次 |
| 没有结果的步骤 | 工具调用到最后都没有结果 |
| 你打断了 | 用户打断的次数 |

Agent 回复完以后、你还没说话的那段时间是在等你，不算停住。

门槛都写在 `monitor.py` 的开头，可以调。

## 第一次跑的结果

数据是 2026-11-22 本项目的 41 个会话，2517 次工具调用。下面是主要发现：

- **`why` 在该用的 9 个会话里一次都没被用过**，`history` 是 6/22，`issue new` 是 1/17。开场白里推荐的查询工具，基本没人用。
- **开发会话动手前写计划：5/8。** 测试会话用命令交回结论：已经结束的 3 个里只有 1 个做到。
- **有一个立项会话被权限规则拦下后，又用 Edit 改了 4 次需求文件。** 拦截信息只说了「目录被禁止」，没说该改用 `rf.py note`。
- **Codex 会话被沙箱拦下 7 次。** 主要是 git 写操作和 rf.py 写记录。
- **「等了很久」的两处都是在等完整测试跑完**，大约 10 分钟，属于正常情况。
- **另有 61 个会话的记录在本机已经找不到了。** 本机副本只在需求完成或修复合并时才另存，进行中被清理、或者被放弃的需求，记录就没了。

## 还没做的

1. **`rf.py monitor` 直接读后台记录**：现在它只读还在的原始记录，原始记录被清掉的会话就算不了。
2. **实时提醒**：同样的判断用在正在跑的会话上，比如等了 10 分钟就提醒你，这就是之前说的「卡住提醒」。现在只能事后看。
3. **据此改进**：
   - 拦截信息里告诉 Agent 应该改用哪条命令；
   - 把没人用的推荐工具放到真正需要的那一步再提示，或者干脆去掉；
   - 测试会话交回结论这一步，要不要由程序来催。
4. **覆盖更多会话**：
   - 没挂到任何需求的日常聊天（`rf.py sessions` 列的那些）；
   - Codex 里用变量调用的 rf.py（`"$RF" note`）。
5. **会话进行中也另存**：减少「记录找不到了」。
