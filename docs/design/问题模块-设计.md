# 问题模块：设计

状态：已定，开始开发。交互以 `docs/prototype/issues-v2.html` 为准，下面列出的几处例外除外。
来源：2026-11-17 的讨论。

## 一、它是什么

使用过程中发现的毛病，随手记下来，由 AI 先判断是哪一类，用户决定怎么办，修完由用户确认。

和需求的边界：产品该是什么样没变、只是现在不是那样，是问题；产品该是什么样要变，是需求。用户不用自己判断，记下来之后由 AI 初判，判错了可以纠正，两边可以互相转。

还没合并的需求里发现的毛病不算问题，在那个需求的会话里说。

## 二、已定的事

### 形态

1. 一个问题就是一条对话：提报、AI 初判、补充、用户的决定、修复报告、用户的结论按先后出现在同一条线里。底部始终有回复框，任何类别都能说话，但从不强制。
2. 列表形式，不做看板。五个状态：待处理、处理中、待你确认、已解决、不处理。
3. AI 初判分四类：是问题、可转需求、已有用法、待补充。每一类只给出判断和依据，下一步由用户点。
4. 来源三种：你、Agent、测试页。Agent 记的走同一个队列，同样经过初判。测试页这个来源现在只留位置。
5. 可以几条一起修（批量修复）。没有「全部确认」，每条单独确认。

### 相对交互稿的例外

| 交互稿里 | 定下来的做法 |
|---|---|
| 初判顺带给出功能点（AI 判断，待确认） | 先不做。功能点由用户手动关联，可以不关联；列表仍可按功能点筛选 |
| 修复报告里的「防止再发生」 | 去掉。修复报告只有两项：改了什么、怎样验证 |
| 「去验证」按钮 | 先不放，等测试模块做好再加 |
| 测试页来的问题带操作记录 | 只留数据位置，界面不显示 |
| 待补充的卡片上有「直接交给 AI 排查」 | 待处理的每张判断卡片（包括没判出来的）都有一个安静的「交给 AI 排查」；已经有排查会话时写「打开排查会话」 |
| 手机适配 | 不做 |
| 分析到一半时回复，AI 一起考虑 | 做不到。等这次跑完，马上带着回复再跑一次 |

### 五个决定

1. **一起修的几条，全部确认之后才合并。** 先确认的不显示「已解决」，显示「已确认，等同批的 #029」；合并后才变成已解决。某一条退回，只有它回到修复会话。
2. **问题只存在项目主目录里，不跟着需求的分支走。** 不管从哪个会话记，都写到同一个地方，所以用顺序编号（#033）不会撞。问题文件的改动由程序自己小步提交到主目录当前的分支上。
3. **截图不存进仓库。** 放在项目主目录里一个不进 Git 的位置。
4. **修复会话的终端和对话在右边切换。** 默认显示对话；一起修的几条共用同一个终端。
5. **初判只读产品事实，不读代码。** 读代码留给「交给 AI 排查」。

### 对话的三种深度

| 深度 | 是什么 | 界面 |
|---|---|---|
| 补充一句 | 用户回一句，AI 结合已有内容重新判断，只看产品事实 | 气泡 |
| 交给 AI 排查 | 一个只读的会话，能读代码、能复现，不能改 | 嵌入的终端 |
| 修复 | 一个能改代码的会话，有自己的分支和工作目录 | 嵌入的终端 |

### 规矩

- 「确认修好了」「还有问题」只由用户触发，AI 不得自己执行。
- 修复的 Agent 做完后逐条交回修复报告；改了代码却没交回，不让它停。
- 初判说「是问题」在复现之前只是推测，文案要如实。
- 同时最多跑两个初判，其余排队。

## 三、技术方案

### 数据

都在主目录的 `.relayforge/issues/` 下。

| 文件 | 内容 |
|---|---|
| 说明文件 | 文件头：编号、标题、状态、来源、类别、功能点、是否暂缓、所属的修复批次、转成的需求、重复的是哪条、创建和更新时间。正文：现象、修复报告（改了什么、怎样验证）、变更记录。格式和其他事实文件一致 |
| 对话记录 | 按时间一行一条：谁说的、说了什么、当时的判断。由程序读写，不手工编辑 |
| 截图 | 不进 Git |

给测试模块留的位置：来源里有「测试页」；可以挂一段操作记录；修复报告以后可以挂用例。

### 命令

| 命令 | 作用 | 谁触发 |
|---|---|---|
| 新建 | 记一条 | 用户、Agent |
| 初判 | 调一次模型，写入类别、依据、要问的问题或用法说明 | 程序 |
| 回复 | 往对话里加一条 | 用户 |
| 改设置 | 关联功能点、以后再说、拿回来、不处理、标重复、重新打开、纠正类别 | 用户 |
| 开始修复 | 一条或几条，开一个分支和工作目录 | 用户 |
| 交回 | 写入修复报告，状态变成待你确认 | 修复的 Agent |
| 确认、退回 | 确认修好了，或者还有问题 | 只有用户 |
| 转为需求 | 新建一个立项中的需求，带上描述、截图和对话 | 用户 |

### 初判

复用现有的后台调用模型的机制。给它：标题和描述、对话记录、截图、产品事实摘要、功能点清单和各自的用户旅程。要求只输出固定格式。程序先检查再写入：类别必须是四种之一，否则不写。

### 修复

复用需求的隔离和合并：分支、独立的工作目录、合并时的冲突处理和锁。一起修的几条共用一个。开场白说明要修哪几条、每条的现象和对话、涉及功能点的事实，以及先复现、再修、自己验证、逐条交回的规矩。

### 界面

左边导航加「问题」，图标上的数字是等用户处理的条数。样式和结构从交互稿搬过来，按现有方式拆成几个脚本。粘贴截图复用现有的存图逻辑。初判完成、修复交回走现有的提醒。

### 和已有功能的衔接

立项时程序算的「影响」里，加上这些功能点身上还没解决的问题。

## 四、分三步

| 步骤 | 内容 |
|---|---|
| 一 | 数据和命令、列表和对话界面、初判、单条修复和合并、转为需求、不处理、以后再说、重新打开、Agent 来源 |
| 二 | 一起修 |
| 三 | 交给 AI 排查 |

第三步的做法（已做，细节见 `app/README.md` 的「问题」）：

- 一条问题一个只读的排查会话，开在项目主目录里（看主线上的代码）；设置里禁止改项目里的文件、拒绝由用户决定的命令，只放行记事实的命令和它专用的 `issue finding`。
- 结论用 `issue finding` 记进对话：一条独立于初判的记录（读过代码），分开写「实际复现、验证过的」和「只是推断、没验证的」，类别跟着改，问题回到「等你决定」。排查会话开着时，用户的回复交给它，不再做只看产品事实的重新初判。
- 停下来时的检查：干了不少活却没记结论、也没问用户，就叫回去记；只能叫它记，拦不住它在聊天里说错话。
- 开始修复时，修复会话的开场白带着排查结论。右边的切换：有排查会话时「对话 / 排查会话」，有修复以后「对话 / 修复会话」。
