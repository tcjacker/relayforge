# 沉淀架构与文件格式（草案 v0.3）

**状态：第 7 节各点均已确认；第一段实现已完成，见第 8 节。** 2026-11-12 起草。本文是产品文档 v1.4 之后的一次收缩：入口只保留 Claude Code 和 Codex 的对话，沉淀由 AI 主动完成，页面只负责渲染。产品文档第 3 章描述的工作台原型保留为最终形态的参照（源文件在 `docs/prototype/`），这里定的是先做出来的最小版本。

## 1. 要解决的四个问题

1. 定好的规划埋在聊天记录里，要用时找不到；过期的信息没有被淘汰，污染上下文。
2. 大量使用子代理后，执行细节看不到。
3. 产品到底长什么样，没有可视化地沉淀下来。
4. 长期开发积累的文档没有治理，没有过期和淘汰。

四个问题是同一件事的四个面：**会话是一次性的，项目需要一份一直保持现行的事实。**

## 2. 架构

```
会话（Claude Code / Codex）
   │  ① 会话开始：读入现行事实摘要和待确认条目
   │  ② 压缩前、会话结束、子代理结束：钩子触发
   ▼
抽取（后台进程，不占用主会话）
   │  读本次会话记录，只抽四类条目，每条带出处
   ▼
收件箱（.relayforge/inbox/，只追加，一次沉淀一个文件）
   ▼
合并（单独一步，按顺序处理）
   │  去重；判断是否替代了旧内容；更新事实层；过期的移入历史
   ▼
事实层与记录层（都在 .relayforge/ 下）
   ▼
页面（只读渲染）  ──「刷新」──▶ 整理 Agent（按需重跑合并）
```

**两层内容，自动程度不同：**

| 层 | 内容 | 写入方式 |
|---|---|---|
| 记录层 | 每次会话做了什么、子代理的回报 | 全自动，只追加，不需要人看 |
| 事实层 | 模块、功能点、功能说明、裁定、文档的现行与过期状态 | AI 自动提出并写入，每条带出处；人明确表态过的直接生效，AI 推断的标为待确认 |

**页面是只读的，有一个例外：刷新。** 页面后面接一个整理 Agent。用户想立即看到最新状态，或想对整个产品重新审视一遍时，点刷新触发它。它和钩子触发的合并是同一段逻辑，只是由人按需发起。除此之外页面没有任何写入口；待确认的条目在下一次会话开头由人在对话里回答。

**第一版只抽四类条目：**

- 人明确作出的决定。
- 产品结构的变化（新增、移动、改名模块或功能点）。
- 哪份内容被哪份替代了。
- 还没定的问题。

功能说明七项的自动更新放到第二步。

## 3. 钩子能力核实

### 3.1 Claude Code

依据官方文档 `code.claude.com/docs/en/hooks.md` 等，2026-11-12 核实。字段名是经摘要读取的，写代码前要对着原页面再核一次。

| 需要做的事 | 能否做到 | 怎么做 |
|---|---|---|
| 会话开始时读入现行事实 | 能 | `SessionStart` 钩子，输出会进入上下文。输入里的 `source` 区分新开、恢复、清空、压缩后。**注入内容上限 10,000 字符** |
| 压缩前抽取 | 能 | `PreCompact` 钩子，`trigger` 区分手动和自动 |
| 会话结束时抽取 | 能，但要小心 | `SessionEnd` 钩子。它的时间预算只有 1.5 秒（可调到 60 秒），抽取进程必须脱离钩子自己跑。**关闭终端或进程被杀时是否触发，文档没有说明** |
| 子代理结束时存回报 | 能 | `SubagentStop` 钩子，输入里有 `agent_type`、`agent_transcript_path` 和 `last_assistant_message` |
| 拿到会话记录 | 能 | 所有钩子的输入都带 `transcript_path` 和 `session_id` |
| 在后台跑、不阻塞会话 | 能 | 命令钩子可设 `"async": true` |
| 钩子直接调用 skill 或子代理 | 不能 | 钩子只能把文字交给主 Agent，或另起一个进程（如无界面的 `claude -p`） |
| 让主 Agent 结束前再做一件事 | 能 | `Stop` 钩子可以阻止结束并给出指令；用 `stop_hook_active` 防止死循环 |

**由此定下的做法：**

- 抽取由钩子另起的后台进程完成，不让主会话自己识别。主会话的上下文不被占用，也不依赖它“记得要沉淀”。
- 后台进程里再跑 Claude 时，文档没有提供防止钩子递归触发的机制。做法是设一个环境变量作标记，钩子脚本看到它就直接退出。
- 会话记录是 JSONL，文档说明它是内部格式、版本之间可能变化。抽取程序只依赖其中最稳定的部分（角色和文本），并容忍读不懂的行。
- 因为 `SessionEnd` 不保证触发，**抽取必须可以补做**：记下每个会话已经处理到哪里，下一次 `SessionStart` 时检查有没有漏掉的会话，补上。
- 钩子写在项目的 `.claude/settings.json` 里。云端会话不读本机用户目录下的设置，只有写在项目里才两边都生效。
- Claude Code 只在没有 `CLAUDE.md` 时才直接读 `AGENTS.md`。约定统一写在 `AGENTS.md`，`CLAUDE.md` 里用一行 `@AGENTS.md` 引入。

### 3.2 Codex

2026-11-12 核实。**核实范围有限：** `developers.openai.com` 在调研环境里无法访问，下面标“已读源码”的来自 `openai/codex` 仓库 `main` 分支的配置结构和源码，标“仅摘要”的来自搜索结果对官方页面的摘要，需要再直接核对一次。

| 需要做的事 | 能否做到 | 依据 |
|---|---|---|
| 会话开始时读入现行事实 | 能 | 有 `SessionStart` 钩子，输出里的 `additionalContext` 进入上下文；`source` 同样区分新开、恢复、清空、压缩后（已读源码） |
| 压缩前抽取 | 能 | 有 `PreCompact` 钩子，`trigger` 区分手动和自动（已读源码） |
| 会话结束时抽取 | 能，但更要小心 | 有 `SessionEnd` 钩子；时间预算据说默认 1 秒、最长 3 秒（仅摘要） |
| 子代理结束时存回报 | 能 | 有 `SubagentStop` 钩子，带 `agent_id`、`agent_type`、`agent_transcript_path`（已读源码） |
| 拿到会话记录 | 能，有例外 | 钩子输入带 `session_id` 和 `transcript_path`，但后者可能为空，例如不保存会话的运行方式（已读源码） |
| 在后台跑 | 能 | 命令钩子有 `async` 选项（已读源码） |
| 后台进程里跑模型 | 能 | `codex exec` 可无界面运行，支持从标准输入读提示、按 JSON 结构输出、不保存会话（已读源码） |
| 约定文件 | 能 | 从仓库根到当前目录逐层读取 `AGENTS.md` 并拼接，总量默认上限 32 KB；没有找到引入其他文件的语法（已读源码） |

**钩子配置位置：** `~/.codex/hooks.json`、仓库内 `.codex/hooks.json`，或 `config.toml` 里的 `[hooks]`；项目内的钩子要求项目被信任（仅摘要）。

**没有核实的：** `Stop` 钩子能否阻止结束并让 Agent 继续；会话记录文件的格式是否稳定（没有找到公开的格式说明）；IDE 插件、桌面应用和云端任务是否执行钩子。稳妥的假设是云端只读 `AGENTS.md`。

### 3.3 两边对照后的结论

- **事件名和输入字段几乎一致。** `SessionStart`、`PreCompact`、`SessionEnd`、`SubagentStop`、`Stop` 两边同名，都带 `session_id`、`transcript_path`、`cwd`。**同一套钩子脚本可以基本通用**，只需按工具分别写一份配置文件（`.claude/settings.json` 和 `.codex/hooks.json`）。
- **会话结束都不可靠。** 两边的 `SessionEnd` 时间预算都很短，是否必然触发都没有保证。所以“可以补做”是必须的，不是优化：以 `PreCompact` 和下一次 `SessionStart` 的补做为主，`SessionEnd` 只当作顺手触发。
- **会话记录格式两边都不是公开约定。** 抽取程序要分别适配两种 JSONL，并且只依赖角色和文本这类最基本的内容。这是整套方案里最可能随版本升级而坏掉的地方。
- **抽取用哪个模型跑，跟着会话所在的工具走。** Claude Code 的会话由无界面的 Claude 抽取，Codex 的会话由 `codex exec` 抽取。两者输出同一种收件箱格式（5.8），合并步骤不关心条目是谁抽的。
- **云端和其他界面是未知数。** 第一版只保证本机命令行可用。

## 4. 目录结构

全部文件放在仓库的 `.relayforge/` 下，不改动仓库里已有的任何目录。

```
AGENTS.md                        写入约定（第 6 节），Claude Code 和 Codex 都读
CLAUDE.md                        只有一行：@AGENTS.md

.relayforge/
  FORMAT.md                      文件格式的定稿版本（本文第 5 节）
  product/                       事实层
    overview.md                  产品介绍
    concepts.md                  核心概念
  modules/
    M-01-场景生命周期.md          一个模块一个文件
  features/
    RF-101-lifecycle-fsm.md      一个功能点一个文件：功能说明七项
  decisions/
    D-0012-整点提交先于跨日交接.md   一条裁定一个文件
  documents/
    DOC-0003-北极星草稿.md        文档登记：仓库里已有文档的状态，不搬动原文件
  history/                       被替代的事实层文件移到这里，保留原编号

  inbox/                         管道：收件箱，一次沉淀一个 JSON 文件；合并后移入 inbox/merged/
  bin/rf.py                      工具本身的副本，钩子调用它
  runs/                          记录层：子代理回报
  context.md                     会话开始时注入的摘要，由合并步骤生成
  pending.md                     待确认条目，由合并步骤生成
  cursor.json                    每个会话已经处理到哪里
```

**为什么这样分：**

- **不碰已有的 `docs/`。** 仓库里原有的设计文档留在原处，原样不动。它们的治理通过 `documents/` 下的登记文件完成：每份被跟踪的文档一个登记，记录它的路径、状态和被谁替代（见 5.6）。这样既不用搬文件，也能回答“哪些文档是现行的，哪些该淘汰”。
- **结构不单独存一份。** 产品结构树由 `modules/` 和 `features/` 的文件头推出来（功能点文件头里写它属于哪个模块），避免结构文件和功能点文件两处不一致。
- **一个对象一个文件。** 多个会话同时写时冲突最少；被替代时整个文件移走即可。
- **事实层用 Markdown，管道用 JSON。** 前者要给人看，后者只在程序之间传。
- **`.relayforge/` 要提交进 Git。** 事实层需要版本记录，也要让云端会话和其他机器读得到。`cursor.json` 是例外，见第 7 节。

**与产品文档的关系。** 产品文档 v1.4 的 5.8 把文档放在 `docs/` 下、设计资料页直接读 `docs/`。第一版改为本节的做法：设计资料页读 `documents/` 的登记，再按登记里的路径显示原文。产品文档等这一版用起来之后再统一修订。

## 5. 文件格式

所有事实层文件都是“YAML 文件头 + 固定标题的 Markdown”。程序只解析文件头、二级标题和标题下的列表项，其他内容原样显示。

### 5.1 通用文件头

```yaml
---
id: RF-101                 # 稳定编号，创建后不变，改名、移动都不变
type: feature              # module | feature | decision | doc
title: Lifecycle FSM
status: current            # current 现行 | draft 草稿 | superseded 已被替代 | reference 参考
updated: 2026-11-12
supersedes: []             # 它替代了谁（编号）
superseded_by: null        # 谁替代了它；非空时文件应在 history/ 下
---
```

### 5.2 条目的出处与确认标记

事实层里每一条陈述都是一个列表项，行尾带出处；AI 推断的在行首加标记。

```markdown
- 整点提交先于跨日交接；顺序颠倒时拒绝并报告。〔S-20261112-a3f1#18〕
- 〔待确认〕跨日交接恰好落在整点时，两条校验都执行。〔S-20261112-a3f1#42〕
```

- `S-20261112-a3f1` 是会话编号，`#18` 是会话里的第几条消息。页面据此显示“出处”，可以点回原话。
- 没有 `〔待确认〕` 的条目，出处必须指向人的一句明确表态。
- 人在后续会话里确认后，合并步骤去掉标记；否认则删除该条并在变更记录里留一笔。

### 5.3 模块

```markdown
---
id: M-01
type: module
title: 场景生命周期
status: current
order: 1                   # 在结构树里的顺序
updated: 2026-11-12
---

## 负责什么
- 一个场景从开始到结束怎么走。〔S-…#…〕

## 变更记录
- 2026-10-28 创建。〔S-…#…〕
```

### 5.4 功能点

文件头在通用字段之外多三项：

```yaml
module: M-01               # 属于哪个模块
order: 1
depends_on: []             # 它依赖的功能点编号
```

正文是固定的八个二级标题，顺序和名称不能改，没有内容的写“- 尚未讨论。”：

```markdown
## 一句话定位
## 在模块中的角色
## 在产品中的位置
## 用户旅程
## 规则与边界
## 还没定的事
## 调整时要注意
## 变更记录
```

- “在产品中的位置”里只写说明文字；依赖关系以文件头的 `depends_on` 为准，“谁依赖它”由程序反推，不手写。
- “变更记录”只追加，每行以日期开头。

### 5.5 裁定

```markdown
---
id: D-0012
type: decision
title: 整点提交先于跨日交接
status: current
applies_to: [RF-101, RF-103]
decided_by: user
decided_at: 2026-11-06
supersedes: [D-0007]
superseded_by: null
---

## 决定
- 整点提交先于跨日交接；顺序颠倒时拒绝并报告。〔S-…#…〕

## 理由
- …

## 没有选的方案
- …以及没选的原因。
```

### 5.6 文档登记

仓库里已有的文档不搬动、不改写，只在 `.relayforge/documents/` 下为每份被跟踪的文档建一个登记文件。

```markdown
---
id: DOC-0003
type: doc
title: 北极星草稿
path: docs/north-star-draft.md      # 原文件在仓库里的位置
status: reference                   # current | draft | superseded | reference
related: [RF-104]                   # 关联的功能点或裁定
supersedes: []
superseded_by: null
updated: 2026-11-12
---

## 这份文档是什么
- 早期的方向性草稿，只作参考，不作为验收依据。〔S-…#…〕

## 哪些内容仍然有效
- …

## 变更记录
- 2026-11-12 登记，状态定为参考。〔S-…#…〕
```

- 状态是 `reference` 或 `superseded` 的文档，不进入会话开始时注入的摘要，Agent 开工时也不把它当依据。
- 没有登记的文档视为“未治理”，页面上单列出来，提醒需要有人判断它的状态。
- 原文件被改名或删除时，由合并步骤更新登记里的 `path`，或把登记标为已被替代。

### 5.7 被替代的内容

不删除。事实层文件移到 `.relayforge/history/`，文件头改为 `status: superseded` 并填上 `superseded_by`。页面默认不显示历史，Agent 开工时也不读它。仓库里的原有文档不移动，只改它的登记。

### 5.8 收件箱条目（机器之间传递）

实现时改用 JSON，字段与下面的示意相同。原因是工具只用 Python 标准库，标准库不带 YAML 解析；这类文件只在程序之间传，不需要给人读。


```yaml
# .relayforge/inbox/20261112T1432-a3f1.yaml
session: S-20261112-a3f1
tool: claude-code            # claude-code | codex
trigger: pre-compact         # pre-compact | session-end | catch-up | refresh
captured_at: 2026-11-12T14:32:00+08:00
range: [1, 57]               # 这次处理了会话里的哪些消息
items:
  - kind: decision           # decision | structure | supersede | open-question
    target: RF-101           # 关联的对象编号；新对象写 new
    statement: 整点提交先于跨日交接；顺序颠倒时拒绝并报告。
    evidence: "同意，就按提交在前、交接在后。"
    evidence_at: 18          # 出处是第几条消息
    stated_by: user          # user 人明确说的 | inferred AI 推断的
  - kind: supersede
    target: D-0007
    by: new
    statement: 「所有 GET 都重试」被「只有版本查询重试」替代。
    evidence: "…"
    evidence_at: 31
    stated_by: user
```

### 5.9 子代理回报（记录层）

```markdown
---
session: S-20261112-a3f1
agent_type: general-purpose
agent_id: a49a…
ended_at: 2026-11-12T14:20:00+08:00
related: [RF-101]            # 能判断出来时填，判断不出留空
transcript: （子代理会话记录的路径）
---

## 被要求做什么
## 改了什么
## 怎么验证的
## 没把握的地方
```

第一版直接把子代理的最后一条消息存下来，放在“被要求做什么”之后，不另外调用模型整理。四个标题的拆分放到第二步。

### 5.10 会话开始时注入的摘要

`.relayforge/context.md` 由合并步骤生成，受 10,000 字符上限约束，只放索引：

```markdown
# 现行事实摘要（自动生成，不要手改）

## 产品
- 一句话介绍。

## 模块与功能点
- M-01 场景生命周期
  - RF-101 Lifecycle FSM：一句话定位。→ .relayforge/features/RF-101-lifecycle-fsm.md

## 现行裁定
- D-0012 整点提交先于跨日交接 → .relayforge/decisions/D-0012-….md

## 待你确认（3 条）
- RF-101：跨日交接恰好落在整点时，两条校验都执行。来自 11-12 的会话。
```

细节按路径去读，不塞进摘要。

## 6. 写进 AGENTS.md 的约定（草案）

```markdown
## 项目事实的写法

本仓库的 .relayforge/ 保存项目的现行事实，由程序解析并渲染成页面。写入或修改时遵守：

1. 一个对象一个文件：模块在 .relayforge/modules/，功能点在 .relayforge/features/，
   裁定在 .relayforge/decisions/，文档登记在 .relayforge/documents/。
2. 文件名是「编号-名称.md」。编号一旦创建不得修改；改名只改名称部分和文件头的 title。
3. 每个文件以 YAML 文件头开始，字段和取值见 .relayforge/FORMAT.md。
4. 正文只用规定的二级标题，名称和顺序不能改；标题下只写列表项，一行一条陈述。
5. 每条陈述行尾标出处〔会话编号#消息序号〕。不是用户明确说过的，行首加〔待确认〕。
6. 用户明确作出的决定可以直接写入；自己的推断必须带〔待确认〕，不得自行去掉这个标记。
7. 不要删除内容。被替代的文件移到 .relayforge/history/，把 status 改为 superseded
   并填写 superseded_by。
8. 依赖关系只写在功能点文件头的 depends_on 里，不要在正文里另写一份。
9. 「变更记录」只追加，不改旧行。
10. 仓库里 .relayforge/ 之外的已有文档，不要为了治理而移动或改写；
    要改变它的状态，修改 .relayforge/documents/ 下对应的登记文件。
11. .relayforge/inbox/、runs/、context.md、pending.md、cursor.json 由程序生成，不要手工编辑。
12. 开工时只以 status 为 current 的文件为依据；.relayforge/history/ 里的内容，
    以及登记为 reference 或 superseded 的文档，不作为依据。
```

约定里引用的 `.relayforge/FORMAT.md` 是本文第 5 节定稿后的独立版本。放在那里是为了让 Agent 需要时按路径读取，不必把全部格式塞进 `AGENTS.md`（Codex 对 `AGENTS.md` 的总量有 32 KB 的默认上限）。

## 8. 实现状态与第一次试跑

### 8.1 已实现

工具是仓库根目录的单个文件 `rf.py`，只用 Python 标准库。测试在 `tests/test_rf.py`，共 18 项。

| 命令 | 作用 |
|---|---|
| `python3 rf.py init [目录] [--hooks]` | 在任意仓库里建好 `.relayforge/`，把约定写进 `AGENTS.md`，没有 `CLAUDE.md` 时建一个只含 `@AGENTS.md` 的；把工具复制到 `.relayforge/bin/`；加 `--hooks` 才写入 Claude Code 的钩子配置。可以重复运行 |
| `rf.py hook session-start` | 会话开始钩子：输出现行事实摘要，并为之前没处理完的会话补做抽取 |
| `rf.py hook capture` | 压缩前和会话结束钩子：另起后台进程做抽取 |
| `rf.py hook subagent-stop` | 子代理结束钩子：把它的最后一条消息存进 `runs/` |
| `rf.py capture --transcript … --session …` | 读会话记录里新增的消息，调用无界面的 Claude 抽取四类条目，写收件箱，然后合并 |
| `rf.py merge` | 把收件箱里的条目写进事实层，重新生成 `context.md` 和 `pending.md` |
| `rf.py status` | 列出各类对象的数量 |

合并是确定性的程序，不调用模型。它保证：用户明确说过的条目直接生效，推断的带〔待确认〕；推断出的替代、改名、移动只留一条待确认的记录，不真的执行；被替代的文件移到 `history/`，编号不重用；重复的决定不会写两次；一个条目出错不影响其他条目。

### 8.2 没有实现

- **只读渲染页面和刷新 Agent。**
- **Codex 的钩子配置和会话记录解析。**

- **功能说明七项的自动更新**（按第 7 节第 5 点，放在第二步）。
- **多个抽取同时运行时的互斥。** 现在没有加锁，两个会话同时沉淀可能互相覆盖 `cursor.json` 或分配到相同的编号。

### 8.3 第一次试跑：用本次设计讨论的会话记录

2026-11-12，对这次会话的记录运行了一次真实抽取，结果已提交在本仓库的 `.relayforge/` 下。

- 会话记录解析出 114 条人和 AI 的文字消息，约 8.4 万字符，一次调用处理完，用时约 3 分钟。
- 抽出 8 个模块、7 个功能点、49 条决定（39 条现行，10 条待确认）、12 条待确认条目，并把 8 条决定标为已被替代。
- 生成的 `context.md` 约 5,400 字符，在 10,000 字符的注入上限之内。

**看到的问题：**

1. **两次运行结果不一样。** 同一份记录先后跑了两次，第一次抽出 13 个功能点，第二次 7 个；决定的条数相同但标题和拆分方式不同。抽取不是可重复的。
2. **替代关系判断得偏激进。** 例如把“新增节点先建出建设中虚框”“提需求是改变产品的独立入口”标为被“页面只读”替代。但讨论中明确说过原型是最终形态的参照，第一版收缩并不否定它们。模型分不清“第一版先不做”和“这个决定作废了”。
3. **模块是按原型的页面划分的**（首页、产品功能、需求……），这是模型自己选的结构，没有人确认过，却因为出处指向用户的话而被标为现行。
4. **“用户明确说过”的界线偏松。** 很多决定是 AI 提出方案、用户回一句“同意”，模型都记成了用户明确表态。这符合本意，但意味着直接生效的内容里有不少是 AI 的措辞。

### 8.4 启用钩子之前要先做的事

钩子一旦启用，每次会话开始、压缩和结束都会自动运行命令并调用模型。启用前建议先完成：

1. 对着 Claude Code 官方文档的原页面，核对钩子配置的写法和输入字段名（3.1 的字段名是经摘要读取的）。
2. 给抽取和合并加互斥。
3. 针对 8.3 的第 2 点，把“第一版先不做”和“作废”区分开，否则自动运行会不断把仍然有效的决定移进历史。

启用的命令是 `python3 rf.py init --hooks`。
