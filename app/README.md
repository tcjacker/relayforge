# RelayForge 外壳演示

一个 Mac 应用窗口，分三栏：

- 左边是需求列表。新建一个需求，同时开出它自己的分支、工作目录和立项会话。
- 中间是嵌在窗口里的 Claude Code（原样的界面）。每个需求有自己的终端，切换需求时会话不会断。
- 右边是这个需求的内容（需求说明、要改的功能点、验收条件）和会话进展。进展由 Claude Code 自己边做边记，不需要手动同步。

新需求先立项、再开发，见下面的「立项」。验收也在右边：点「跑起来让我验收」，Claude Code 会把程序跑起来并告诉你怎么逐条检查；你自己操作过之后点「我试过了，确认完成」，这个需求的改动就合并进项目目录现在签出的分支（不一定是 main）。

大图是主线上的产品全貌：按层分页，每页是一棵「模块 → 功能点」的树，点开模块看它的用户旅程。已完成需求的完成记录里，模块和功能点的编号可以点，直接跳到大图里的那一项。见下面的「大图」。

这是演示：进行中的需求还不能在大图里预览它将带来的变化，大图里也不能反过来发起需求。

## 运行

需要 Node.js 20 以上、Python 3.10 以上，以及已经登录的 `claude` 命令。

```
cd app
npm install
npm start
```

## 默认演示项目

默认打开 FlowNote 演示项目，由仓库里的 `test-project/` 模板生成。看板、需求影响、产品大图、用户旅程、设计稿和会话进度都有虚构示例。浏览示例记录不启动 AI；点击「开始真实会话」或「开启真实编辑」才使用所选工具。新建需求和聊天同样会启动真实工具。

开发时工作目录在 `test-project/.runtime/flownote/`，打包后在 `~/.relayforge/test-project/`，与模板和 RelayForge 源码隔离。已有演示目录会保留，不自动重置。使用 `RELAYFORGE_PROJECT` 可覆盖默认项目。

## 选择项目

- 点窗口左上角的「项目：xxx ▾」，会列出这台电脑上登记过的项目，点一个就切过去；最下面的「打开其他目录…」可以选任意一个项目目录。
- 选中的目录如果还没初始化，应用会先问你，同意后替你初始化并提交一次（只提交它自己加的文件）。目录必须是 Git 仓库，并且至少有一次提交。
- 初始化之后，应用会让 AI 读一遍代码，生成大图的第一版草稿：模块、功能点和产品介绍。它们全部标为待确认，生成好了窗口下方会提示，到「大图」里看。密钥、`.env` 和被 Git 忽略的文件不会被读。
- 初始化失败会显示可关闭的页面状态条，不遮挡工作区。点「重试（AI 协助）」会用当前选择的工具打开修复会话，带上项目路径、失败阶段和错误详情，让 AI 检查原因并实际重试；修复完成后点「检查结果」验证初始化文件、提交状态和大图渲染。
- 关闭提示后仍可从项目菜单点「重试初始化（AI 协助）…」找回，失败记录在重启应用后保留。
- 默认启动回到演示项目；也可以在启动时指定自己的项目：`RELAYFORGE_PROJECT=/path/to/project npm start`。
- 切换项目会关掉正在开着的会话，切回来后点需求可以接着聊。

## 立项

新需求分两段：先立项，再开发。两段各用各的 Claude Code 会话，中间有一道只有你能过的门。

- 立项会话只聊不改：设置里禁止它在项目目录（包括所有需求的工作目录）下用 Edit 和 Write 改文件，笔记本工具直接拿掉（`--disallowedTools NotebookEdit`）；想用命令写文件会先问你，你可以拒绝。读文件、记录（`rf.py note`）、查影响（`rf.py req brief`）和保存设计稿（`rf.py design`）不用问。
- 唯一能写的地方是项目外面这个需求的草稿目录 `~/.relayforge/drafts/需求编号/`（设了 `RELAYFORGE_HOME` 时在它下面），只用来放设计稿：Write 和 Edit 在那里放行，不用问。
- 开场白里带着这个产品现在的事实摘要（项目主目录里的 `.relayforge/context.md`，太长时让它先去读），讲清楚清晰度的分级，要求它一次只问一个问题、尽量给 2 到 3 个具体选项，聊定一件就用 `rf.py note say|feature|check` 写进需求文件。
- 清晰度由程序从需求文件和设计稿算出，分四级：想法（只有标题）→ 方向（写了需求说明，并且至少一个要改的功能点）→ 方案（至少一份设计稿；没有界面的需求说明理由后跳过）→ 可验收（至少一条验收条件）。右边按台阶显示哪几级到了、还差什么；跳过的方案显示成「↷ 跳过了：理由」，不算画了。清晰度是从上往下没有断档的最高一级，所以方案没画也没跳过时停在「方向」，但不挡立项。
- 要改的功能点写现有的编号，或者「新增：名称（属于 M-xx）」。右边的「影响」由程序按这些编号算出：引用了哪些功能点和模块、哪些编号不存在、哪些功能点依赖它们、哪些现行裁定管着它们。Claude Code 在会话里运行 `rf.py req brief` 看到的是同一份结果，会把依赖和可能冲突的裁定讲给你听。
- 事情太小、不是功能上的改动，它会建议改用「日常聊天」；太大，它会建议拆开。

## 设计稿

方向定了以后，只要需求有看得见的界面，立项会话不再抽象地问，而是直接画一份设计稿给你看，你看着它提意见，它改同一份。

- 设计稿是一个单独的 HTML 页面：样式和脚本都在文件里，不引用外部网址和别的文件，断网能打开；有像样的示例数据，主要的按钮能点。要改的功能点已经有设计稿时，它从那一份改起，保持现有界面的样子（`rf.py req brief` 会告诉它文件在哪）。
- 保存的办法：它先用 Write 把页面写进草稿目录，再运行 `rf.py design save --title … --feature RF-101 --file 草稿路径`。程序检查页面（不能是空的、不能有外部引用、功能点编号要存在，新功能点写「新增：名称」），把它存进项目主目录的 `.relayforge/designs/`（一个说明文件加一个同编号的 HTML），和别的事实一起在下一个提交时刻提交；命令会打印页面的完整路径。改的时候用 Edit 改草稿，再加 `--id 编号` 保存，覆盖同一份。
- 为什么不直接从命令行把 HTML 交给它：试过 `<<'HTML'` 这种写法，页面里的脚本一带花括号和引号，Claude Code 自己的命令检查就会拦下，不可靠。所以改成「只许写项目外面的草稿目录，再由命令收进来」。
- 没有界面的需求（只改导出格式、后台逻辑之类），它会运行 `rf.py design skip "理由"`。
- 右边「设计稿」一栏列出这个需求的设计稿。点一份，它显示在中间聊天区的上方，终端在下面照常能打字，边看边聊。新画的一份会自动打开；改过的那份自动刷新。上下之间的横线可以拖，双击恢复一半一半；右上角可以收起，或者在单独的窗口里打开放大看（改了也会自动刷新）。
- 选上下排而不是再加一栏：三栏已经可以拖宽窄，再加一栏在 1500 宽的窗口里每栏都太窄；设计稿大多是横向铺开的页面，放在中间这一栏能拿到最宽的地方，终端照样留在眼前。
- 设计稿是 AI 写的页面，所以只在隔离的地方显示：预览是 `sandbox="allow-scripts"` 的 iframe（没有 allow-same-origin，页面脚本能跑，但拿不到应用的任何东西，也没有 Node）；单独的窗口不带预加载脚本、开着沙箱。它们发出的网络请求一律拦掉，也不能跳到别的地址或开新窗口。应用页面的内容安全策略本来就允许 `file:` 的 iframe，不用放宽。
- 需求确认完成时，设计稿从草稿（进行中）变成现行，成为它画的功能点「现在的样子」：完成记录里写着带来了哪些设计稿。某个功能点现在的设计稿，是覆盖它的、最晚完成的那一份；旧的一份如果画的功能点都有了更新的，就整份移到 `history/`，标为已被替代。
- 大图里点一个功能点，详情里有「现在的样子」：缩小的预览，点它或「放大看」在大图里放大，「单独打开」在单独的窗口里看。
- 门只看一件事：至少有一条验收条件（被否决的不算）。其他都可以跳过。条件不够时右边的「确认立项，开始开发」是灰的，下面写着还差什么。
- 点下去调用 `rf.py req start`：需求改为开发中，变更记录里记一笔，提交需求文件；然后关掉立项会话，给同一个需求开一个新的开发会话，让它读需求文件开始实现。这个需求从此有两个会话。
- 立项中的需求没有验收按钮，也不能确认完成。
- 需求列表顶部的「筛选需求阶段」只控制左侧需求列表；默认勾选立项中、进行中、待验收，已完成和已取消默认隐藏。看板始终保留五列，可以直接点击其中的历史需求。
- 不想做了，在左边列表或看板卡片上右击这个需求，选「取消这个需求…」。确认框会说清楚会发生什么：它的会话关掉；调用 `rf.py req drop`：没提交的代码改动提交到这个需求的分支上，分支保留；项目主目录里的需求文件留着，标为已取消并记下取消前的状态；它带来的功能点、裁定、设计稿移到 `history/`（注明随哪个需求放弃），它对现有功能点的改动不再算数；再收掉工作目录。恢复时把这些拿回来。立项中和进行中的需求都能取消，已完成的不能。
- 已取消的需求在「已取消」那一列里只读查看。右击它选「恢复取消前的状态」，调用 `rf.py req restore`，重建原分支的工作目录，内容、代码、会话和取消前所在的栏都保留。旧版取消的需求恢复为立项中。已完成并合并的需求不回退，新变更另建需求。

## 问题

用的时候发现的毛病，随手记下来，AI 先判断是哪一类，你决定怎么办，修完由你确认。设计见仓库里的 `docs/design/问题模块-设计.md`，交互稿是 `docs/prototype/issues-v2.html`。三步都做了：单条修复、一起修、交给 AI 排查。

- 左边导航的「问题」：图标上的数字是等你处理的条数（AI 在问你话的「待补充」，修好了等你确认的，和排查会话在问你话、等你批准的）。
- 左边是列表：五个状态页签（待处理、处理中、待你确认、已解决、不处理），待处理下面按 AI 初判的类别筛，还可以按功能点筛。每行写着一句话的状态（分析中、等你决定、等你补充、修复中、等你确认……），不是你记的标出来源（Agent、测试页），「以后再说」的沉在下面、变淡。
- 右边是这条问题的对话：提报、AI 初判、你的补充、你的决定、修复报告、你的结论，按先后排成一条线。底部一直有回复框，Enter 发送，Shift+Enter 换行，可以直接粘贴截图（存图用的是新建需求那套）。
- 「＋ 记个问题」：一句话现象，补充说明和截图都可以不写。记下以后 AI 在后台初判，同时最多判两条，其余排队；判的时候你可以去做别的。
- 初判分四类，每类只给判断和依据，下一步由你点：
  - 是问题：开始修复、其实是新需求、以后再说、不处理。初判只看了产品事实（事实摘要、功能点清单和各自的用户旅程、你的描述和对话），没读代码也没复现，卡片上照实写。
  - 可转需求：转为需求、按问题直接修、以后再说、不处理。
  - 已有用法：卡片上写着怎么做；解决了、还是不行、不处理。
  - 待补充：卡片上问你一个具体的问题，回复框亮起来；你回答以后 AI 带着回答再判一次。
  - 判的时候你又回复了：这次判完马上带着你的回复再判一次。没判出来（模型没回答、回答格式不对）什么都不改，卡片上有「重试」。
- 相关功能点由你手动关联（头部的「关联功能点」「改」「去掉」），可以不关联；点它就只看这个功能点的问题。
- 不处理：写一句原因；写 #18 这样的编号就是标成和 #18 重复。已解决、不处理的可以重新打开；转成需求的不行，在需求里跟进。
- 转为需求：新建一个立项中的需求，需求说明里带上描述和你说过的话，截图和整个对话放在这个需求的草稿目录里，立项会话开始时交给 AI。问题移到不处理，标为已转需求。
- 开始修复：和需求一样开一个分支 `fix/f-005` 和工作目录 `.worktrees/F-005`，右边从「对话」切到「修复会话」，是一个嵌在里面的 Claude Code。开场白里有问题的现象、对话、关联功能点的事实和用户旅程，规矩是先复现、再修、自己验证、提交、用 `rf.py issue handback` 交回修复报告（改了什么、怎样验证），不许自己确认。改了代码却没交回，它停下来时会被叫回去。切回「对话」时会话照常在跑；处理中的问题，你在对话里补充的话会顺手交给修复会话。
- 交回以后问题变成待你确认，弹一条提醒。「确认修好了」像需求的确认完成一样排队合并进项目目录现在签出的分支，也一律先在修复会话里合并：修复分支还没包含目标分支的最新内容、或者还有没提交的改动，就回到修复会话让 AI 提交、把目标分支合并进来、解决冲突，它说完程序再检查、合并回去（卡住了点「重新检查并合并」，也可以「中止合并」）。目标分支上新多出来的只是程序记的问题文件时不算，不用为此回去合并（需求的确认完成也一样）；修复分支上没有任何改动时不用合并，直接算已解决。「还有问题」写一句哪里不对，回到同一个修复会话，你的话替你交给它。
- 一起修：待处理列表里，判成「是问题」、没放到「以后再说」、不在分析的行，前面有勾选框（点它不会打开这条问题；焦点不在输入框里时，空格勾选或取消勾选当前这一行），别的行留着空位，标题对得齐。勾了以后列表底下钉着选择条：已选 N 条、取消选择、一起修（两条起才能点）；已选的都是同一个功能点时多一句「把 RF-101 的另外 N 条也选上」，涉及几个功能点或都没关联功能点时提示「分开修更稳」，已选的有几条被筛选挡住时写「其中 N 条不在当前筛选里」。换类别、换功能点筛选时选择保留，离开待处理、开始修复、点取消选择时清掉。点「一起修」弹出确认，列出这几条，确定后开**一个**修复（一个分支、一个工作目录、一个修复会话，开场白里列出每一条的现象、对话和功能点，要求逐条交回）。每条的对话里有一行「和 #027、#026 一起修 · 修复会话 F-00N」，列表里写「修复中 · 一起修 N 条」，右边「对话 / 修复会话」切换对几条显示的是同一个终端。
  - 对话底部有同批其他几条的小标签（点一下跳过去），各带状态：修复中、等你确认、已确认、已解决。
  - 逐条交回、逐条确认，没有「全部确认」。确认一条后它还留在「待你确认」，写作「已确认，等同批的 #029、#026」（同批还没确认的几条），自动跳到同批下一条还在等你确认的，并提示「还有 K 条等你确认」；这样的行不算等你处理（图标上的数字、页签的黄点都不算它），也不用排合并队伍。同批最后一条确认了才合并，几条一起变成已解决。合并时要先回修复会话、有冲突，处理的是整个修复，每一条的确认都保留。
  - 「撤回确认」把自己的确认收回来（修复还没合并时可以）。「还有问题」只让这一条回到修复会话，同批别的条保留各自的确认。
  - 属于还没完成的修复的问题（处理中、待你确认）不能被「不处理」「以后再说」「改类别」「重新打开」：先让修复完成，或者用「还有问题」把它退回。
- 交给 AI 排查：待处理的每一条问题（不在修复里的），判断卡片上都有一个安静的「交给 AI 排查」，待补充和没判出来时是自然的下一步，别的类别可有可无；已经有排查会话时按钮写「打开排查会话」。一条问题一个排查会话，再打开时接着上次的，聊天记录不在了才另开一个。
  - 它是右边的一个嵌入终端（编号 `probe:问题编号`），开在**项目主目录**里：看的是主线上现在的代码，也就是你正在用的那份。右边的切换是「对话 / 排查会话」；一开始修复（有修复会话了）就换成「对话 / 修复会话」，排查会话收起来，它的结论还在对话里。
  - 开场白有：问题的现象、对话、截图路径、关联功能点的事实（`rf.py issue brief 问题编号`）；任务是弄清是不是真毛病、毛病在哪、怎么复现；能自己查的不问你，要问一次只问一个，并配 2 到 3 个选项；不改任何文件；有结论就记下来、然后停。
  - **只读怎么保证的**：和立项一样，启动时带的设置里禁止在项目主目录下 Edit、Write（整个目录，包括 `.worktrees/`），笔记本工具拿掉（`--disallowedTools NotebookEdit`），Codex 用只读沙箱；它能写的只有项目外面它自己的草稿目录（`~/.relayforge/drafts/probe-问题编号`，放脚本、复现用的拷贝）。另外明确拒绝：`rf.py issue fix、set、reply、confirm、unconfirm、reject、to-req、probe、handback`，`rf.py req start、done、drop、set`（项目里 `.relayforge/bin/rf.py` 的写法也一样），以及 `git add、commit、checkout、switch、merge、rebase、reset、stash、push、apply、restore、clean、cherry-pick、worktree` 和 `rm`、`mv`。会写文件的 shell 命令（比如 `echo > 文件`）没有预先放行，和别的命令一样要你批准，但也没有逐条拦住：这一层靠开场白和你的批准，不靠规则。放行的只有记事实的命令、`issue new|list|show|brief` 和它专用的 `issue finding`；别的会话拿不到 `issue finding` 的放行。
  - **记结论**：`rf.py issue finding 问题编号 --kind bug|request|usage|ask --text "结论" --steps "怎么复现" --where "问题在哪" --verified "实际复现、验证过的" --inferred "只是推断、没验证的"`。对话里加一张「AI 排查结论 · 读过代码」的卡片，和只看产品事实的初判分开：复现过的和只是推断的各占一块，颜色不同，要求两项都写（没有复现就写「没有复现」），判成是问题还要写怎么复现；问题的类别跟着改，回到「等你决定」，按这个类别给平常的按钮。只有交给过 AI 排查、还在待处理的问题能记，已经在修复里或已关闭的会被拒绝。排查会话不得自己开始修复、改状态、转需求，那些由你点。
  - **停下来时的检查**（`rf.py hook event` 里，和记进展、修复交回的检查一起做）：这一轮操作了三次以上（或回复里下了「结论」「根因是」「复现了」这样的结论）却没记结论、回复的最后一句也不是问你的问题、也没用「问用户」的工具，它被叫回去：要么记结论，要么说清卡在哪并问你一个问题。被叫回一次以后不再拦；只问问题、查得很少、记了结论的不受影响。这只能叫它记，拦不住它在聊天里说错话。
  - 列表里：排查会话在干活时那一行写「排查中」，在问你话写「等你回答」，等你批准写「等你批准」，说完了（比如记了结论）回到「等你决定」/「等你补充」；问题图标上的数字也算上等你回答、等你批准的；系统通知点一下跳到这条问题、右边切到排查会话。排查有了结论弹一条提醒。
  - 排查会话开着的时候，你在对话里回复的话交给它（和回复修复会话的方式一样），不再触发只看产品事实的重新初判；对话里这句标「说给排查会话」。会话没开着，回复照旧让 AI 重新初判（初判会读到排查结论）。
  - 开始修复时，修复会话的开场白里带着排查结论（复现步骤、问题在哪、实际复现过的、只是推断的）：修复的人从它出发，推断的部分要自己确认。
- 初判完了等你决定、修复交回了，都走现有的提醒：系统通知，点一下跳到那条问题；你正看着它时不提醒。
- 问题只存在项目主目录的 `.relayforge/issues/` 下，跟着主目录现在签出的分支走：从哪个工作目录记、交回、转换，读写的都是这里，需求和修复的分支上不存问题数据，所以用顺序编号（#033）。每改一次，程序自己提交一次，只提交这个目录，提交到主目录现在签出的分支上，不碰你别的改动。截图放在 `.relayforge/issues/shots/`，不进 Git（`init` 写进 `.gitignore`，以前初始化的项目在 `.git/info/exclude` 里补上）。
- 任何会话都可以用 `rf.py issue new "…" --source Agent` 记一条（放行规则里已经放行），应用看到文件变了就把它排进初判。`rf.py issue confirm`、`rf.py issue unconfirm` 和 `rf.py issue reject` 不放行，只由你在应用里点。
- 需求转问题：立项中的需求其实是现有功能的毛病时，在左边列表或看板上右击它，选「转为问题…」（可以顺手关联一个功能点）。问题照常记在项目主目录里，来源是你，现象是需求说明的原话，由 AI 初判；需求留着，文件头记下转成了哪条问题，右边面板上出现「查看转换后的问题」，点它跳到那条问题。反过来，问题转成的需求面板上是「查看来源问题」。
- 立项时右边的「影响」里，也列出要改的功能点身上还没解决的问题。
- 还没有的：一起修（几条共用一个修复会话，全部确认后才合并）、交给 AI 排查（只读、能读代码的会话）、「去验证」按钮（等测试模块）、测试页来的操作记录的显示（数据位置留着）。

## 发布

确认完成、确认修好了之后，代码只合并进了项目目录当前分支，没有推送。推送可能触发部署，所以只由你在应用里点「发布」：不自动、不由 AI 做。

- 顶栏的小提示：当前分支比它的上游多几个提交，就显示「N 个提交未发布」。没有可比的东西时是更轻的提示：「还没有远端」、「还没设置上游分支」（不报数）；点开都能看到原因。它在项目目录的提交有变化、远端或上游配置变了、窗口回到前台时重读（`rf.py publish status`，只看本地、不抓取远端，没有定时抓取）。
- 点开是发布对话框，推送之前先给出清单：会推到哪个远端的哪个分支（写成「main → origin/main」，并提醒推送可能触发部署）；包含哪些已完成的需求和已解决的问题（按标题）；程序自己提交的事实记录有几个；其他提交（折叠起来，点开看）；要注意的事：项目目录里没提交的代码改动不会被发布，会列出几个文件名；挡住发布的事：有合并或变基没做完、不在任何分支上、远端比本地新。
- 「检查远端」会抓取一次（有超时，不会弹口令框）再重看一遍；远端的新提交只算到上次抓取为止。远端比本地多、本地没有新提交时，有「先拉取」：抓取后只做快进。两边都有对方没有的提交时什么都不动（程序自己不合并也不变基），改为下一条的「让 AI 来合并」。
- 「让 AI 来合并」：对话框看到两边分叉了，或者「先拉取」因为做不了快进而没成，就出现这个按钮。点它：先抓取一次、确认两边还是分叉的，对话框关掉，应用切到聊天并新开一个日常聊天（在项目目录里），开场白交代好：远端已经抓取过；把 `远端/分支` 合并进当前分支；冲突要先弄懂两边各想做什么，不整个文件只选一边；`.relayforge/` 下两边的事实都保留、一条记录都不丢（并说明是哪几个文件）；项目有明显的跑测试的办法就跑；提交这次合并；不推送，也不运行 `rf.py publish run / pull`；最后用大白话说哪些冲突了、各自怎么解决的，并提醒回到发布。开场白里还列着两边都改过的文件（程序用 `git diff` 算的，只是提示，以 git 为准）。这个聊天的权限里放行了 `git status / diff / log / show / add / merge / commit`（别的聊天照旧会问你），推送照旧禁止。合并好以后，你回到发布对话框点「检查远端」，不再落后了就能发布。
- 项目目录里有一次合并（或变基、拣选）没做完时，对话框说明是哪一种没做完，并挡住发布；应用记得是它开的聊天（只记在内存里，重开应用就忘了）并且那个聊天还在，就有「回到那个聊天」，否则只是说明。
- 当前分支还没有上游：只有一个远端时，对话框说明会在远端新建同名分支并设为上游，要勾选「我知道……」才能点发布；有好几个远端要先选一个；没有远端时发布不可用，说明原因。
- 点「发布」：程序先把攒着的事实提交，写好这次的发布记录并提交，再推送当前分支到它的上游。明确写出「本地分支:远端分支」，不强推、不推标签、不推别的分支（你的 git 配置里的 push.default、followTags 也改不了这一点）。推送在后台运行，有超时；运行时按钮变灰、不能再点第二次，对话框也关不掉。
- 成功：弹一条提示说明发布了什么，顶栏的提示消失（发布记录和它带的事实提交随这次一起推送，所以数目回到 0）。失败：原因用大白话写在对话框里，加上 git 的最后一行；被拒绝（远端有新提交）、没有权限、连不上或超时、推送前的钩子没通过、远端的规则拒绝，各是各的说法，什么都不会换个办法重试。
- 「以前的发布」：对话框下面折叠着，列出以前的发布记录（日期、分支、带着的需求和问题）。记录在项目主目录的 `.relayforge/publishes/`，格式见 `.relayforge/FORMAT.md` 的「发布」。
- AI 不能推送：应用开出的每一种会话（立项、开发、修复、排查、聊天）都在权限规则里禁止了 `git push` 和 `rf.py publish run / pull`，只放行只读的 `publish status` 和 `publish list`。这只拦得住应用开的会话，拦不住你自己在终端里的操作。
- 哪个需求、哪个修复带来了哪些提交：确认完成和确认修好了合并时，程序把合并提交的编号记在需求文件头的 `merge_commit` 和 `issues/fixes/F-xxx.json` 里；以前完成的按合并提交的标题找。细节见 `backend/relayforge/project/publish.py` 开头。

## 人工验收

需求到了待验收，左栏这个需求下面有「人工验收」标签（之前的阶段也能点开先试）。测试页的「人工测试」是同一套界面，对着项目主目录（主线），没有验收条件那一栏，改成「发现不对 → 连同日志记成问题」。

- 中间上面是当前测试环境的每个服务：名称、状态（没启动 / 正在启动 · 等端口可连 / 运行中 / 已退出（退出码）/ 启动失败）、启动、停止、重启、打开（配了端口时用系统浏览器打开 `http://localhost:端口`）；「全部启动」「全部停止」。下面是日志：各服务的标准输出和标准错误按时间排在一起，可以只看一个、清空；保密值打码以后才显示、才写到本机的日志文件。
- 进程由主进程直接管（`src/main/services.js`，不经过模型）：在需求的工作目录（加上服务的子目录）里执行测试环境「怎么启动」里的命令，带上这套环境的环境变量（你在应用里点的，带保密值）和服务的「验收时额外带的环境变量」。应用自己的 `RELAYFORGE_*` 变量不会带过去。启动前按准备步骤的规矩执行要执行的步骤；启动命令第一次执行、或命令和目录改了以后，先弹出确认框给你看（和准备步骤同一个框）。
- 每个服务一个进程组，停的时候整组停。切换项目、退出应用、确认完成或放弃需求之前都会停掉；应用异常退出后，下次启动时把上次留下的进程停掉（看记下的进程号和启动时间）。
- 启动前显示这次会用什么：RelayForge 这样的应用说「打开的是：演示项目 / 当前项目的副本（只读用途，改了也不会回到真实项目）」，别的项目列出解析后的验收变量。
- 启动失败（很快退出、端口一直连不上、端口被占）时有「让 AI 来处理」：命令、目录、退出码、日志尾部交给开发会话（或新开的聊天）。
- 右边需求面板在待验收时，每条验收条件下有「通过」「这里不对」。「这里不对」写一句话，程序把这句话、验收条件和检查步骤、当时的日志尾部交回开发会话，需求退回进行中。「我试过了，确认完成」照旧，不强制逐条点完，完成记录里如实写哪几条点了通过、哪几条没点。
- 测试环境里没配服务时，面板上的按钮仍是「跑起来让我验收」（交给开发会话），旁边提示可以去配；配了就换成「去人工验收」。

### 作为验收实例启动（RelayForge 自己）

RelayForge 本身也能这样被启动成「验收用」的第二个实例，和你正在用的那个互不影响。入口是几个环境变量（`src/main/config.js`）：

- `RELAYFORGE_USER_DATA`：数据目录（Electron 的 userData：上次打开的项目、初始化失败的记录、窗口里的存储都在这里）。在应用 ready 之前设，所以单实例相关的东西、最近项目都跟着它分开。
- `RELAYFORGE_HOME`：本机登记的项目、保密值、草稿、应用的标记。
- `RELAYFORGE_PROJECT`：打开哪个项目；`demo` 是演示项目。
- `RELAYFORGE_WINDOW_TAG`：窗口标题前面加的一段标记，顶栏上也显示（连同数据目录）。

给 RelayForge 这个项目推荐的测试环境（在测试页的「测试环境」里填，或者让 AI 读项目来填）：

- 服务「应用」，命令 `npm start`（`app/package.json` 里的 start，先跑 prestart），子目录 `app`，没有端口。
- 验收时额外带的环境变量：
  - `RELAYFORGE_USER_DATA` = `{{scratch}}/userdata`
  - `RELAYFORGE_HOME` = `{{scratch}}/home`
  - `RELAYFORGE_PROJECT` = `demo`（演示项目；要用当前项目的副本就写 `{{project_copy}}`）
  - `RELAYFORGE_WINDOW_TAG` = `验收用 · 需求 {{req}}`
- 准备步骤「装依赖」：`npm ci`，目录 `app`，`app/package-lock.json` 变了才执行（需求的工作目录是新签出的，没有 `node_modules`）。
- 每个工作目录单独安装依赖。`app/node_modules` 是本地生成目录，旧工作目录如果还带着共享依赖的符号链接，先移除链接本身，再运行 `npm ci`。macOS 的 `npm start` 从同一工作目录下的 `app/.electron-runtime/` 启动 Electron，该应用包按版本和品牌资源缓存，重新安装 npm 依赖时仍可启动渲染进程。

## 追溯：提交、需求、会话

设计见 `backend/relayforge/sessions/trailers.py` 和 `trace.py` 开头。目的：以后问「这段代码为什么这样写」，能从一个提交（或一个文件、一行）走到需求、它的理由、做它的会话，也能看一个需求改了哪些文件。

- **提交上的出处由 git 自己带上，不靠 AI 记得。** 需求和修复的工作目录里的每个提交，说明末尾都有 `RelayForge-Requirement: R-…`（或 `RelayForge-Fix: F-…`，加上这次修复带着的每条问题一行 `RelayForge-Issue: I-…`）和 `RelayForge-Session: S-…`。需求确认完成、修复确认修好了的合并提交也带需求或修复那几行（不带会话）。
- **做法：** 每个工作目录有自己的 `core.hooksPath`（`git config --worktree`，需要共享配置里 `extensions.worktreeConfig` 为 true，这是 git 自带的机制），指向它私有目录（`.git/worktrees/名字/relayforge-hooks/`）里的一套钩子。选它而不是往共享的 `.git/hooks` 里放一个钩子，是因为：只影响这些工作目录，项目主目录里你自己的提交不会带这些行、也不会多出任何钩子文件；不动你已有的钩子；你自己设了 `core.hooksPath`（比如 husky）时共享目录的钩子根本不会运行。代价：共享配置里多一行 `extensions.worktreeConfig = true`（不改变项目主目录的行为）。
- **你自己的钩子照常运行：** 钩子目录里每个钩子名都有一份同样的小脚本，先找你的钩子（共享、全局或系统配置里设的 `core.hooksPath`，没设就是仓库的 hooks 目录），原样运行：别的钩子 `exec` 过去，参数、标准输入、退出码都不变，所以照常运行、照常能拦住提交；`prepare-commit-msg` 先运行你的、再在它改过的说明上加那几行。这个钩子 `git commit -m`、`--amend`、`--no-verify`、合并、拣选、`-F` 都会运行，不管是哪个工具提交的。已有同样的行不再加；我们这一步出任何错（工具缺了、数据文件坏了）都吞掉、退出码是 0，提交不会因为我们失败。
- **会话是哪个：** 应用启动会话时把会话标识放进环境变量 `RELAYFORGE_SESSION_ID`。实测（真实的 Claude Code 在需求工作目录里用 Bash 工具提交）：它传得到工具运行的命令里，钩子读得到；Claude Code 自己的 `CLAUDE_CODE_SESSION_ID` 是第二选择；都没有（比如你在终端里提交）就用挂在这个需求或修复下最新的会话。
- **会话的身份不靠它：** `RELAYFORGE_SESSION_ID` 只用来记出处。程序要知道「这是哪种会话、属于哪个需求」（比如测试会话才能交回测试结论）时，只认应用签名的会话令牌 `RELAYFORGE_SESSION_SIG`：密钥只在应用的内存里，rf.py 通过应用登记的本机 unix socket 请应用验证，令牌只在发给的那个会话进程下面算数（`src/main/session-token.js`、`backend/relayforge/core/identity.py`，见 FORMAT.md 的「会话的身份」）。没有令牌的会话按日常聊天算。
- **什么时候装：** 开出工作目录时（新建需求、开始修复）、会话挂上时、应用打开需求或修复的会话时（`rf.py trailers install`，以前开的工作目录也补上；重复装没有害处）、恢复取消的需求时。装不上（git 太旧、仓库是 bare 等）就没有这些行，别的都照常。项目主目录永远不装。
- **`rf.py trace R-… | F-… | I-… [--json]`：** 它的提交（哈希、日期、说明、会话）、改了哪些文件（行数）、挂了哪些会话（带进展文件的路径）、合并提交、有没有发布。认提交先看提交说明里的行；这个功能出现之前完成的，按合并提交的第二个父提交一路上的提交（和发布认「哪个需求带来了哪些提交」是同一个办法），再早的按合并提交的标题找；`rf.py trace --commit 哈希` 从一个提交出发。
- **`rf.py why 文件[:行|:起-止] [--json]`：** 文件用 `git log --follow`（跟着改名），几行用 `git blame -M -C`，找到最近改它的提交，各自对到需求或修复：需求给出标题、需求说明、验收条件、它记下的裁定、会话和进展文件；修复给出问题的现象和修复报告；不属于任何一个的提交单独列出。带会话出处的提交，本机还有那个会话的聊天记录（存档或原始记录）时，再给出产生它的那一轮的步骤摘要（和 `history session --steps` 同一份数据，最多 12 步）：先按提交号认，`git commit -q` 这类输出里看不到提交号的按提交标题认并注明。输出有上限。
- 这两条命令只读、不调用模型，应用开的每一种会话都预先放行；开发和修复会话的开场白、`AGENTS.md` 的约定都让它改不知道原因的代码前先 `rf.py why`。
- **完成记录：** 确认完成、确认修好了时，写下这次工作的提交数和文件数（需求的变更记录一行「改动：N 个提交、M 个文件」，修复记录里的 `commits`、`files`），完整的列表用 `rf.py trace` 现算。
- **应用里：** 已完成的需求的右边面板、已解决的问题的对话底部，有一小块安静的「改动」：N 个提交、M 个文件（文件列表折叠着）、挂的会话、有没有发布。只读，没有新的页面。

## 历史：会话存档、总结、查询

设计见 `backend/relayforge/sessions/archive.py`、`summary.py` 和 `history.py` 开头。目的：以后问「以前怎么做过、为什么这么定」，能查到当时的需求、裁定、进展和聊天。

- **会话记录另存到本机：** Claude Code 的原始聊天记录（`~/.claude/projects/…/会话.jsonl`，子代理的在旁边的 `会话/subagents/`）会被它自动清理。需求确认完成、放弃，修复合并时，程序把挂在上面的会话（修复还包括排查会话）压缩复制到 `~/.relayforge/archive/项目标识/R-…或F-…/`（目录 700、文件 600；`RELAYFORGE_ARCHIVE` 可以换位置）。不进仓库；仓库里只在需求文件头 `archived`、`archive_missing`（修复记录里同名两项）记会话编号，加一行变更记录。复制失败只记日志，不挡确认完成。应用打开项目时在后台跑一次 `rf.py archive sweep`，把还没存过或后来又聊长了的补存，原始记录已经不在的记成「原始记录已不在」。
- **客观标签：** 确认完成、问题解决时由程序算（不经模型）：涉及的功能点、模块、裁定、问题，写进文件头 `tags`。改过的文件和完成记录一样不写列表，查的时候由 git 现算。
- **总结：** 确认完成（合并成功）以后，应用在后台跑 `rf.py summarize R-…`，和问题初判一样调一次无界面模型（设置里选的那个），一次给出概括标签（`topics`）、几句话的总结（需求文件的「总结」一节）和聊到了但没记下的决定。没记下的决定照抽取的老路进收件箱，合并成草稿裁定、行首〔待确认〕、出处是那个会话的那条消息，等你确认；程序和模型都不确认。一次只总结一个；失败或没装模型时需求照常完成，面板显示「还没总结」和「重新总结」。再总结一次替换上次的，提过的决定不再提。
- **需求之间的冲突：** `rf.py conflicts [--json]`（`requirements/conflicts.py`，只读，不调用模型）对每个进行中、有自己工作目录的需求和修复，算它改了哪些文件（已提交的：`git diff 合并目标...分支`；还没提交的：工作目录里的 `git status`；`.relayforge/` 不算），两两求交集；再用 `git merge-tree --write-tree` 不碰任何工作目录地预演合并：每个分支对合并目标（项目主目录签出的分支），以及改动有重叠的那几对分支之间（只看已提交的）。`main/conflicts.js` 在会话说完一轮、需求列表刷新（包括合并以后主分支前进了）时去抖 10 秒在后台重算，推 `conflicts` 给界面；界面第一次要（`conflicts:get`）时马上算，之后的动静不再把这次往后推。`renderer/scripts/conflicts-model.js` 算说法：看板卡片上最多两行（会冲突的在前，红色；只是改到同一处的黄色），进行中需求的右边面板「和其他需求的改动」列出全部文件和怎么办（让开发会话现在就同步合并目标、设成前置需求、先做完一个）。只提示，不改依赖、不改代码。重算出和合并目标会冲突的，经收件箱告诉那个需求或修复的开发会话现在就同步（`git merge` 合并目标、解决冲突、跑测试）；和别的需求会冲突的，告诉两边各自尽量少改这些文件、谁等谁由用户决定。同一组文件只说一次，会话没开着就排着、不替你打开，立项中的不提醒（立项会话只读）；只是改到同一处、还不冲突的只在界面上标。立项时按历史预测（第 6 步）：`rf.py conflicts --predict R-…`（`conflicts.predict`）从这个需求「要改的功能点」（含模块）找出改过同样功能点、已经完成的需求，用 `sessions/trace.item_files` 拿到它们改过的全部文件，按次数排出预计会动到的文件（只算现在还在的），再和进行中需求实际改的文件比，加上同样要改这些功能点的立项中、进行中需求，列成「可能撞上」。立项中的需求面板「和其他需求的改动」里显示（主进程一分钟内同一个需求不重算），点「确认立项」时确认框里也列出来；只提示，不拦立项。
- **Codex 钩子的信任（`main/codex-trust.js`）：** Codex 的钩子要用户信任过才运行，后台运行时会跳过未信任的钩子。应用每次启动（窗口加载完）和窗口回到前台时检查：装了 Codex 才查，用 `codex-hooks.js` 的 `trustEntries` 算出每个钩子在 Codex 里记信任用的键（`/<session-flags>/config.toml:事件:0:0`）和指纹（sha256(按键排序的紧凑 JSON)，和 Codex 源码 `hooks/src/engine/discovery.rs` 的 `hook_hash` 一致），和 `~/.codex/config.toml`（或 `$CODEX_HOME`）里 `[hooks.state]` 的 `trusted_hash` 比，推 `codex:trust` 给界面。没信任或改过（应用升级、换安装位置都会变）时弹窗（`renderer/scripts/codex-trust.js`、`codex-trust-model.js`），列出要运行的命令和时机；「以后再说」这次启动里不再弹；点「信任」经 `codex app-server` 的 `config/batchWrite` 写入（和 Codex 终端里「Hooks need review」写的是同一处），不用 `--dangerously-bypass-hook-trust`。没信任时 Codex 的无界面会话在过程记录里提示一次。
- **无界面运行的会话（`main/headless.js`、`main/codex-app-server.js`、`main/hitl.js`）** 测试会话的再测一轮、合并前的同步（会话没开着时）、问题的修复会话在后台跑一轮。`sessions.open({ headless: true })` 保留会话设置，Claude Code 加 `-p --output-format stream-json --verbose`，Codex 用 `codex app-server --listen stdio://`，经 JSON-RPC 新建或恢复原生线程，再开始一轮。输出整理成可读过程，点开后台会话时回放。结束时沿用钩子报告和原来的会话流程，剩余的收件箱消息在下一轮交付。

- **会话收件箱（`main/inbox.js`）：** 程序发给会话的每一句话——测试会话的「再测一轮」、测试交回的问题清单、测试集改动被你退回、问题的补充和退回修复、同意拆分的回执、合并前的同步说明（界面经 `sessions.open({ say })` 交给开着的会话）——都经 `inbox.post` 出去，不再各处直接往终端里输。消息先存在本机 `~/.relayforge/inbox/<项目路径的散列>.json`（应用重启不丢；带 key 的同一件事只发一次），每段前面标「〔RelayForge 程序 · 来源 · 编号〕」，开场白里的 `INBOX_GUIDE` 说明这种话是程序转来的通知、不代表用户同意了只由用户决定的事。送的时机看 `attention.js` 记的会话状态（starting / running / reply / answer / approve / idle / exited，来自钩子或 Codex 的聊天记录）：只在说完了（reply）或停着（idle）时用 `sessions.type` 输进去，几条排着的合成一段；在干活、在问你问题、在等你批准时排队，等它这一轮说完再送（在等批准时输进去的字和回车可能被当成对批准框的回答）。后台 Codex 运行中用 RPC（`turn/steer`）交付，遇到待批准或待回答的卡片时也排队。不带开场白打开的会话先算 starting，4 秒后才算能收。会话没开着：排着，并像以前一样让界面在后台打开它（`tests:say` / `issues:say`），`sessions.open` 用 `takeForOpen` 把排着的话放进开场白。会话的聊天记录里出现了消息编号就记成读到了（seen）。交付方式（第 4 步）：会话的钩子能用时不往终端里粘贴正文——这一轮说完时由 Stop 钩子把排给这个会话的话作为理由交回（`core/inbox.py`，经 `rf.py hook event` / `hook codex`；最后一句在问用户问题时不交），会话早就停下了只往终端里输一行固定的唤醒句（`inbox.js` 的 `WAKE`），提交时由 UserPromptSubmit 钩子用 `additionalContext` 把正文交过去。钩子读的收件箱文件在会话环境变量 `RELAYFORGE_INBOX` 里，只交消息里记着 `session` 是自己的那些，交出去的编号追加到 `<收件箱文件>.delivered`，应用读到后记成已送出（`via`：stop / prompt）。这个会话还没报过钩子状态（Codex 没信任钩子等），或者唤醒以后钩子没交（那一轮说完了还排着），退回往终端里粘贴正文（`via: type`）。在真实的 Claude Code 会话里试过：Stop 钩子交回的话模型照着做了，聊天记录里留下「Stop hook feedback」和消息编号。需求的开发和测试、问题的修复和排查，以及日常聊天的终端旁都有「程序消息」。展开可看来源、入队时间、送出方式、读到状态和正文，长正文可以单独展开。排队时，会话标签或列表项显示黄点。点「撤回」后消息从投递队列移除，保留撤回记录。钩子已经取走的消息以实际交付回执为准。主窗口通过 `inbox:list` 读取所选会话，通过 `inbox:queued` 初始化黄点，收到 `inbox:changed` 时刷新对应会话。

- **Codex 会话的钩子：** Codex CLI 有和 Claude Code 同名的钩子事件。`main/codex-hooks.js` 启动 Codex 时用 `-c` 传入 UserPromptSubmit、PreToolUse、PermissionRequest、PostToolUse（后台跑）、Stop、Interrupt 六个钩子，命令都是 `python3 rf.py hook codex`，不改用户的 `~/.codex/hooks.json`。Codex 要求钩子先经用户信任才运行：第一次开 Codex 会话时终端里出现「Hooks need review」，信任一次即可；信任按钩子内容记在 `~/.codex/config.toml` 的 `[hooks.state."/<session-flags>/config.toml:事件:0:0"]`，不跟目录走，所以钩子的内容必须固定——会话编号（`RELAYFORGE_SESSION_ID`）和这个会话不能改的地方（`RELAYFORGE_GUARD`）都放在会话的环境变量里。`rf.py hook codex` 把 Codex 自己的会话编号换成 RelayForge 的，再交给 `hook event`（状态，含等批准；Codex 的 Interrupt 记为停了）或 `guard.py`（执行前）。钩子一开始报状态，`attention.js` 就把这个会话标成 `hooked`，`watcher.js` 不再从聊天记录读这一轮的开始和结束；没信任时照旧读聊天记录。停下来时的几项检查（没记进展、修复没交回、排查没记结论、测试会话改了产品代码等）对 Codex 会话也生效：它们读聊天记录都经过 `core/transcript.py` 的 `claude_shaped`，把 Codex 的记录换成 Claude Code 的格式——Codex 新版把工具调用写在一段 JS 里（`tools.exec_command({cmd:…})`、`tools.apply_patch(…)`），跑命令记成 Bash，补丁里的每个文件记成一次 Edit，问用户的工具记成 AskUserQuestion；钩子让它接着做时交回的 `<hook_prompt …>` 和环境说明不算新的一轮。shell 命令写文件（不经 `apply_patch`）拦不住，和 Claude Code 一样；需求和修复的会话里，记录目录在项目主目录、不在 Codex 可写的工作目录里，由 Codex 的沙箱挡住。
- **后台记录：** 设置里的「后台记录」（应用级，`settings.json` 的 `monitor`，默认关）。打开以后，`main/monitor.js` 在会话每说完一轮时（`attention.onSettled` 的 reply / answer / exit），调用 `rf.py monitor record --session … --kind … --owner … --agent … [--transcript …] [--waits JSON] [--closed]`，由 `sessions/recorder.py` 把新说完的几轮整理成一轮一行，追加到 `~/.relayforge/monitor/项目/events-年-月.jsonl`（`state.json` 记到第几轮，不重复；`README.md` 是给分析的 Agent 看的字段说明）。「等你批准」到再动起来的时间随下一次记录交过去；会话关掉时带 `--closed`，把没说完的最后一轮也记下。只记行为，不记工具输出，像密钥的打码，不进仓库。
- **监控：** `rf.py monitor [--since 日期] [--kind 种类] [--owner R-…|F-…|I-…] [--session S-…] [--json]`：从需求、修复、排查、大图和日常聊天挂着的会话记录里，由程序算出三件事：开场白里的规矩（`sessions/monitor.py` 的 `RULES`，和 `prompts.js` 一一对应）每种会话做到了几个；每个工具、每条 rf.py 命令用了多少次，开场白推荐的命令（`GUIDED`）在该用的会话里有几成用了；打转的地方（被规则拦下后还在重试、同一步反复失败、一轮里反复改同一个文件、等一条命令或批准等了很久、模型停着没动、很长的一轮、用户打断）。只读，不调用模型，不预先放行给会话：给人和开发 RelayForge 的人看。
- **查：** `rf.py history search 词… [--tag/--feature/--file/--kind]`、`history show R-…|I-…|D-…|S-…`、`history session 会话编号 [--steps] [--grep 词] [--tail N]`（`--steps` 按轮次列出读了什么、跑了什么、改了哪些文件、失败和被拒绝的步骤、提交、用时和 token；`--brief` 是续接用的简要版：最后 3 轮、每轮最后 8 步。应用另开开发、修复或测试的后续会话时，`sessions.js` 把上一个会话的 `--brief` 放在开场白末尾，取不到就不带，最多等 15 秒）。只读，应用开的每一种会话都预先放行（立项、排查也是），开场白和 `AGENTS.md` 第 21 条都提到它；`summarize`、`archive` 不放行。
- **应用里：** 已完成的需求右边面板，「改动」上面一小块「总结」：概括标签、几句话、涉及的编号、会话记录存到本机了没有、有没有聊到了但没记下的决定在等你确认。已取消的需求只显示会话记录那一行。

## 数据只在项目主目录里有一份

设计见仓库里的 `docs/design/数据只用主目录一份-设计.md`。

- 需求、设计稿、会话进展、裁定、没定的事、问题、功能点、模块、用户旅程都只在项目主目录（你打开的那个目录）现在签出的分支下的 `.relayforge/` 里有一份。应用的列表、看板、右边的面板、设计稿预览、大图和问题页都只读这一份。
- 需求和修复各自的工作目录只改代码。会话照常在工作目录里跑，但它记的进展、写的需求内容、画的设计稿、记的裁定，都由 `rf.py` 写到项目主目录。开场白里给它的需求文件、会话进度、事实摘要都是主目录里的完整路径，并告诉它工作目录里的 `.relayforge/` 是旧副本、不作数。
- 还没确认完成的需求带来的事实标为「进行中，尚未完成」：新加的功能点、裁定文件头写 `in_progress`，改现有功能点的说法行首加〔进行中 R-…〕、被它换掉的旧说法加〔R-… 完成后替代〕，旧的说法照旧算数。大图上它们带着「进行中」的标记，事实摘要里单独列出来，别的需求的会话不拿它们当依据。确认完成时转成现行；取消时移到 `history/` 或不再算数；恢复时拿回来。
- 事实改动由程序攒着提交到项目主目录当前的分支上：确认立项、确认完成、取消和恢复、手动改状态、你对问题做决定、会话停下来时。只提交 `.relayforge/` 下的路径，不碰你别的改动；你正在合并或 rebase 时先不提交。主目录里还没提交的事实不挡确认完成和确认修好了。
- 合并只合代码：目标分支上新多出来的提交只改了 `.relayforge/` 的，不算分支没包含目标分支的最新内容，不用为此回到会话里合并。
- 以前的布局里，进行中需求的事实在各自的分支上。按你的决定这些不搬过来：只在旧需求分支上的需求不出现在列表和看板上，留下的 `.worktrees/R-…` 目录和 `req/…` 分支应用不删、也不碍事。已经在项目主目录里的（以前完成并合并的需求等）照常显示。
- 你在项目目录里切换了分支，看到的就是那个分支上的数据。

## 需求看板

- 「需求」里没有选中任何需求时显示看板，需求按阶段分成五列：立项中、进行中、待验收、已完成、已取消。点卡片进入这个需求；点左边列表上方的「看板」回来。
- 阶段默认是推出来的：还没确认立项的算「立项中」，卡片上显示清晰度；以前没走立项、也还没写验收条件的老需求也放在这一列；已经立项的算「进行中」；计划里的步骤都做完算「待验收」；你确认完成后算「已完成」。
- 也可以手动改：在左边列表或看板卡片上右击，菜单里有「打开」「修改状态」（五个状态，当前的打勾）和「取消这个需求…」；或者把看板卡片拖到另一列。规则是严格的：已完成、已取消之后不能再改；已立项的不能退回立项中；从立项中改到进行中、待验收或已完成，至少要有一条验收条件。不能改的菜单项是灰的，鼠标停上去能看到原因；拖卡片时放不进去的列会变灰。改到已完成（合并进主线）和已取消（分支保留）之前先弹确认框，其余直接生效，底部提示改成了什么。手动放到进行中或待验收后，就按你放的算，不再按计划自动算。

## 进展是怎么来的

- Claude Code 干活时用 `rf.py note` 把进展、计划、你做的决定、没定的问题、需求的内容记进项目文件；编号、出处和格式由这个命令生成。应用盯着这些文件，一变就刷新。

## 提醒

Claude Code 的会话有三种状态：正在干活、停下来等你、没事。停下来等你又分三种：回复完了、在等你回答（回复的最后一句是个问题）、等你批准（它要做一个需要你同意的操作）。

- 正在干活的会话，在列表和看板卡片上安静地标着「正在干活」（一个缓缓闪的小灰点）。它不是在等你，所以不弹通知，也不算进图标上的数字。
- 你正看着那个会话时不提醒。
- 否则：左侧导航的图标上出现数字，列表和看板卡片上标出是哪一个、等的是什么；同时弹一条系统通知，点通知直接跳到那个会话；Mac 的程序坞图标上也有数字。
- 点开那个会话，或者在里面打字，提醒就消掉。同一件事不会重复弹通知。
- 第一次弹通知时 Mac 可能会问是否允许通知，需要选允许。

它是怎么判断的：

- 你发出一句话，就算开始干活；它回复完了、没有子代理还在跑，才算「回复完了」或「在等你回答」。
- 它派出子代理（Task 工具）后，自己的这一轮可能先结束了，子代理还在跑。这时仍然显示「正在干活」，不会提前说「回复完了」。子代理都做完以后，Claude Code 会自己把它叫醒接着回复，等那一次回复结束才提醒。
- 要批准的操作直接用 Claude Code 的「请求许可」事件判断，不再靠通知里的字眼。它的「在等你输入」提醒不算。你批准后它一动手，状态回到「正在干活」。
- 兜底：如果子代理一直没有报告结束，4 小时后不再等它；等的子代理都没了，3 分钟内没有后续动静，就当它回复完了，提醒一次。会话已经回复完了之后，Claude Code 内部偶尔还会起一些小帮手（比如做摘要），它们不会让会话又变回「正在干活」。
- 「正在干活」的会话如果半小时内一个事件也没有（比如你按了 Esc 打断它），就不再显示正在干活。
- 判断都在 `rf.py hook event` 里做，状态记在应用临时目录里和事件文件放在一起的状态文件里，不在项目里；应用只读已经判断好的结果。钩子里出任何错都不会影响会话，唯一会拦它的是前面说的「这一轮没记进展」的检查。

## 怎么工作

- 点左栏「＋ 新建需求」弹出窗口，写几句话，可以粘贴、拖入或选择图片，⌘↩ 创建；图片会在立项会话的第一句话里交给 Claude Code。
- 草稿目录里的文件在需求完成或放弃时删掉；设计稿本身已经在仓库里。
- 新建需求调用 `rf.py req new`：生成编号，开分支 `req/…`，在项目根目录的 `.worktrees/` 下开工作目录（只用来改代码），需求文件建在项目主目录的 `.relayforge/requirements/` 下，状态是立项中（`state: draft`）。
- 第一个会话是立项会话（见上面的「立项」）。确认立项调用 `rf.py req start`，之后开的是开发会话。
- 再次打开需求时接着上一个会话聊；立项刚通过、最后一个会话还是立项会话时，另开开发会话。一个需求可以先后挂多个会话。
- 确认完成调用 `rf.py req done`：把分支上的代码合并进项目目录现在签出的分支（只合代码，分支上的 `.relayforge/` 不覆盖主目录，有的话在完成记录里说明），再把这个需求带来的事实转成现行，在完成记录里写下它新增和修改了哪些模块、功能点、裁定、设计稿，收掉工作目录和分支。下面几种情况会拒绝并说明原因：还有代码没提交、项目目录不在任何分支上（detached HEAD）、项目目录里合并要改到的文件有未提交的改动、分支上没有任何改动、需求还在立项。
- 同一时间只合并一个需求（`app/src/main/merge.js` 排队，`rf.py req done` 在 `.git/relayforge-merge.lock` 加锁）。别的需求正在合并时，点了确认完成的需求显示「排队等合并」，轮到它自动开始。
- 合并一律先在开发会话里做：需求的分支还没包含目标分支的最新内容，或者还有没提交的改动，程序就打开这个需求的会话（开着就直接用），替你告诉 AI 提交改动、把目标分支合并进来、解决冲突、跑测试、提交。需求显示「AI 在开发会话里合并 main」（或你签出的分支），它这一轮说完，程序检查：分支已经包含目标分支的最新内容、没有没提交的改动，才把它合并回去并标成已完成，这一步不会再有冲突；还没弄好就等你在会话里接着让它处理。合并回去时因为项目目录的状态（比如有没提交的同名文件）失败，显示「合并卡住了，要你处理」，处理好点「重新检查并合并」。右边也可以随时「中止合并」退出队伍（用 Codex 时没有「说完了」的通知，要手动点「重新检查并合并」）。
- `resources/pty_bridge.py` 在一个假终端里启动 Claude Code，只用 Python 标准库，不需要编译任何组件。
- 主进程（`src/main/`）启动 Claude Code 时带上一组钩子（都交给 `rf.py hook event`：开始干活、停下来、子代理开始和结束、请求许可），和记录、查影响、设计稿、问题（`issue new`、`list`、`show`、`brief`、`handback`）几个命令的放行规则，立项中的需求再加上禁止在项目目录下改文件、只许写草稿目录的规则，排查会话在这之上还放行 `issue finding`、拒绝由你决定的命令；它盯着 `.relayforge/` 下的文件（包括 `designs/`），变了就用 `rf.py state --json` 和 `rf.py req list --json` 重读。
- **拦下时说清该怎么做：** 权限规则拦下一次调用时，Claude Code 只说「被禁止」，会话常常换个写法再试（会话监控里看到过同一个需求文件被 Edit 拦了 5 次）。所以每个会话还带一个同步的执行前钩子（PreToolUse，`claude-settings.js` 的 `guardHooks` → `rf.py hook guard` → `core/guard.py`）：认出一定会被拦的调用，先拦下并说明该改用哪条命令——只由用户触发的 rf.py 命令（`USER_COMMANDS`、`APP_ONLY`，每条在 `guard.HINTS` 里写了会话该做什么）、立项和排查会话改项目文件、立项排查测试会话改记录目录（按改的是需求、功能点、决定、进展、问题、测试集还是设计稿给出对应的 `note` 等命令）、测试会话改 `src/main`；同一个会话第二次在同一个目标上被拦，说明里加一句「不要再换方式重试，停下来告诉用户」（计数在 `~/.relayforge/guard/`，一周没动的清掉）。拦不拦仍以权限规则和 rf.py 自己的校验为准，钩子只拦它们本来就会拦的，出错时什么也不做。`rf.py` 遇到 `hook guard` 只加载 `guard.py` 一个文件，每次约 60 毫秒。Codex 会话用同一套规则：启动 Codex 时用 `-c hooks.<事件>=…` 传入内容固定的钩子（`main/codex-hooks.js`），都交给 `rf.py hook codex`；执行前的检查同样只加载 `guard.py`，Codex 改文件用的 `apply_patch` 从补丁里认出文件再逐个核对，这个会话不能改哪些地方由环境变量 `RELAYFORGE_GUARD` 传入。另外 `trust.user_gate` 拒绝时也附上同一份 `HINTS`（「如果你是 AI 的会话：……」）。
- 终端和窗口之间走应用内部的管道，不开网络端口。

## 代码结构

应用分成三层：主进程（Node.js，管会话、文件和系统通知）、预加载脚本（只把一组固定的接口交给页面）、渲染层（窗口里的页面，碰不到 Node）。具体的事都交给仓库根目录 `backend/` 下的 Python 后端 `rf.py` 去做。

```
app/
├── package.json             入口是 src/main/index.js
├── electron-builder.yml     打包成 macOS 应用的配置
├── build/                   打包用的资源（entitlements.mac.plist，以后放图标）
├── resources/
│   └── pty_bridge.py        假终端：在里面启动 Claude Code，经管道和窗口相连
└── src/
    ├── main/                主进程，一个文件一件事
    │   ├── index.js         启动、建窗口、退出时清理
    │   ├── config.js        环境变量和路径（rf.py、pty_bridge.py、~/.relayforge、事件文件）
    │   ├── state.js         当前项目、主窗口、开着的会话，往界面发消息
    │   ├── backend.js       调用 rf.py 和 git
    │   ├── project.js       找项目根、初始化、导入时的大图草稿、切换项目、项目菜单
    │   ├── requirements.js  需求列表、新建、确认立项、确认完成、放弃、大图
    │   ├── issues.js        问题：列表、后台初判的队伍（最多两个）、开始修复（一条或几条一起）、确认（一起修时先确认的不合并）、撤回确认和退回、转为需求、交给 AI 排查和把回复交给开着的排查会话、提醒
    │   ├── sessions.js      开会话（假终端里的 Claude Code）、关会话、整理进展
    │   ├── prompts.js       开场白：立项、开发、后续会话、问题的修复会话和排查会话
    │   ├── claude-settings.js  启动 Claude Code 带的钩子和权限规则、草稿目录
    │   ├── attention.js     提醒：读钩子事件、正在干活和等你、系统通知、程序坞数字
    │   ├── designs.js       设计稿的隔离窗口，拦掉设计稿的网络请求和跳转
    │   ├── publish.js       发布：后台运行 rf.py publish（有超时、一次只做一件事）、顶栏提示用的状态、「让 AI 来合并」的开场白和聊天
    │   ├── session-history.js  用量和回放（通过 rf.py 查询本机记录）
    │   ├── trace.js         改动：rf.py trace --json（只读），给「改动」块
    │   ├── merge.js         合并排队：需求的确认完成和问题的确认修好了排在同一个队伍里
    │   ├── watcher.js       每 1.5 秒看一眼：钩子事件、事实文件、设计稿、问题、会话停没停
    │   ├── stuck.js         后台会话超时、交互会话卡住提醒和收件箱回执计时
    │   ├── images.js        选图片、把粘贴的图片存成文件
    │   └── ipc.js           和界面之间的所有通道
    ├── preload/
    │   └── index.js         window.shell：页面能用的全部接口
    └── renderer/
        ├── index.html
        ├── styles/app.css、issues.css（问题页，从交互稿搬来）
        └── scripts/         按界面区域分开的普通脚本，按 index.html 里的顺序加载，共用一个全局作用域；
                             各自的事件由 main.js 按顺序绑上（core、terminal、reqs、board、new-req、intake、
                             designs、panel、attention、layout、map、actions、compose、issues、main）；
```

- 应用总是用自己带的 `backend/rf.py`，钩子命令和放行规则里写的也是它的绝对路径。
- 初始化项目时，`rf.py init` 把入口 `rf.py` 和整个 `relayforge` 包复制到项目的 `.relayforge/bin/` 下。项目里的钩子、AGENTS.md 里的命令都只认 `.relayforge/bin/rf.py` 这个入口，所以以前初始化的项目不用改；重新初始化会补上包。本仓库自己的 `.relayforge/bin/` 也是这样一份副本，改了 `backend/` 要同步过去。
- 后端只用 Python 标准库，运行时不写 `__pycache__`。
- 测试：在仓库根目录运行 `python3 -m unittest discover -s tests -t .`（后端，测试从 `backend/` 导入 `rf`；问题模块的在 `tests/test_issues.py`），主进程的几个模块用 `node --test tests/*.cjs`。
- 打包（还没实际做过）：`npm install --save-dev electron-builder`，再 `npx electron-builder --mac`。`backend/` 放进应用资源目录，`pty_bridge.py` 解到 `app.asar.unpacked` 里让 python3 能读到。打出来的应用运行时仍然需要这台电脑上有 python3 和已经登录的 `claude`。
